# 01 产品定位

> VibeGuide 是集成在 DeepSeek Harness 中的理解与沟通助手。用户照常与主 AI 开发，侧栏帮助用户看懂项目和变化、判断方案的影响，并把明确的修改要求传回主对话。

### 用户希望获得的能力

1. **看懂过程**：知道 AI 当前在做什么，实际完成了什么。
2. **判断方案**：知道某个选择如何影响使用体验、费用、维护和以后修改。
3. **表达修改**：用自己的话提出要求，不需要先写技术指令。
4. **建立项目认知**：逐渐知道页面、数据保存和外部服务各自承担什么职责。

### 两个相互配合的界面

| 主对话 | VibeGuide 侧栏 |
|---|---|
| 澄清需求、制定开发计划、执行修改、运行检查 | 解释方案与进展、说明影响、帮助理解检查结果 |
| 接收正式要求，处理执行中的关键选择 | 区分追问和修改意图，转交明确要求并显示回执 |
| 原始回答就应让非技术用户看懂 | 提供可选择的进一步解释和项目上下文 |

### 产品边界

VibeGuide 的旁路解释不直接修改业务代码、不独立运行部署或业务操作。开发执行、权限请求和必要的确认继续由主 AI 与宿主负责。

学习发生在真实开发过程中，目标是理解职责和后果。本版不设计编程课程、小测、熟练度评分，也不默认展开文件与代码差异。

侧栏可以关闭。关闭或忽略讲解不构成暂停开发的理由，也不代表用户已经理解或同意某个方案。

# 02 问题与机会

### 直接来自使用经历的问题

用户能描述想要的功能，但面对技术性回答、方案和技术栈时，不知道选择会带来什么影响。反复追问术语后，仍可能无法判断方案是否符合实际需要；直接开发又会产生项目不受自己掌控的感觉。

| 痛点 | 典型时刻 | VibeGuide 应帮助用户得到的答案 |
|---|---|---|
| 方案看不懂 | AI 要用户选择实现方式 | 这个选择改变什么？有什么代价？以后能不能调整？ |
| 项目结构看不懂 | 接手已有项目或增加功能 | 这件事涉及哪几个部分？它们怎样配合？ |
| 改动看不懂 | AI 汇报“已经完成” | 用户现在能做什么？有什么限制？哪些结果有证据？ |
| 不知道怎样纠偏 | 效果不符、报错、反复修复 | 当前问题影响什么？有哪些处理办法？怎样把意图说清楚？ |

### 产品机会

把理解放在真实开发上下文里，减少用户来回搬运报错、术语和代码的负担。解释应帮助用户做判断或继续沟通，同时保留对项目整体结构的认识。

### 可参考的产品机制

| 类型 | 可参考的机制 | 本项目需要验证的假设 |
|---|---|---|
| AI 编程工具 | 主对话、执行结果、任务进展 | 在原有工作流旁补充解释，能否减少用户的盲选 |
| 项目解读工具 | 功能地图、模块关系、数据流 | 与当前改动关联后，是否更容易帮助非技术用户理解 |
| 代码解释工具 | 就地选中与追问 | 用后果和取舍组织回答，是否比术语定义更有用 |

以上是参考方向与待验证假设，不是对其他产品当前能力的完整评测。课程汇报中应使用实际试用结果，避免以“所有现有工具都不能做到”作为论据。

# 03 目标用户与三类场景

核心用户是使用 AI 开发产品的非技术人员，包括产品、设计、运营、研究人员及跨专业学生。他们需要对自己的项目做决定，但不以掌握编程语法为目标。

### 三类场景均纳入课程交付

| 场景 | 用户起点 | 主对话与侧栏如何配合 |
|---|---|---|
| A 接手已有项目 | 有现成代码，不清楚组成和修改位置 | 侧栏建立功能与结构概览；主对话接收目标，侧栏解释影响 |
| B 从零新建项目 | 只有想法，尚未决定关键行为 | 主对话用易懂的选项澄清关键问题；侧栏按需补充解释，随后跟随开发更新 |
| C 开发途中卡住 | 报错、效果不符、修复未见进展 | 侧栏说明现象、影响和已知尝试；明确处理要求转给主对话 |

场景可以自然切换。例如新项目做到一半出错，进入问题解释；重新打开已有项目，可以先看结构，再继续修改。不要求用户先完成一套课程或固定步骤。

### 用户故事

- 设计师接手开源博客，希望知道改成作品集会涉及哪些部分，以及是否影响文章详情。
- 学生从零做 21 天思考小游戏，希望理解单设备保存、换设备继续和隐私之间的关系。
- 产品经理给内部工具增加审批功能后遇到登录问题，希望知道谁受到影响，以及下一步应修什么。

### 使用前提

课程交付支持在指定兼容版本的 DeepSeek Harness 中安装插件、选择项目和使用侧栏，并提供必要的安装说明及首次使用提示。专业代码审查、通用环境教学和整套宿主一键安装不属于本版交付范围。

目标用户不必会读代码；实现与验证也不得把“自己检查源代码”作为判断产品是否正确的必要条件。

# 04 产品原则

| 原则 | 具体要求 |
|---|---|
| 原始回答可理解 | 主 AI 的问题、计划和结果先说产品行为与后果。侧栏不是读懂主对话的必经步骤。 |
| 解释不阻塞开发 | 阅读、追问、关闭侧栏不暂停主线。主 AI 必要的产品决策和宿主权限流程照常处理。 |
| 影响优先 | 先解释变化和影响，再按需提技术名称；默认不做术语百科、文件逐项讲解或代码差异教学。 |
| 意图与行动分开 | 普通问题只解释；明确修改直接转交；含糊或冲突要求先澄清相关部分。 |
| 状态有依据 | 区分用户要求、AI 建议、已观察事实与推断；区分已修改、已发送和检查通过。 |
| 不打断阅读 | 正在阅读的内容保持位置；新进展以提示呈现，用户可回到最新。旧结论失效时明确标记。 |
| 一套开发计划 | 主对话持有和更新执行计划，侧栏解释和呈现，不维护第二套独立审批流程。 |
| 用户可以纠正 | 用户能指出解释错误、修正记录；查看过不等于掌握，讨论过不等于同意。 |

### 写入与执行边界

VibeGuide 可以保存必要的项目记录、讲解历史和发送回执。业务代码与执行操作由主 AI 处理。恢复功能不在本版范围内：不建立自动恢复存档，不提供回退、局部撤销或专门的“请 AI 改回”入口。

用户想恢复某种效果时，可以直接在主对话中提出修正要求。该要求仍按普通开发任务处理，不承诺恢复历史文件或外部服务状态。

### 解释质量要求

只读解释仍可能影响用户决策。对不知道的事实明确说不知道；对推断说明依据和不确定性。出现文件出处不代表内容必然正确，过时证据不能继续支撑当前结论。

# 05 产品形态

用户照常在 DeepSeek Harness 主对话中开发。VibeGuide 使用一个模式、一个侧栏，提供三个入口。

| 入口 | 回答的问题 | 主要内容 |
|---|---|---|
| 当前进展 | AI 在做什么？刚才有什么变化？ | 当前目标、最近重要变化、影响、检查情况、追问和发送回执 |
| 项目结构 | 产品由什么组成？一次操作经过哪里？ | 功能与职责、数据经过的部分、当前改动关联的位置 |
| 了解过的 | 我之前问过什么？当时怎样解释？ | 查看和追问记录、关联项目状态、可重新查看或纠正的解释 |

### 双向沟通

**主 AI → 用户**：项目事实和执行结果经过整理，形成与用户体验相关的解释。侧栏可使用文件、事件、检查结果作为依据，但不把原始工具日志当成默认界面。

**用户 → 主 AI**：侧栏先识别表达意图。明确的修改要求带上原话及必要背景转交；问句和方案讨论留在侧栏。转交后给出可追踪的回执。

### 呈现规则

- 当前进展默认展示几句简短结论，深入内容按需展开，不机械限制句数。
- 优先在侧栏提供问题入口；主对话中的选中提问等增强交互，按宿主验证结果接入。
- 检查结果和计划摘要放在相关进展中，无需另外维护“计划”“检查”页签。
- 不要求用户编辑文件路径、依赖名称或结构化任务字段。
- 与主对话重复的信息尽量只呈现一次，避免两边同时生成大量通知。

### 连续使用

切换项目后，侧栏加载对应项目记录。切换会话后，显示该会话的执行状态；历史解释可保留，但需要标明来源和适用范围，不能混入其他项目或会话的当前上下文。

# 05 宿主接入与验证

### 固定首发宿主：DeepSeek Harness

本版仅交付 DeepSeek Harness 集成。产品逻辑与宿主接入保留清晰边界，方便维护；其他宿主的适配与通用替代界面不作为课程交付要求。

已有仓库调研记录了侧栏、消息事件、模型调用和消息转交的候选接入点。接口资料只能说明可能的实现路径，不能替代当前安装版本的端到端验证。

| 需要验证的能力 | 验证成功的可观察结果 |
|---|---|
| 侧栏加载与生命周期 | 在固定版本中安装后可打开；切换项目、会话、重启后归属正确 |
| 进展与变化来源 | 事件关联到正确任务；工具调用结束不会被直接标为功能完成 |
| 独立解释与追问 | 追问可返回结果，主 AI 的开发任务继续运行 |
| 修改要求转交 | 明确要求进入正确主会话，只产生一次有效消息并显示回执 |
| 模型与费用 | 实测模型配置来源、并发影响、调用失败与费用提示方式 |
| 结果与过时处理 | 检查结果能关联当前代码；代码变化后相关旧结果失效 |

### 实施前的最小验证

固定一组宿主与插件版本，完成“打开侧栏 → 接收一次真实变化 → 追问 → 转交一个修改要求 → 显示真实回执”的完整链路，并保存运行证据。将结果用于选择具体接口，不以 HTML 演示替代集成验证。

若某项接入不可用，必须显示相应能力不可用并记录待解决项。不能用模拟进度、自动切换到其他宿主或把消息放入输入框冒充已发送，来宣称目标交付已经完成。

### 用户上手

提供固定版本的安装说明、插件启用方式、项目选择和一次简短示例。模型未配置或插件不兼容时，说明缺失条件及下一步。安装说明需在干净测试环境中走通。

# 06 核心流程与职责边界

> 主对话表达目标 → AI 推进开发 → 侧栏解释当前情况 → 用户理解或追问 → 明确修改要求转回主对话。

这是一条可随时进入的循环，不要求用户依次完成九个页面。项目结构、技术影响、结果检查和问题解释服务于当前任务。

| 阶段 | 主对话 | 侧栏 |
|---|---|---|
| 开始 | 接收目标，澄清真正影响产品的未知项 | 帮助理解选项与后果；展示已有结构或计划草图 |
| 开发 | 修改代码、运行命令、更新执行计划 | 呈现当前动作和重要变化，保持追问独立 |
| 判断 | 处理需要用户选择的实际问题 | 说明方案差别、依据、限制；不重复发起相同提问 |
| 修改 | 接收明确要求，决定执行安排 | 传递原意，显示发送与处理状态 |
| 检查 | 执行合适的验证并提供结果 | 解释覆盖了什么、仍不知道什么，提供可操作的体验检查 |
| 继续 | 根据结果继续或调整任务 | 更新结构与项目记录，使旧解释适当失效 |

### 三类入口

接手项目从结构概览进入；新项目从主对话的关键需求澄清进入；卡住时从当前问题及其影响进入。三者最终使用同一套解释、沟通和状态规则。

### 节奏和暂停

只保留一个 VibeGuide 模式。调整解释深度不会改变主线是否执行。关闭侧栏、看历史解释、连续追问，都不新增开发暂停点。

主 AI 因真实需求歧义、任务依赖、执行错误或宿主权限而等待时，侧栏准确展示等待原因。用户在侧栏明确提出暂停或取消属于新的控制请求，需通过宿主支持的通道处理并显示实际结果，不能仅改变侧栏标签。

# 07 功能详述 · F1 项目结构

### 解决什么

帮助用户理解“产品能做什么、由哪些部分配合完成”，并把当前改动放回整体结构中。

### 用户看到什么

默认按功能和职责组织少量节点，例如“每日问题”“回答保存”“打卡进度”。再按需说明这些能力由页面、存储或外部服务中的哪些部分承担。

| 层次 | 示例 | 展示规则 |
|---|---|---|
| 产品功能 | 回答今天的问题、查看过去回答 | 默认用用户能操作的行为命名 |
| 职责与联系 | 页面接收输入，保存位置记录答案，进度读取日期 | 解释各部分怎样配合，不先展示文件树 |
| 依据 | 对应文件、事件、需求与检查结果 | 需要核对时展开；不承担代码教学 |

### 一次操作的故事

> 用户提交今天的回答 → 保存回答与日期 → 更新打卡进度 → 再次打开时读取之前的记录。

这条故事必须基于项目现状。尚未实现的部分显示“计划中”；仅从代码推测的连接标明“推测”。功能、模块和文件之间允许多对多关系。

### 更新与边界

- 当前任务涉及的节点可高亮，其他部分仍能查看。
- 每个节点关联来源和项目版本；变化后重新核对相关结论。
- 扫描结果提供结构证据，不能由静态文件直接推断运行正常。
- 结构未知时先显示已确认的部分，不补造连接或隐含实现。
- 实现状态与验证状态分别展示，例如“已修改 · 尚未验证”。

### 验收

用户能指出一个功能涉及哪些职责、数据大致经过哪里，并知道哪些部分尚未实现；无需说出技术术语或文件名。

# 07 功能详述 · F2 技术影响解释

### 解决什么

用户听到了技术选择，但不知道它对自己的产品意味着什么。解释重点是收益、限制、成本和以后调整的影响。

### 默认回答结构

| 内容 | 要回答的问题 |
|---|---|
| 当前作用 | 这个选择正在为项目解决什么问题？ |
| 实际影响 | 用户体验、数据可用性、费用或维护会怎样变化？ |
| 可选取舍 | 如果换一种做法，会多出或失去什么？哪些仍未知？ |

不机械套用三段模板。没有必要选择时，直接解释当前影响；用户追问实现原理时再展开。

### 示例：回答保存

> 现在回答保存在当前浏览器里，用户不用注册就能使用；但换手机后看不到原来的记录。若要换设备继续，需要让不同设备识别同一个用户并访问同一份数据，也会增加使用步骤与维护工作。

可以顺带说明“这是本地存储方案”。默认不讲存储接口的语法、文件位置和实现细节。

### 示例：API Key

> 这是项目调用模型服务时使用的凭证。把它暴露给网页访问者，可能让别人使用你的额度；应由受控的服务端保存和使用。是否有可用额度还需要另外确认。

### 交互与规则

在当前解释、项目结构节点或支持的主对话内容旁提供“为什么这样做”“还有其他办法吗”“这会影响什么”。追问保留所指内容和项目背景，主线继续开发。

讲解不默认罗列技术百科，不把用户看过的内容标为“已掌握”。技术影响没有证据或取决于条件时，要把条件说清楚；费用示例必须注明估算依据或明确只是示意。

# 07 功能详述 · F3 / F4

## F3 目标关联与影响理解

**解决什么**：用户知道想改变的效果，却不知道它与项目哪些部分有关。

用户问“如果希望换手机继续，会影响哪里”，侧栏关联“识别用户”“回答保存”“进度读取”，说明当前限制和可能需要增加的能力。该表达属于讨论，不自动修改代码。

定位结果包含：当前事实、相关职责、可能影响、未知部分。避免直接承诺“不会影响其他功能”；可表述为“目前未发现会影响每日问题展示，修改后仍需检查”。

“我想改这里”用于帮助表达要求；用户若已明确说出目标，直接按 F5 转交，不强制重新填写计划。

## F4 方案与关键选择解释

**解决什么**：主 AI 提出的方案或问题过于技术化，用户无法判断。

主对话负责澄清和维护执行计划，选项本身先说明使用差别和关键影响。用户可以直接看懂并选择；仍有疑问时，侧栏按需补充已有问题与计划的解释。对新的模糊目标，主对话先问少量真正影响行为的问题，数量由不确定性决定；不固定套用问卷，不在澄清前自动搭建项目。

| 关键选择示例 | 应解释的差别 |
|---|---|
| 只在当前设备使用 / 支持换设备 | 注册与身份识别步骤、数据连续性、服务维护 |
| 回答仅自己可见 / 可以公开分享 | 谁能查看、分享后的可见范围和用户预期 |
| 固定每日问题 / 自动生成问题 | 内容可控性、等待时间、外部服务依赖与费用 |

追问随前面的答案变化。例如选择验证码登录后，不机械继续询问密码找回。明确且低歧义的修改直接推进。

主对话出现待回答的问题时，侧栏仅关联原题并提供“帮我理解这些选择”等轻量入口，默认不调用模型重复解释。用户点击入口或主动追问时，才针对具体疑问补充影响与取舍；不另调模型判断“用户是否看得懂”，不自动预生成每个选项的解释。此规则针对选项讲解，不取消开发中重要变化的摘要。

再次查看同一问题时，优先复用依据仍有效的已有解释；选项或相关项目状态变化后，标明旧解释不再适用，等待用户需要时再生成。如果支持在侧栏回答，必须回到原问题的正确通道，避免生成第二份答案或重复任务。无法可靠接回时，引导用户回原问题作答。

**验收**：看懂选项后直接作答，不产生额外的侧栏选项解释调用；主动求助时，无需先完成主 AI 回合就能解释当前选项。用户能说出主要影响，主对话与侧栏显示同一份当前决定。

# 07 功能详述 · F5 修改要求转交

### 意图识别

| 用户表达 | 行为 |
|---|---|
| “为什么不用云端？” | 解释原因和取舍，不转交修改 |
| “用云端会不会更好？” | 帮助比较方案，不把讨论记成决定 |
| “那就改成换手机也能看。” | 直接转交明确要求，显示实际回执 |
| “这个不太合适。” | 澄清具体想改什么，再处理 |

### 转交内容

保留用户原话、所指功能、相关解释及必要的项目背景。系统补充的建议与用户要求分开标记，不擅自增加登录方式、收费服务或其他功能。用户不需要编辑技术字段，也不必每次点击第二次发送。

若当前上下文已经变化，只有实质影响意图解释的部分才需要澄清。例如用户说“就用第二个”，但选项已经变化，不能凭旧位置转交。

### 可追踪的状态

| 状态 | 成立条件 |
|---|---|
| 正在发送 | 转交已发起，尚无可靠接收结果 |
| 已发送 / 待处理 | 宿主确认要求进入指定主会话 |
| 正在处理 | 主 AI 明确开始处理关联要求 |
| 已完成 | 有与要求对应的修改结果，且无未处理的要求；验证结果另列 |
| 处理受阻 | 主 AI 已接收，但执行失败或仍需处理实际问题 |
| 发送失败 / 结果待核对 | 明确失败，或无法确认是否已进入主会话 |

主 AI 忙碌时，默认按宿主支持的待处理消息机制交付，不能因用户在侧栏阅读或提问而打断当前执行。排队能力和关联方式须实测；不得虚构回执。

### 重复与错误处理

同一要求使用稳定标识，避免重试产生重复任务。结果未知时先核对，不直接重发。用户要纠正已发送要求时，把纠正作为新消息关联原要求；不宣称已执行的操作被撤销。

**验收**：明确要求只转交一次；普通追问不发任务；状态与主会话实际一致，保存记录失败不等于发送失败。

# 07 功能详述 · F6 当前进展与改动解释

### 解决什么

用户希望知道 AI 正在做什么、刚才改变了什么，以及这些变化是否符合自己的目标。

### 展示节奏

开发中提供简短的当前动作，例如“正在把回答保存和进度关联起来”。重要变化形成有意义的结果后再汇总解释，不逐条播报工具调用或每一次文件写入。

“为什么这样做”优先依据已记录的决定和主 AI 的说明。仅从代码推测理由时明确标注，不替 AI 编造原始动机。

### 一条解释的内容

| 内容 | 示例 |
|---|---|
| 变化 | 现在提交回答后，今天的打卡进度会更新 |
| 影响 | 再次打开时可以继续查看；当前方案仅覆盖同一浏览器 |
| 关键取舍 | 暂时无需注册；若要换手机继续，需要增加跨设备的数据访问能力 |
| 检查情况 | 同一浏览器刷新保留已检查；换设备同步尚未实现 |

示例仅用于说明结构。实际显示必须依据真实变化和检查结果。

### 发现意外变化

以产品行为判断是否偏离约定。例如“文章详情的字体也发生变化，可能超出你只调整首页的要求”。只有某个文件不在计划清单里，不足以认定改动越界。

提供“问问原因”和表达修正要求的入口，不提供局部撤销按钮。用户也可以直接回主对话说明希望怎样修改。

### 阅读与更新

阅读历史解释时保持当前位置，新进展用提示显示；提供“回到最新”。如果当前所读解释的依据已变化，保留历史内容并标注过时，避免悄悄替换或继续充当现状。

**验收**：用户能用自己的话说出变化及一个重要限制，无需阅读文件清单或代码差异。

# 07 功能详述 · F7 检查结果理解

### 解决什么

帮助用户区分“AI 已经改了”“系统做过检查”和“产品行为符合自己的需要”。

主 AI 和宿主执行检查；VibeGuide 读取实际结果并解释。没有运行记录时显示“尚未检查”，不由模型根据代码生成绿色通过状态。

| 状态 | 用户看到什么 | 不能推导出什么 |
|---|---|---|
| 尚未检查 | 该行为还没有验证记录 | 不能因为没有报错就称为正常 |
| 检查通过 | 检查对象、覆盖行为、时间和结果 | 项目可以启动不等于所有功能正确 |
| 检查失败 | 失败现象、影响与已知原因 | 未确认的猜测不能作为唯一原因 |
| 需要重新检查 | 相关代码或条件已改变 | 历史通过不能直接代表当前版本 |
| 用户体验确认 | 用户明确反馈某项行为符合预期 | 一项确认不能覆盖整个系统 |

### 可操作的体验检查

例如：“写一段回答并提交，刷新页面，查看内容是否仍然存在。”检查紧扣用户目标；用户可以稍后验证，不要求逐项打勾后才允许继续开发。

发现失败后可进入 F9 理解问题。若用户明确说“请修复这个问题”，按 F5 转交；只是查看失败详情时不自动创建修复任务。

### 安全、费用与影响提示

课程范围内解释当前任务中有证据的相关问题。例如已发现的凭证暴露、明确新增的收费服务或已验证的访问限制。没有检查依据时说明未知，不宣称已完成全面安全扫描或费用预测。

本功能不包含存档、回退、文件恢复或“请 AI 改回”的专门入口。完整风险雷达与独立自动检查平台不属于本版范围。

**验收**：用户能准确区分已完成的改动、已经检查的行为和仍需验证的内容。

# 07 功能详述 · F8 项目记忆与了解过的

### 解决什么

减少跨会话重复解释项目的成本，让用户能够找回曾经讨论的选择，同时避免旧解释覆盖新的事实。

| 记录类型 | 记录内容 | 使用边界 |
|---|---|---|
| 用户决定 | 原话、来源、适用项目、后续纠正 | 只有明确表达的决定可作为要求；AI 建议不能冒充决定 |
| 当前事实 | 已观察的结构、变化和检查结果 | 关联证据与项目状态，失效后重新核对 |
| 项目日志 | 重要变化、决定及理由 | 按功能语言记录，保留来源和执行、验证的区别 |
| 了解过的 | 用户打开或追问过的解释 | 只表示有过接触，不推断掌握、认同或偏好 |
| 发送回执 | 要求标识、目标会话和实际处理状态 | 支持追踪及去重，不以记录保存代替发送成功 |

### 换会话继续

新会话使用当前有效的项目摘要：目标、明确决定、当前状态、最近相关变化和未解决问题。若状态无法核对，显示不确定或待更新，不把全部历史讲解重新塞给主 AI。

用户可以纠正记录或要求不再使用某条记录。忘掉一项记忆不会修改业务代码；功能修改需要明确表达为开发要求。

### 存储与隐私

项目记录必须隔离，沟通偏好和项目需求分开处理。优先复用现有存储能力，具体目录与迁移方案在实施验证后确定；不能宣称仅复制一个目录即可完整迁移到任何宿主。

允许关闭持久记录并说明影响。保存失败时提示跨会话续接可能不完整，当前开发不应因此被误标为失败。查看过的解释按需加载，过时内容保留历史标记。

**验收**：换会话后保持已确认要求；用户纠正后不再使用旧结论；另一个项目不会读取到这些记录。

# 07 功能详述 · F9 卡住时的理解与沟通

### 解决什么

用户遇到报错、效果不符或多次修复仍未解决时，需要知道影响范围和可选处理办法，而不是继续盲目发送“再修一下”。

### 用户看到什么

1. **现象与影响**：谁在什么操作下遇到什么问题，哪些功能受到影响。
2. **已知与未知**：有证据的事实、可能原因、尚未排查的条件分别呈现。
3. **已尝试的办法**：主 AI 做过哪些相关尝试，检查是否显示改善。
4. **可选下一步**：继续定位、缩小修改范围或调整实现方式，并说明代价。

### 示例

> 新增登录后，未登录访客打不开原本公开的作品页。已有访问检查能够复现。可能是访问限制覆盖得过宽，还需要核对具体规则。可以先让主 AI 只处理“保持作品页公开”，暂不改变其他登录行为。

这是一项建议。用户问“为什么会这样”继续解释；用户说“就先修作品页公开访问”才直接转交。

### 反复修复提示

仅在同一问题有多次关联尝试、且复现或验证仍显示未解决时，提示“这个问题仍未解决”。同一文件被多次修改本身不构成卡住证据，也不使用固定次数直接判断“越改越乱”。

### 传给主 AI 的问题背景

保留用户期望、实际现象、复现步骤、相关检查和已尝试方法。可以附必要的技术依据，但用户无需阅读或编辑这些字段。缺失信息由主 AI 或侧栏针对性询问，不凭空补齐。

本版不提供回退方案按钮，也不保证一次修复成功。用户想恢复旧效果时，直接在主对话中提出要求。

**验收**：用户能说清当前问题影响什么，并提出一个符合其目标的下一步要求；侧栏的问题解释不启动未经要求的修复。

# 08 完整使用旅程 · 从零新建

## 21 天思考小游戏

以下为目标体验示例，展示主对话和侧栏如何共同工作，不表示现有插件已实现。

| 时刻 | 主对话 | VibeGuide 侧栏 |
|---|---|---|
| 提出想法 | 用户：“做一个 21 天打卡思考网页，每天回答一个问题。” | 显示当前目标，尚无代码时不生成“已实现”的项目结构 |
| 澄清关键问题 | 主 AI 询问每日问题来源、回答是否公开、是否要换设备继续，并说明主要影响 | 默认关联原题；用户主动求助时补充解释，不重复生成整组选项说明 |
| 确定起步方案 | 用户选择固定问题、仅自己查看、先在当前设备使用；主 AI 给出易懂的计划并开始 | 用计划草图展示问题、回答保存和进度，标为“计划中” |
| 开发与解释 | 主 AI 实现提交和保存，继续其他工作 | 说明现在能保存什么、当前浏览器的限制；用户可追问且主线继续 |
| 讨论取舍 | 用户在侧栏问：“为什么换手机看不到？” | 解释当前保存范围，以及支持换设备会增加的身份识别和共享存储能力 |
| 明确修改 | 用户：“那就改成换手机也能看，仍然只给本人看。”主 AI 接收并调整任务，必要时澄清新的产品选择 | 直接转交原意并显示真实回执，不要求再填任务卡；结构先标“待实现” |
| 检查结果 | 主 AI 检查相关行为并提供结果 | 展示实际验证范围；若没有真实换设备检查，明确显示尚未验证 |

### 用户最终获得什么

用户理解单设备与跨设备方案的影响，知道保存和身份识别之间的关系，能提出“换手机继续但仍然私密”的真实需求。无需了解数据库表结构、浏览器接口语法或文件差异。

期间若仅追问或查看历史解释，开发继续。出现真正需要用户决定的新问题时，主 AI 按正常流程提出，侧栏协助理解。

| 打开项目 | 侧栏根据现有依据说明首页、详情、内容来源与样式各自负责什么；不承诺固定扫描时长 |
| 理解结构 | 用户查看“访客打开首页时发生什么”；不需要逐层阅读文件目录 |
| 提出目标 | 用户明确说“把首页改成带封面的作品卡片，详情内容先不变”，要求直接转给主 AI |
| 开发中追问 | 用户询问手机展示方式；侧栏说明取舍，主 AI 继续当前任务 |
| 看懂变化 | 侧栏解释首页展示变化及实际影响。若发现全站字体也变化，说明依据和可能偏离的要求 |
| 提出纠正 | 用户可在主对话中要求修正；也可在侧栏明确提出具体修改并按 F5 转交，不使用恢复按钮 |
| 验证与继续 | 展示实际桌面和手机检查范围；未验证部分保留标记。项目日志记录最终决定与状态 |

## C 增加登录后，公开页面打不开

| 步骤 | 目标体验 |
|---|---|
| 遇到问题 | 用户说“分享出去别人打不开”；侧栏说明需要区分自己的登录状态与访客实际访问 |
| 查看依据 | 聚合真实的复现现象、相关改动和主 AI 已尝试方法；原因未知时明确保留不确定性 |
| 判断办法 | 解释“保持作品页公开、只限制私人内容”会怎样影响访问权限，避免向用户倾倒认证术语 |
| 明确要求 | 用户说“作品页继续公开，私人记录仍要登录”，直接转交并显示接收状态 |
| 主 AI 修复 | 侧栏解释新的访问行为；用户阅读和追问不影响修复进行 |
| 观察结果 | 分别显示未登录访客、已登录本人访问的检查结果；一次成功不代表所有访问场景都通过 |

三个场景都需要真实端到端演示。仅有静态地图或模拟聊天不能作为该场景已经交付的证据。

# 10 系统设计概要

具体技术接口在固定宿主版本上验证后确定。本章约束数据职责和正确性，不把候选接口写成已完成集成。

| 模块 | 职责 | 必须守住的边界 |
|---|---|---|
| 宿主适配 | 获取事件、展示侧栏、转交消息及读取接收结果 | 绑定项目和会话；不自动代答权限请求 |
| 项目观察 | 读取结构、变化及检查证据 | 区分主 AI、用户和其他来源的改动；无法归因时明确未知 |
| 状态与证据 | 关联目标、事件、文件状态、解释和验证 | 代码变化使相关旧结论失效；不以工具成功冒充业务完成 |
| 解释服务 | 生成影响、取舍、结构关系和问题解释 | 旁路只读；保留未知和推断；与主任务隔离 |
| 意图与转交 | 区分问题、讨论和明确修改；关联回执 | 保留用户原话，不扩张要求；去重和未知结果核对 |
| 项目记录 | 保存决定、当前事实、历史解释和必要偏好 | 项目隔离、用户可纠正；保存成功与执行成功分开 |
| 侧栏界面 | 当前进展、项目结构、了解过的 | 不抢走阅读位置；不以阅读状态控制开发 |

### 数据与更新

处理事件需有顺序、关联标识和重复处理保护。一次有意义的产品变化可能跨多个工具调用；同一文件也可能由多人修改。对无法获得的变化只说明观察范围，不能假装完整覆盖。

### 模型与隐私

仓库保留在本地，但必要的代码片段、问题和上下文可能发送到所配置的模型服务。界面应说明使用的服务和必要的数据范围；过滤凭证及敏感配置内容，不把“本地仓库”描述成所有内容均不离开设备。

增量更新和缓存减少重复解释；并发追问不应使主任务失去响应。模型来源、限流和成本需要实测。文档只承诺有依据的费用说明，不提供无来源的价格或完成时长。

# 11 课程交付范围与开发顺序

### 完整目标范围

先确定课程版本要交付什么，再分阶段实现。A 接手项目、B 从零新建、C 途中卡住均需要演示和验收，不能以只完成一个入口代替最终交付。

| 能力 | 课程目标版本包含 |
|---|---|
| F1 项目结构 | 功能与职责概览、简化数据流、变化关联、依据及状态 |
| F2 技术影响解释 | 当前作用、实际影响、关键取舍、上下文追问 |
| F3 目标关联 | 定位相关职责、解释现状和可能牵连，说明未知 |
| F4 方案理解 | 主对话以易懂选项澄清需求、侧栏按需解释及单一计划 |
| F5 修改转交 | 明确要求直接转交、含糊澄清、真实回执、去重 |
| F6 变化理解 | 当前进展、重要变化与影响、阅读保持、过时提示 |
| F7 检查理解 | 实际结果、检查覆盖范围、用户体验检查、已知风险说明 |
| F8 连续使用 | 项目日志、有效摘要、了解过的、记录纠正与项目隔离 |
| F9 卡住沟通 | 问题影响、已尝试方法、处理选项和明确修复要求转交 |
| 安装与接入 | 单一 VibeGuide 模式、指定版本 Harness 集成、安装说明 |

### 本版本不包含

自动存档与恢复入口、逐步验收后放行、完整风险雷达、独立自动检查平台、复杂计划编辑、计划模板库、第二宿主、整套宿主一键安装、自动汇报系统、多人共享地图、术语熟练度或强制测验。

### 开发顺序

1. **验证接入**：固定宿主版本，跑通事件、侧栏、独立追问和消息回执。
2. **打通变化与沟通**：实现 F2、F5、F6 的最小真实链路及意图边界。
3. **补齐项目理解**：连接 F1、F3、F4、F7、F8，处理过时与跨会话状态。
4. **完成三类场景**：实现 F9，走通三段真实旅程和异常情况，开展用户测试。

阶段完成代表实现进度，不改变上表范围。范围调整需记录影响到的场景、原因和新的验收条件。

# 12 衡量成功与验收方式

核心观察是：用户能否在理解影响的基础上表达真实意图，并识别结果是否符合目标。功能完成率仍需关注，但不能单凭用户点“通过”、术语数量或模型自评证明效果。

| 维度 | 观察方法 |
|---|---|
| 变化理解 | 用户能否说出刚才改变的产品行为，并指出一个重要限制 |
| 方案判断 | 用户能否比较当前相关选项的实际后果，说明自己的选择理由 |
| 沟通准确 | 转交要求是否保留原意；是否存在漏项、扩张或把提问当任务 |
| 结构理解 | 用户能否描述相关部分的职责和联系，不要求复述技术名词 |
| 结果判断 | 用户能否区分已修改、已验证、尚未验证与历史结果 |
| 开发干扰 | 追问是否阻塞主任务、自动更新是否打断阅读、是否重复确认 |
| 连续性 | 换会话后要求是否保持，旧事实是否失效，项目之间是否隔离 |

### 三类场景的完成标准

A：看懂已有项目并提出一次准确修改；B：理解关键选择并跟随从零开发；C：理解一个真实故障的影响并提出有效下一步。每类都要出现一次旁路追问与一次明确修改转交，验证真实回执。

系统验收还需覆盖：普通问题零任务发送、同一要求有效转交一次、关闭侧栏不暂停、过时结果不显示为当前通过、发送失败不冒充完成、无证据不标功能成功。界面测试、真实集成与用户理解证据分别记录。

### 课程用户测试

建议招募 6-8 名非技术用户作为探索性可用性测试，安排难度相近的任务，交替使用普通主对话与 VibeGuide。测试顺序交错，使用独立项目副本和独立会话，避免前一组答案或记忆影响后一组。

评估依据由真实项目行为、检查记录和事先准备的标准共同确定，不只对照 VibeGuide 自己生成的地图。记录误解和失败案例；小样本结果用于改进，不宣称具有普遍统计结论。解释关闭率只作线索，需结合用户是否已经理解来判断。

# 13 风险与异常处理

| 风险或异常 | 用户可能遇到什么 | 产品处理 |
|---|---|---|
| 解释错误 | 依据存在，但总结或取舍讲错 | 区分推断，提供纠错；修正记录并重新核对关联解释 |
| 内容过时 | 主线已修改，侧栏还在讲旧方案 | 标记适用状态与过时原因，重新提问使用最新上下文 |
| 误识别意图 | 一句追问变成修改任务 | 问题和讨论不发送；对含糊或冲突部分先澄清 |
| 转交结果未知 | 网络超时，不知道要求有没有送达 | 显示待核对，查询接收结果后再决定是否重试 |
| 执行与保存不同步 | 任务已执行，回执记录未保存 | 分开说明两种结果，不重新执行已成功的任务 |
| 事件缺失或多人修改 | 无法确认变化由谁产生 | 标注观察范围和未知来源，不归功或归责给主 AI |
| 把检查当保证 | 页面能打开，被理解成所有功能完成 | 展示具体检查对象、版本和覆盖范围 |
| 讲解过多 | 抢阅读位置、堆叠概念、重复通知 | 默认简短，按需深入；固定阅读位置，聚合相关变化 |
| 模型慢或不可用 | 侧栏持续等待或失败 | 给出真实状态并保留内容；主线不因解释失败停止 |
| 宿主不兼容 | 侧栏或转交通道不可用 | 固定兼容版本，显示不可用项，修复接入后重新验证 |
| 隐私与成本 | 用户误以为所有分析均在本地 | 说明模型服务、必要发送范围与可能产生的调用费用 |
| 项目记录混用 | 另一个项目的选择影响当前项目 | 绑定项目和会话、限制检索范围，并覆盖隔离测试 |

### 接入失败不等于用户流程可以造假

当宿主尚不支持某项接入，产品设计目标仍在，交付状态应记为未完成或受限。静态界面、模拟事件和手动复制可以帮助调试，但必须明确标注，不能替代真实发送回执和运行结果。

### 恢复范围

本版不提供恢复功能，风险应对不依赖自动回退。用户希望纠正效果时，通过主对话提出修改要求；侧栏继续负责解释和状态呈现。
