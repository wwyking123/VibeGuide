## 合并后的优先修改项

### R1 · 最高优先级：用户还没回答主 AI 时，可以按需解释选项

**来源：agy 问题 1；主 agent 核对源码确认复用边界。**

产品 F4 明确要求解释主对话正在等待回答的问题。技术第 7/24 章主要描述完成回合材料和变化解释，但拟参考的 dsh-explain `observer.ts` 的自动来源采集入口要求 `turn/end(completed)`，`tool/call` 摘录只保留工具名，不保存问题参数。它不能直接提供当前未决问题的完整上下文。

例如主 AI 正问“只在一台设备使用，还是换手机也能继续”，用户看懂后可直接选择，侧栏不重复生成解释。若用户尚未选择就主动问“换手机使用会多哪些步骤”，侧栏此时应能解释，不能等回合结束再回答。

**最小补充：**

- 明确独立的未决问题上下文：原问题 ID、会话、选项、状态和版本，从宿主当前问题及已落定事件获取。实际字段以锁定宿主接口为准。
- 默认只关联原题和帮助入口，不为选项出现额外调用解释模型；不另调模型判断用户是否看懂。用户主动求助才生成，依据有效时复用同题同问缓存，重复点击不重复发起在途请求。选项失效不自动重新生成。
- 进行中状态和完成回合摘要分开；已发生的动作可以解释，未返回的结果不能提前写成已完成。
- 用户主动追问优先于后台自动总结。可取消或降级后台解释，不取消主 AI；保留主动提问的顺序和回执。
- 问题已被回答、替换或取消时更新状态；若侧栏支持回答，必须关联原题，否则引导回原生问题卡。

**验收：**用户直接作答时额外选项解释调用为零；主动求助时无需等待主 AI 回合结束；有效缓存与重复点击不重复生成；后台自动总结期间仍能提问，解释失败或取消不影响主任务。首字 5 秒是现有待测目标，不能作为未测过的保证。

**复核修正：**dsh-explain 的 `EXPLAIN_SOURCE_BUSY` 取决于该来源是否已有解释任务，不等于“主 AI 只要在工作，侧栏就必然拒绝”。不能照搬其调度器，但也不应夸大这一限制。

### R2 · 高优先级：修改要求从原话到执行，要有连续、准确的状态

**来源：agy 问题 2/3，kiro 问题 3。**

技术第 5/10/11 章已有保留原话、直接转交、待发送记录和 `unknown` 对账规则。这些方向正确，需要补齐具体契约，而非重新设计一套审批流程。

需要解决三个断点：

1. **澄清不能吞掉限制。** 原型 `submitSide()` 与澄清按钮使用场景预设短语，没有完整保存并拼接含糊输入。真实实现若沿用，可能把“支持换设备，但不要手机号登录”缩成“支持换设备”。
2. **排队不等于主 AI 已改变计划。** `followup` 的接收回执可能先于原生用户事件出现。不能等待原生 `seq` 才显示用户新要求，也不能把排队中的要求显示为已经实现。
3. **请求去重仍需明确发送边界。** 所读 Harness rc.2/rc.3 消息实现先查 `requestId`，随后还会异步处理内容再入队；仅凭这段检查不能证明并发原子去重。响应为 `{ accepted: true }`，不直接包含原生消息 ID。

**最小补充：**

- 持久保留首次原话、澄清补充和必要上下文；模型摘要独立标识，不能覆盖用户原文。
- 每条要求有独立记录；显示“已排队，当前任务仍在继续”“正在处理”“已有改动”“尚未验证”等有依据的状态。不能未经宿主验证承诺“下一步立即执行”。
- 侧栏将新要求显示为“已提出、等待处理”，与已观察的实现状态分开。收到原生事件后再关联来源，不伪造 `seq`。
- 固定 `sessionId + requestId + contentDigest`；经过发送边界后结果不明，保持对账状态，不因工作租约过期就自动重发。发现多个匹配事件必须暴露异常。
- 覆盖假设性问题、礼貌请求、混合提问与要求、否定和条件。不采用“有问号就是提问”或“有如果就绝不执行”的关键词规则。

**验收：**连续提出两条要求仍能分别追踪；澄清后原文限制完整保留；普通追问不产生任务；双击、双进程、超时和重启不会被界面虚报为成功或偷偷重复发送。

**证据入口：**技术第 11 章；`prototype/v2.1/index.html` 的 `submitSide()`、`deliver()` 和 `explicit` 点击分支；Harness `packages/api/session-controller/src/commands.ts` 的 `prompt()`。

### R3 · 高优先级：解释的“当前有效”需要更精确的依据模型

**来源：agy 问题 4，kiro 问题 5。**

技术第 9/14 章已明确重新核对依据、失效传播和统一 ContextResolver。缺口在于第 5 章示例 `Basis` 只列全局 revision、文件哈希和来源，没有充分表达这些承诺所需的依赖。

例如旧解释说“目前仅本地保存”，后来增加新的同步模块，旧文件本身可能没有变化。只校验旧文件列表会漏掉变化；每次任意文件变化都让全部解释失效，又会制造噪声。

**最小补充：**

- 具体要求、事实、检查和证据的 ID、版本或内容摘要。
- 解释包含“只有这些模块”“尚无某能力”等结论时，记录其依赖的文件集合、职责节点集合、任务要求集合及覆盖范围。
- 多份存储的版本向量或等效一致性策略，避免一次查询拼接不同时点的要求和事实。
- 每条关键结论标明属于用户要求、观察、计划、推断或验证结果；“已完成／已验证”的状态不能仅来自模型措辞。
- 查询时核对适用性；后台失效传播用于加速，不能成为避免旧结论泄漏的唯一机制。

**验收：**相关要求或文件集合变化能使旧解释失效，无关变化不使全页变灰；生成期间依据改变，不发布成当前结论；没有当前检查依据，不能显示已验证。

**范围说明：**`currentFacts()` 未过滤过时证据是文档已列出的待修缺口，不能重复包装为本次新发现。来源真实也不能证明语义正确。

### R4 · 高优先级：本地记录要能从异常退出恢复，并为用户要求留出容量

**来源：kiro 问题 4，agy 问题 6。**

现有 `Ledger.update()` 与 `ProjectStore.write()` 使用独占锁文件，锁存在即返回 `busy`，正常退出才删除锁。未见死亡持有者识别与遗留锁恢复逻辑。进程在持锁期间异常结束后，后续写入可能一直被阻挡。工作队列的领取租约不能自动解决文件锁问题。

技术第 6 章已承认跨文件无事务、操作缓存很短以及容量上限；还需给出可实现的恢复与容量策略。

**最小补充：**

- 区分文件锁、工作领取租约、发送状态；遗留锁接管要能识别旧持有者，防止旧工作者恢复后覆盖新结果，不能仅按文件年龄删除。
- 事件、用户输入和发送记录使用持久业务 ID 去重。现有 128/64 条 operation 缓存仅作短期写入重放辅助。
- 为用户输入和未完成发送保留硬容量；解释历史等可重建数据不能占满它。可选拆分核心记录与派生投影，但“保存输入 + 创建发送记录”仍须原子完成。
- 原有工具和后台工作者共用串行提交入口，明确谁负责抽取、谁负责提交。减少主 AI 重复记账；证据观察是否能完全替代现有工具，应逐项验证后迁移。

**验收：**在创建锁、写临时文件、替换文件、宿主接收等位置终止并重启；能恢复或明确报告状态；历史超过短缓存后不会重复处理；派生历史接近上限时仍能保存必要请求。

**证据入口：**`src/workbench/ledger.ts:44`，`src/continuity/store.ts:209`；技术第 6/7/15 章。

### R5 · 高优先级：明确安装组成，以及解释模型如何选择和降级

**来源：kiro 问题 1/2。**

现有安装器主要安装 agent preset 中的服务端沟通与连续性插件，生成的包没有侧栏客户端装载元数据，当前 TypeScript 配置也未覆盖 TSX。技术第 4 章已有逻辑模块和生命周期，但正式打包需要进一步落实到物理入口。

**最小补充：**

- 明确全局 Host 服务、Web Client bundle、会话 preset 的装载位置、注册与释放责任。一个用户模式可以包含多个技术模块。
- 列出客户端入口、宿主服务注入、共享 React/Cordis、安装升级与卸载处理；双会话不应重复启动全局发送者。
- 版本表区分本机 rc.2、官方发布提交与调研快照。`22ddee…` 是所读上游快照；其包版本号为 rc.3，不应据此等同于发布标签的精确代码。
- 定义解释模型选择策略、配置来源和运行时 route，以及未配置、不可用、可用三种状态。可明确采用宿主已选模型，但不能假定所有调用自动继承它，也不必把 provider 术语和复杂配置强加给非技术用户。
- 无可用模型时展示已知状态和明确提示；独立取消与预算管理。共享服务额度时，“独立调用”不等于完全没有延迟影响。

**验收：**锁定本机版本，安装后出现唯一侧栏；切换、重启、禁用和卸载正常；能核对实际模型来源；未配置不乱发请求，侧栏取消不取消主线。性能影响需真实并发测量。

**证据入口：**`scripts/desktop.mjs:38`、`tsconfig.json:14`；dsh-explain `package.json` 的 `dsh.client` 与独立客户端构建；技术第 3/4/17/19/24 章。

### R6 · 中优先级：历史阅读和小型结构图需要验证，不宜先定重组件

**来源：agy 问题 4/5，kiro 问题 6。**

原型将历史阅读与部分当前视图共用 `state.read`，看历史后可能继续停在旧版本；它已经显示“之前的说明／项目有新变化”，所以不能说完全没有过时提示。应验证用户是否仍把“当前进展”中的旧正文理解为现在的状态。

结构图应继续以产品职责和行为命名，同时呈现有依据的计划与未验证环节。已有文档已要求这一点，不能把静态 import 图等同于既定产品方案。

**建议：**

- 历史详情与当前状态使用独立选择状态，或显著标明历史模式；切回当前与保留阅读位置的规则要一致，避免无条件清除所有阅读锚点。
- 以少量业务职责节点开始，按需展开；不强制任何项目都必须恰好 3–6 个节点。
- 保留与渲染器无关的结构模型，用相同数据比较受控 SVG 与 React Flow。滚动、键盘、节点位置稳定、维护和打包成本通过后再选；React Flow 继续放在 P3。
- dsh-explain 优先参考来源读取、独立模型调用、取消和预算方式；其 scheduler 与全局学习运行时耦合较深，不整套搬入。

**验收：**窄栏内能理解职责与尚未验证的环节，滚动不被意外截获；从历史返回后能明确判断正在看哪一个版本。组件选择不阻断 P0–P2。

## 对原始评审意见的取舍

| 原始意见 | 复核后的处理 |
|---|---|
| agy：含“如果／要是”等词一律归为提问 | 不采纳硬规则。“如果已经做好就部署”也可能是明确条件指令；结合完整语境，含糊时才澄清 |
| agy：所有带动作倾向的回答都加原话转交按钮 | 可测试为误分类补救，不替代明确修改直接转交，不变成每次都要点确认 |
| agy：排队后承诺当前步骤结束立即处理 | 改为有宿主依据的排队说明，未经验证不承诺处理时点 |
| agy：固定 3–6 个节点，SVG 开发前定为唯一默认 | 保留少量职责节点方向；固定数量与渲染库选择留给实例验证 |
| agy：现有隐私、来源和证据链已全面闭环 | 不采用此完成性判断。本轮未验证全面敏感内容过滤，来源真实也不保证语义忠实 |
| agy：主 AI 忙碌必然触发解释 BUSY | 修正为解释任务本身的互斥限制，见 R1 |
| kiro：需要防止把 requestId 当成严格恰好一次保证 | 接受具体并发证据和契约补充；原文已不承诺任意故障下严格恰好一次，不把这一原则算新发现 |
| kiro：短操作缓存不能替代持久业务去重 | 原文已有此约束；新增重点是遗留文件锁、核心记录容量与具体恢复验收 |
| 两者：复用不应带入第二套学习状态或复杂图工具 | 保留，落实到文件级取用边界；现有方案已排除的功能不重新立项 |

## 下一步顺序

1. 补 R1 的未决问题通道、R2 的原话与投递契约、R3 的依据 schema；同步落实 R4/R5 的运行时边界。
2. 在固定 Harness 版本做最小真实链路：主 AI 提问 → 侧栏解释 → 主线继续开发 → 侧栏提出修改 → 正确会话接收 → 有依据的状态更新。
3. 验证并发、异常退出、过时结果和项目隔离，再扩展三个场景的完整体验。
4. 结构图组件和历史阅读做对照验证，最后以实际非技术用户试用判断是否减少误选、反复追问和失控感。

不新增模式、审批流程、恢复入口或知识测验；继续保持“主 AI 本身说人话、侧栏解释影响、明确要求直接转交”的方向。
