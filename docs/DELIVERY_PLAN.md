## 1. 起点与唯一 P0 成果

开发起点 `0.1.0-alpha.2` 已有规则注入、独立会话预设、兼容版本安装与接入检查，以及对照评测准备工具。`src/index.ts` 继续只注册静态沟通规则；`0.1.0-alpha.3` 在独立 P0 模式下通过 `src/continuity/` 加入本地项目记录与动态上下文。具体实现和边界见 [P0 说明](CONTINUITY.md)，不能据此声称真实模型或用户效果通过。

**P0 成果：用户说出要求，连续修改两次，换会话继续，AI 仍保留有效要求；用户纠正后能更新理解。用户能说清关键选项各自的后果及选择理由。**

首个小范围试用优先使用已有、可运行的独立报名应用样例，避免先建设完整新应用才验证续接。新建与已有项目仍共用同一套行为，随后覆盖新建入口；不把它们拆成两个产品。

新机制限于当前要求、来源、纠正、任务进度及可靠保存/读取。维持必要业务检查与准确完成说明，直接引用现有工具结果。完整证据库、自动失效引擎、架构分析、专用 API 引导、跨会话个人偏好整合均后置。

## 3. 首个可单独试用的主路径

在执行前冻结初始项目、用户输入和必要结果。试用脚本可明确要求“名单只有组织者可见”，并使用同一份独立初始样例。

1. 用户表达要求。AI 用实际后果说明理解，保存要求及来源，告知是否保存成功。已有规则不重复询问。
2. 第一次修改：增加 20 人上限，就满员后拒绝或候补的业务后果作必要说明。在这一关键选择抽样观察用户理解，再执行与检查。
3. 第二次修改：调整页面样式，确认名单可见范围和已选满员处理仍保留，不重新启动冗长访谈。
4. 换会话回到同一项目继续。AI 从已保存要求和当前实际状态接上，不要求重述已知背景，不把旧检查当作当前可用证明。
5. 用户纠正此前记录中的理解。AI 判断是理解纠正还是新功能要求，更新对应来源和替代关系；只更新记录时不宣称代码已经改变。

首轮可使用本地可验证样例；若用户实际要求多人共享，必须标明样例验证范围，不能据此宣称已经满足真实多人使用。

## 4. 必须覆盖的边界案例

以下是围绕同一小记录机制的验证分支，不要求每位用户在一条试用中经历全部异常。具体状态行为以[产品设计](PRODUCT_DESIGN.md)第 4.5 节为准。

| 案例 | 预期行为与检查点 |
| --- | --- |
| 外部 Agent 将组织者专属名单改成公开 | 并列记录原要求与当前观察、说明影响；不把公开写成新共识；不直接覆盖外部改动。已有授权范围内无冲突的修复可继续 |
| 用户只清除审核规则的记忆 | 清除记录不触发代码或独立规格修改；报告实际删除范围，无其他依据时将业务理解标为未确定 |
| 用户明确取消审核 / “忘掉审核”语义不明 | 前者进入功能任务；后者结合上下文，仅在仍有歧义时澄清；不得将记录更新当成实现完成 |
| 关闭窗口、工具结果未返回 | 从最近成功保存点续接；核对文件和可用历史/工具状态，结果缺失时保留未知；不盲目重做可能已经执行的操作 |
| 先不做 / 明确取消 / 两个任务切换 | 暂停和取消分别记录；已产生改动保留；任务分别保存，只推进明确选择的一项；“继续”有歧义才询问 |
| 代码已改，保存失败或结果未知 | 当场说明代码与记录各自状态，提供未保存摘要；重开不得承诺取得缺失记录；恢复后先核对再补录，不重复改代码 |
| 另一个写入者已更新记录 | 先核对版本和差异，不静默覆盖；同一要求冲突按用户决定和证据处理 |
| 代码未变，但预览退出或服务权限撤销 | 保留历史成功结果；用户问现在可用时做相关必要检查，没有当前依据则明确未知 |
| 解释过长导致随便选 / 安心但误解后果 | 该次理解不通过；不能用低追问次数、高信心或记忆完整抵消 |

异常测试用隔离样例和受控失败。真实服务条件未具备时记录未验证；模拟可验证失败处理行为，不能冒充真实业务接通。

## 5. P0 记录的最小契约

| 对象 | 最小信息 | 关键约束 |
| --- | --- | --- |
| 当前要求 | 内容、项目/任务范围、用户来源、有效/被替代/已删除状态 | 用户决定、AI 假设和代码观察分开；有效用户决定定义预期 |
| 差异与纠正 | 原要求、当前观察及依据、影响、新决定或待处理事项 | 修正理解与修改功能分开；不能静默用实现覆盖预期 |
| 任务续接 | 任务标识、执行状态、已做/未做、下一步、相关文件或结果入口 | 同项目任务分别保存；暂停/取消不代表回滚；结果未知不猜测 |
| 保存状态 | 最近成功版本、待保存内容、写入结果及必要错误信息 | 仅在已确认持久写入后报告已记住；失败提示留在当前对话也不能冒充已持久记录 |
| 最小结果引用 | 已有检查入口、时间、范围、相关版本、未检查事项 | 历史记录和当前可用判断分开；无需 P0 就建完整证据管理 |

先用可审阅的本地记录；路径、写入接口和并发处理在 VG-N02 验证。结构校验通过不代表记录准确。跨会话个人偏好管理不在本次新增契约内，当前明确沟通要求继续由原生对话遵循。

## 6. 试用通过与继续开发的判断

**先验证用户看懂。** 事先写清关键选项的必要后果，观察用户能否用自己的话说明两个选项、选择理由和对自己项目的影响。允许选择任何符合其目标的方案，不以服从 AI 推荐为正确答案。

分别记录首次理解、补充解释后的理解、实际操作与主观信心。解释过长导致随便选、或信心很高但后果理解错误，都不能通过；缺少真实用户观察记为未测。该方法只在试用中抽样使用，不要求日常每步复述。

理解与事实正确性都必须通过。严重失败包括：将代码现状或推测当作新决定、未经协调覆盖他人改动、误接任务、虚报保存或完成、把忘记要求当作功能已变、把历史成功说成当前可用。固定案例无严重失败仍不代表生产环境零风险。

成本、回答长度、重复解释和追问次数只作辅助指标。理解失败就先修解释和选择设计；续接失败先修记录；不以增加功能代替修复。小样本只决定下一轮迭代，不宣称总体提升比例。
