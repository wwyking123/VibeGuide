# VibeGuide：让原生 AI 回答直接可理解

日期：2026-10-14。本文记录用户确认的交互方向：“AI 的回答本身就是非技术的人就能看懂的”。2026-10-18 已开始实现原生插件并完成接入验证，实际沟通效果仍待模型与用户评测；当前进度见[开发说明](DEVELOPMENT.md)。

2026-10-21 修订后的功能范围与优先级见[产品设计](PRODUCT_DESIGN.md)和[实施计划](DELIVERY_PLAN.md)：P0 聚焦两次修改后的要求续接与纠正，理解验收优先。本文继续作为原生对话交互原则，不代表新增记忆、验收或恢复能力已经实现。

本文取代旧方案中“技术原文为主、旁边白话解释、两边改选”的主交互。`prototype/index.html` 保留为被否定方向的比较材料，暂未按本方向重做。

## 1. 产品定义与边界

VibeGuide 是 DeepSeek Harness 内面向非技术创作者的开发协作模式。它在 AI 生成回答、方案和问题之前提供持续的沟通要求，让同一个开发 Agent 直接用用户能判断的结果、行为和影响表达；让用户的目标持续参与后续实现与验收。

用户只有一个对话对象、一个输入框、一段连续的开发过程。VibeGuide 的存在可以很轻：创建会话时选择相应模式；日常继续使用 Harness 原会话。技术证据保留在宿主记录中，用户需要时可以展开。默认没有第二个解释助手、翻译按钮或独立工作步骤。

“容易理解”同时要求：语言能懂、决定与用户目标有关、结果可以亲自核对。把框架名称换成生活比喻，仍然让用户选择实现方案，并不能达到目标。

## 2. AI 应改变的五种行为

| 时刻 | 原生回答应该怎样表达 | 判断依据 |
| --- | --- | --- |
| 提出想法 | 只有方向、核心流程或规则未确定时，先问 2–3 个关键问题并等待回答；要求已足够明确时继续制作 | 不替用户决定玩法；不把常规技术选择转嫁给用户 |
| 给出方案 | 用实际使用过程和本次范围组织；已知要求不重复问；无须每次请用户批准计划 | 覆盖目标、遗漏与假设可纠正；技术实现由 Agent 结合项目处理 |
| 需要选择 | 询问用户熟悉的业务情境，说明各选择的后果；提供推荐依据和自由表达入口 | 缺少的回答是否改变行为、费用、维护责任或既有约束 |
| 正在开发 | 在有意义的阶段用结果表达当前动作；给出可体验成果 | 不把工具数量或文件数当成果，不编造进度百分比 |
| 完成或失败 | 先讲实际发生的变化、已查证及未查证的部分，再给具体下一步 | 工具成功、自动检查、用户体验与上线分别记录 |

不使用僵硬的五段模板回答每一句话。简单修改可以只有一句变化说明和一个预览；复杂取舍才需要展开。用户要求技术细节时正常提供，保持事实准确，不居高临下。

## 3. 什么问题交给用户

先使用已有会话和项目事实。只追问尚未明确、且会改变使用结果的事项；一次集中问当前阻塞的关键问题。**想法阶段与执行阶段分开：核心玩法、使用流程或范围尚有关键分叉时，问完要等待回答，不在后台先写代码、初始化项目或安装依赖。** 用户回答足够后简短串起第一版流程，继续开发，不再加一轮机械开工审批。明确委托“你来定，先做个原型”时可标明假设后推进。可逆、低影响的实现细节由 Agent 自行选择，不转嫁给用户。

- 不让普通网站用户比较 React/Vue；直接依据项目选择实现。
- 用户已说“市场同事每周独立更新案例”，就据此设计编辑流程，不再问一次“要不要 CMS”。账号、发布权限或新增费用未明确时，只补相关缺项。
- 用户只说“要公司官网”，先问清主要访客和希望他们完成的动作；已经明确只展示业务、案例、联系方式时，可用占位素材推进草稿。不要提前用长问卷逼用户完成全套产品规划。
- 用户新增“客户留下需求”，要明确这些信息由谁查看和处理。展示一个表单并不能证明有实际收件或提醒能力。
- 重要假设用一句可纠正的话表明。已授权范围内的常规工作继续推进；不能把“看懂了”当成所有未来操作的授权。
- 只有业务含义确实依赖某技术限制时才解释术语，例如某个外部服务暂不支持所需功能。解释落到当前影响，保留未知项。

## 4. 公司介绍网页：一段连贯的示范对话

以下为设计示例，不是实际运行记录。示例中的完成声明仅能在取得相应证据后使用。

**用户：** 帮我做一个公司介绍网站，主要展示业务和案例，放电话和邮箱让客户联系我们。先做一个草稿。

**AI：** 可以。我先做一版让客户“了解公司 → 看业务和案例 → 找到联系方式”的网页，手机也能浏览。暂时按电话和邮箱联系来做；缺少的公司资料会标为待补充。先给你一个可打开的草稿，看到页面后我们再调整内容重点。

没有影响当前草稿的关键缺项时继续制作，不要求用户批准技术栈。若当前环境不能运行，先说明并处理实际阻碍，不承诺已有预览。

**用户：** 案例需要市场同事每周更新，她不会写代码，也不用 AI 工具。

**AI：** 那她需要一个能登录、上传图片和修改文字的页面。这会增加编辑和发布功能。我会先把这段使用过程补进方案。还需要确定：她编辑后直接展示给客户，还是先由你看过再发布？

原生提问用相同语言显示选项：“她可以直接发布 / 我看过后再发布 / 我希望另一种流程”。这是用户掌握的职责决定。是否采用 CMS、何种框架由 Agent 结合实际条件决定。若涉及外部服务或持续费用，另行说明具体依赖与可替代路径，不凭空报价。

**用户：** 我看过后再发布。

**AI：** 好，流程是“同事编辑并提交 → 你查看 → 通过后客户才看得到”。审核前，公开网站保持原来的内容。我先做出这段流程的可操作草稿。

后续实现应保留这条要求；只有界面示意时必须注明保存、账号或发布尚未接通。

**AI 在取得相应证据后：** 展示页已经可以预览。编辑和审核目前只有页面示意，暂时不会把修改发布到公开网站。你可以先看案例布局是否合适；审核功能接通后，再一起检查“提交后客户看不到、审核后才看得到”。

**用户：** 手机上案例图片太小。

**AI：** 我会把手机上的案例改为一行一张，让图片更容易看清；电脑上的排列保持当前样式。

常规可逆调整直接推进，不再发一次方案确认。修改后的回复简短说明实际变化，并提供可检查的结果。

## 5. 页面应有多轻

产品主体仍然是 Harness 原会话。只需要两个主要交互区域：对话与实际成果预览。是否使用宿主已有预览能力，需要在真实环境核实。

- 入口：会话使用 VibeGuide 的沟通规则；具体安装与启用形式由技术验证决定，不能现在承诺旧会话热切换。
- 主对话：用户直接读到可理解的回答。结构化问题本身也使用日常语言，只有一个回答动作。
- 预览：有页面、流程或实际结果时展示；没有结果时不为了“可视化”制造假完成。
- 可选详情：技术选择依据、原始日志、目标与历史决定按需查看，不作为每日必经页面。
- 用户反馈：直接在同一输入框说“这不是我要的”“手机上看不清”“这是什么意思”；AI 沿用上下文调整表达或任务。

下一版 HTML 应以一段连续会话展示这些行为，而非把五个阶段变成产品导航。原型演示控制仍可存在于产品之外，但不能成为用户完成开发的步骤要求。

## 6. 最小落地路线与证据

优先验证同一模型加入沟通规则之后，原生回答是否改善，再决定要不要增加 UI。

1. **内容实验**：编写一个显式调用的 VibeGuide skill，用现有会话比较普通原生回答与加入规则后的回答。官方机制支持用户 `/name` 将完整指令注入当前步骤；持续遵循与压缩后的稳定性仍需测试。[官方 skill 调用机制](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/skill/tool-skill/README.md)
2. **持续规则**：小型插件通过 Agent 作用域的 `systemPrompt.section` 加入沟通规范。该接口支持按步骤组装提示，作用域贡献不影响其他 Agent；保留原宿主指令与工具上下文，不替换整个系统提示。[官方提示机制](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/system-prompt/README.md)
3. **会话配置**：用自定义 Agent preset 装配插件。官方说明 preset 修改影响后续创建的 Agent，不能据此承诺既有会话可即时切换。[官方 preset 生命周期](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/preset/agent-preset/README.md)

这些来源核实了生成前指导的扩展路线，不证明 VibeGuide 已安装、有效或保证每次遵循。先测试同一个 Agent 的直接输出，不默认增加第二个模型逐句重写回答。成本、延迟、长会话和子代理结果汇总仍要实测；提示规范不能代替业务正确性和运行验证。

## 7. 第一轮验收

用原有用户研究中的真实困难来测试，不以“文案更亲切”判定成功：

- 最高优先级：在试用中抽样一个关键选择，用户能用自己的话说出两个选项的实际后果、自己选择的理由，以及对项目的影响；不要求选择 AI 推荐项。
- 用户因解释太长而随便选，或感到安心却理解错后果，该次理解均不通过。分别记录首次和补充解释后的结果；没有真实观察记为未测。
- 用户能从 AI 第一份回答说明预期结果，不必另问一次“这个技术是什么意思”。
- 技术选型问题减少；用户仍能发现会改变自己业务的关键取舍。
- 方案遗漏、失败和未知条件没有被流畅语言掩盖。
- 用户说出的要求在后续方案和成果中仍被保留，例如“我批准以后客户才看得到”。
- 用户能用实际操作核对成果，知道界面示意与真实功能的差别。
- 相同任务下，新增确认次数和读文负担没有上升。

理解观察只用于抽样试用，不要求用户日常每次选择都复述。文字评分、记录完整或少追问不能替代理解证据；具体方法见[评审细则](../evals/RUBRIC.md)。

先观察用户阅读“公司网站 + 同事编辑 + 审核发布”这段对话，记录他认为会发生什么、还缺什么以及怎样检查。对照组允许正常追问和白话提示；若一个简短提示就能达到同样效果，首版保持轻量 skill，持续插件的价值需要后续证据。
