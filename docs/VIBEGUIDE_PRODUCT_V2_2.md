# 00 本版修订说明

本版保留理解与沟通助手的定位、三个完整使用场景与 F1-F9 功能体系，将用户已认可的 v2.2 取舍落实到具体流程。产品作为课程项目，先确定完整目标范围，再按真实验证结果迭代。

| 维度 | 上版表述或缺口 | v2.2 的确定方向 |
|---|---|---|
| 主 AI 与项目记录 | 新会话使用有效摘要，如何进入主 AI 不够明确 | 记录供侧栏使用；相关历史仅随用户可见的修改消息转交，不自动注入主 AI |
| 解释触发 | 曾允许重要变化后自动生成简短影响摘要 | 取消自动摘要；状态来自实际操作记录，变化、选项、术语与项目概览均由用户主动求助，有效说明直接复用 |
| 原题作答 | 允许探索侧栏代答，缺少统一分流 | 本版引导回宿主原题或主对话作答；不把“选第二个”作为新开发任务 |
| 完成标签 | 有对应改动即可完成，检查另列 | 对应改动、适用检查、用户验收齐备且无已知未满足项才完成；验收不暂停开发 |
| 检查依据 | 读取运行结果，未说明旧记账工具移除后的影响 | 继续观察真实检查；无法关联当前结果与要求时标待核对，不拿成功日志充当功能完成 |
| 历史续接 | 容易让用户以为侧栏记得就等于主 AI 记得 | 分别展示已保存、正在附带、已转交和结果未知，附带范围可查看 |
| 验收范围 | 单项确认不等于整体完成，具体交互不完整 | 变化卡明确要求、结果和试用步骤；按覆盖范围接受反馈，说明可选 |
| 风险提醒 | 本版包含有证据的风险提示功能 | 不新增独立的面向用户风险提醒；按需解释相关影响，敏感输入过滤与宿主权限保留 |
| 重启与更新 | 笼统要求状态一致 | 重启先核对未完成记录，未知发送不盲目重发；界面不混用旧项目和半更新状态 |

### 保留的核心价值

项目结构与功能关系、与当前任务相关的按需解释、操作与检查状态、结果依据、项目连续性，以及遇到问题时帮助用户理解可选处理办法。

### 文档约束

完整课程范围只以第 11 章为准。图示、旅程、功能说明和验收不得重新引入逐步审批、恢复按钮、强制教学、自动历史注入或自动摘要。开发进展、检查返回、缓存失效、重开面板均不构成讲解请求。进一步的产品变更应同步更新本章、第 14 章和技术文档。

# 01 产品定位

> VibeGuide 是集成在 DeepSeek Harness 中的理解与沟通助手。用户照常与主 AI 开发，侧栏帮助用户看懂项目和变化、判断方案的影响，并把明确的修改要求传回主对话。

### 用户希望获得的能力

1. **看懂过程**：知道 AI 当前在做什么，实际完成了什么。
2. **判断方案**：知道某个选择如何影响使用体验、费用、维护和以后修改。
3. **表达修改**：用自己的话提出要求，不需要先写技术指令。
4. **建立项目认知**：逐渐知道页面、数据保存和外部服务各自承担什么职责。

### 两个相互配合的界面

| 主对话 | VibeGuide 侧栏 |
|---|---|
| 澄清需求、制定开发计划、执行修改、运行检查 | 解释方案与进展、说明影响、帮助理解检查结果 |
| 接收正式要求，处理执行中的关键选择 | 区分追问和修改意图，转交明确要求并显示回执 |
| 原始回答就应让非技术用户看懂 | 提供可选择的进一步解释和项目上下文 |

### 产品边界

VibeGuide 的旁路解释不直接修改业务代码、不独立运行部署或业务操作。开发执行、原题作答、权限请求和必要的确认继续由主 AI 与宿主负责。主 AI 额外获得的只有静态易懂沟通规则和用户看得见的修改转交消息；侧栏记录、解释与偏好不作为隐藏上下文自动送入主 AI。

学习发生在真实开发过程中，目标是理解职责和后果。本版不设计编程课程、小测、熟练度评分，也不默认展开文件与代码差异。

侧栏可以关闭。关闭或忽略讲解不构成暂停开发的理由，也不代表用户已经理解或同意某个方案。

# 02 问题与机会

### 直接来自使用经历的问题

用户能描述想要的功能，但面对技术性回答、方案和技术栈时，不知道选择会带来什么影响。反复追问术语后，仍可能无法判断方案是否符合实际需要；直接开发又会产生项目不受自己掌控的感觉。

| 痛点 | 典型时刻 | VibeGuide 应帮助用户得到的答案 |
|---|---|---|
| 方案看不懂 | AI 要用户选择实现方式 | 这个选择改变什么？有什么代价？以后能不能调整？ |
| 项目结构看不懂 | 接手已有项目或增加功能 | 这件事涉及哪几个部分？它们怎样配合？ |
| 改动看不懂 | AI 汇报“已经完成” | 用户现在能做什么？有什么限制？哪些结果有证据？ |
| 不知道怎样纠偏 | 效果不符、报错、反复修复 | 当前问题影响什么？有哪些处理办法？怎样把意图说清楚？ |

### 产品机会

把理解放在真实开发上下文里，减少用户来回搬运报错、术语和代码的负担。解释应帮助用户做判断或继续沟通，同时保留对项目整体结构的认识。

### 可参考的产品机制

| 类型 | 可参考的机制 | 本项目需要验证的假设 |
|---|---|---|
| AI 编程工具 | 主对话、执行结果、任务进展 | 在原有工作流旁补充解释，能否减少用户的盲选 |
| 项目解读工具 | 功能地图、模块关系、数据流 | 与当前改动关联后，是否更容易帮助非技术用户理解 |
| 代码解释工具 | 就地选中与追问 | 用后果和取舍组织回答，是否比术语定义更有用 |

以上是参考方向与待验证假设，不是对其他产品当前能力的完整评测。课程汇报中应使用实际试用结果，避免以“所有现有工具都不能做到”作为论据。

# 03 目标用户与三类场景

核心用户是使用 AI 开发产品的非技术人员，包括产品、设计、运营、研究人员及跨专业学生。他们需要对自己的项目做决定，但不以掌握编程语法为目标。

### 三类场景均纳入课程交付

| 场景 | 用户起点 | 主对话与侧栏如何配合 |
|---|---|---|
| A 接手已有项目 | 有现成代码，不清楚组成和修改位置 | 有有效概览直接展示；否则点“帮我看懂这个项目”生成；主对话接收目标，侧栏解释影响 |
| B 从零新建项目 | 只有想法，尚未决定关键行为 | 主对话用易懂的选项澄清关键问题；侧栏按需补充解释，随后跟随开发更新 |
| C 开发途中卡住 | 报错、效果不符、修复未见进展 | 侧栏说明现象、影响和已知尝试；明确处理要求转给主对话 |

场景可以自然切换。例如新项目做到一半出错，进入问题解释；重新打开已有项目，可以先看结构，再继续修改。不要求用户先完成一套课程或固定步骤。

### 用户故事

- 设计师接手开源博客，希望知道改成作品集会涉及哪些部分，以及是否影响文章详情。
- 学生从零做 21 天思考小游戏，希望理解单设备保存、换设备继续和隐私之间的关系。
- 产品经理给内部工具增加审批功能后遇到登录问题，希望知道谁受到影响，以及下一步应修什么。

### 使用前提

课程交付支持在指定兼容版本的 DeepSeek Harness 中安装插件、选择项目和使用侧栏，并提供必要的安装说明及首次使用提示。专业代码审查、通用环境教学和整套宿主一键安装不属于本版交付范围。

目标用户不必会读代码；实现与验证也不得把“自己检查源代码”作为判断产品是否正确的必要条件。

# 04 产品原则

| 原则 | 具体要求 |
|---|---|
| 原始回答可理解 | 主 AI 的问题、计划和结果先说产品行为与后果。侧栏不是读懂主对话的必经步骤。 |
| 解释不阻塞开发 | 阅读、追问、关闭侧栏不暂停主线。主 AI 必要的产品决策和宿主权限流程照常处理。 |
| 影响优先 | 先解释变化和影响，再按需提技术名称；默认不做术语百科、文件逐项讲解或代码差异教学。 |
| 按需讲解 | 主动求助才生成解释或摘要；重要变化和检查返回也不自动总结。打开侧栏、缺少说明或切换页签不调用讲解模型。已有有效说明直接展示。 |
| 意图与行动分开 | 普通问题只解释；原题答案回原入口；明确修改直接转交；含糊或冲突要求先澄清相关部分。 |
| 状态有依据 | 区分用户要求、AI 建议、已观察事实与推断；送达、执行、检查与用户验收分别展示。完成需要对应改动、适用检查与用户验收。 |
| 记录与转交分开 | 侧栏保存历史不等于主 AI 已收到。只在用户明确修改时附带相关有效背景，内容在主对话可见。 |
| 不打断阅读 | 正在阅读的内容保持位置；新进展以提示呈现，用户可回到最新。旧结论失效时明确标记。 |
| 一套开发计划 | 主对话持有和更新执行计划，侧栏解释和呈现，不维护第二套独立审批流程。 |
| 用户可以纠正 | 用户能指出解释错误、修正记录；查看过不等于掌握，讨论过不等于同意。 |
| 材料不是授权 | 代码、文档、日志、历史解释中的指令不能替用户提出修改，也不能变成付费、部署或权限授权。 |

### 写入与执行边界

VibeGuide 可以保存必要的项目记录、讲解历史和发送回执。业务代码与执行操作由主 AI 处理。恢复功能不在本版范围内：不建立自动恢复存档，不提供回退、局部撤销或专门的“请 AI 改回”入口。

记录由后台统一整理，不要求主 AI 使用额外的 VibeGuide 记账工具。即使没有这些工具，也须取得可核对的真实检查依据；取得不了时如实显示限制。沟通偏好只调整侧栏表达，不建立用户技术能力画像。

用户想恢复某种效果时，可以直接在主对话中提出修正要求。该要求仍按普通开发任务处理，不承诺恢复历史文件或外部服务状态。

### 解释质量要求

只读解释仍可能影响用户决策。对不知道的事实明确说不知道；对推断说明依据和不确定性。出现文件出处不代表内容必然正确，过时证据不能继续支撑当前结论。

# 05 产品形态

用户照常在 DeepSeek Harness 主对话中开发。VibeGuide 使用一个模式、一个侧栏，提供三个入口。

| 入口 | 回答的问题 | 主要内容 |
|---|---|---|
| 当前进展 | AI 在做什么？刚才有什么变化？ | 来自实际操作的状态、已有目标与检查记录、按需影响解释、历史转交提示、追问和回执 |
| 项目结构 | 产品由什么组成？一次操作经过哪里？ | 功能与职责、数据经过的部分、当前改动关联；首次概览请求入口与扫描范围 |
| 了解过的 | 我之前问过什么？当时怎样解释？ | 查看和追问记录、关联项目状态、可重新查看或纠正的解释 |

### 双向沟通

**主 AI → 用户**：侧栏根据实际操作记录显示状态；用户主动求助时，再结合项目事实和执行结果解释使用影响。原文只作为可展开的依据，不占据默认主区域，不逐条展示原始工具日志。

**用户 → 主 AI**：侧栏先识别表达意图。明确的修改要求带上原话及必要背景转交；普通追问和方案讨论留在侧栏，回答原题则引导回原入口。不能仅凭问号区分提问与修改。转交后给出可追踪的回执。

### 呈现规则

- 当前进展默认展示简短操作状态，例如“正在查看项目”“正在修改文件”“等待你选择”；使用确定性映射，不为生成状态文案调用模型。没有可靠事件时显示暂无法确认，不推断业务功能已完成。
- 变化含义、限制与下一步建议由用户主动提问后生成；已生成且仍有效的解释可直接展示。不展示主对话原文，也不提供原文展开入口；保留现有提问框，不新增替代的快捷求助入口。
- 优先在侧栏提供问题入口；主对话中的选中提问等增强交互，按宿主验证结果接入。
- 检查结果和计划摘要放在相关进展中，无需另外维护“计划”“检查”页签。
- 不要求用户编辑文件路径、依赖名称或结构化任务字段。
- 与主对话重复的信息尽量只呈现一次，避免两边同时生成大量通知。

### 连续使用

切换项目后，侧栏加载对应项目记录。切换会话后，显示该会话的执行状态；历史解释可保留，但需要标明来源和适用范围，不能混入其他项目或会话的当前上下文。新会话不会自动取得 VibeGuide 的项目摘要；侧栏明确显示哪些历史已随修改消息转交，哪些尚未转交。宿主自身已有历史不受此规则改变。

# 05 宿主接入与验证

### 固定首发宿主：DeepSeek Harness

本版仅交付 DeepSeek Harness 集成。产品逻辑与宿主接入保留清晰边界，方便维护；其他宿主的适配与通用替代界面不作为课程交付要求。

已有仓库调研记录了侧栏、消息事件、模型调用和消息转交的候选接入点。接口资料只能说明可能的实现路径，不能替代当前安装版本的端到端验证。

| 需要验证的能力 | 验证成功的可观察结果 |
|---|---|
| 侧栏加载与生命周期 | 在固定版本中安装后可打开；切换项目、会话、重启后归属正确 |
| 进展与变化来源 | 事件关联到正确任务；工具调用结束不会被直接标为功能完成 |
| 当前原题 | 原题未回答时即可追问；答案引导回正确入口；过期选项不套到新题 |
| 独立解释与追问 | 追问可返回结果，主 AI 的开发任务继续运行 |
| 修改要求转交 | 明确要求进入正确主会话，只产生一次有效消息并显示回执 |
| 模型与费用 | 实测模型配置来源、并发影响、调用失败与费用提示方式 |
| 结果与过时处理 | 停用旧记账工具后仍能观察真实检查；结果对应当前版本和要求；相关变化使旧结果失效 |
| 恢复与状态更新 | 重启后核对已有发送；第二个活动工作者不重复发送；界面不会漏掉已保存的状态更新 |

### 实施前的最小验证

固定一组宿主与插件版本，完成“打开侧栏 → 接收一次真实变化 → 追问 → 转交一个修改要求 → 显示真实回执”的完整链路，并保存运行证据。将结果用于选择具体接口，不以 HTML 演示替代集成验证。

若某项接入不可用，必须显示相应能力不可用并记录待解决项。不能用模拟进度、自动切换到其他宿主或把消息放入输入框冒充已发送，来宣称目标交付已经完成。

### 用户上手

提供固定版本的安装说明、插件启用方式、项目选择和一次简短示例。模型未配置或插件不兼容时，说明缺失条件及下一步。安装说明需在干净测试环境中走通。

# 06 核心流程与职责边界

> 主对话表达目标 → AI 推进开发 → 侧栏解释当前情况 → 用户理解或追问 → 明确修改要求转回主对话。

这是一条可随时进入的循环，不要求用户依次完成九个页面。项目结构、技术影响、结果检查和问题解释服务于当前任务。

| 阶段 | 主对话 | 侧栏 |
|---|---|---|
| 开始 | 接收目标，澄清真正影响产品的未知项 | 帮助理解选项与后果；展示已有结构或计划草图 |
| 开发 | 修改代码、运行命令、更新执行计划 | 更新实际操作状态与检查记录，按需解释变化，保持追问独立 |
| 判断 | 处理需要用户选择的实际问题 | 说明方案差别、依据、限制；不重复发起相同提问 |
| 修改 | 接收明确要求，决定执行安排 | 传递原意，显示发送与处理状态 |
| 检查与试用 | 执行合适的验证并提供结果，照常继续任务 | 展示检查覆盖范围和具体试用步骤，用户反馈只对所试范围有效 |
| 继续 | 根据结果继续或调整任务 | 更新结构与项目记录，使旧解释适当失效 |

### 三类入口

接手项目可以先点“帮我看懂这个项目”；新项目从主对话的关键需求澄清进入；卡住时从当前问题及其影响进入。三者最终使用同一套解释、沟通和状态规则，用户也可直接继续主对话，不必先经过侧栏。

### 节奏和暂停

只保留一个 VibeGuide 模式。调整解释深度不会改变主线是否执行。关闭侧栏、看历史解释、连续追问，都不新增开发暂停点。

主 AI 因真实需求歧义、任务依赖、执行错误或宿主权限而等待时，侧栏准确展示等待原因。用户要暂停、叫停已接受的任务或回答权限问题，使用主对话和宿主原生入口；侧栏不提供撤回或独立控制入口，不把“停一下”按普通修改排队后声称已停止。

用户没有试用确认时，可以继续开发；“等待你试用确认”仅描述结果状态，不是开发放行条件。

# 07 功能详述 · F1 项目结构

### 解决什么

帮助用户理解“产品能做什么、由哪些部分配合完成”，并把当前改动放回整体结构中。

### 用户看到什么

默认按功能和职责组织少量节点，例如“每日问题”“回答保存”“打卡进度”。再按需说明这些能力由页面、存储或外部服务中的哪些部分承担。

首次接手已有项目时，先显示已扫描范围与能确定的事实。有仍适用的职责概览就直接展示；没有时提供“帮我看懂这个项目”。用户点击或明确提出同等请求后，一次生成整体职责概览，无需逐文件、逐节点提问。打开页签、缓存缺失或概览过时本身不触发讲解。

| 层次 | 示例 | 展示规则 |
|---|---|---|
| 产品功能 | 回答今天的问题、查看过去回答 | 默认用用户能操作的行为命名 |
| 职责与联系 | 页面接收输入，保存位置记录答案，进度读取日期 | 解释各部分怎样配合，不先展示文件树 |
| 依据 | 对应文件、事件、需求与检查结果 | 需要核对时展开；不承担代码教学 |

### 一次操作的故事

> 用户提交今天的回答 → 保存回答与日期 → 更新打卡进度 → 再次打开时读取之前的记录。

这条故事必须基于项目现状。尚未实现的部分显示“计划中”；仅从代码推测的连接标明“推测”。功能、模块和文件之间允许多对多关系。

### 更新与边界

- 当前任务涉及的节点可高亮，其他部分仍能查看。
- 每个节点关联来源和项目版本；变化后重新核对相关结论。
- 扫描结果提供结构证据，不能由静态文件直接推断运行正常。
- 结构未知时先显示已确认的部分，不补造连接或隐含实现。
- 实现状态与验证状态分别展示，例如“已修改 · 尚未验证”。
- 结构图只读，可点击、缩放、键盘选择，并提供等价职责清单；不通过拖拽或连线修改项目。
- 节点被选中时先显示已有说明；缺少解释时提供求助入口，主动请求才补充。重复请求复用仍有效的内容，过时解释保留历史标记。
- 概览生成失败时保留扫描事实和覆盖限制，提供重试入口；主线照常开发。

### 验收

用户能通过一次主动概览请求看懂主要职责，指出一个功能涉及哪些部分、数据大致经过哪里，并知道哪些部分尚未实现；无需说出技术术语或文件名。只打开面板不产生概览讲解调用。

# 07 功能详述 · F2 技术影响解释

### 解决什么

用户听到了技术选择，但不知道它对自己的产品意味着什么。解释重点是收益、限制、成本和以后调整的影响。

### 默认回答结构

| 内容 | 要回答的问题 |
|---|---|
| 当前作用 | 这个选择正在为项目解决什么问题？ |
| 实际影响 | 用户体验、数据可用性、费用或维护会怎样变化？ |
| 可选取舍 | 如果换一种做法，会多出或失去什么？哪些仍未知？ |

不机械套用三段模板。没有必要选择时，直接解释当前影响；用户追问实现原理时再展开。

### 示例：回答保存

> 现在回答保存在当前浏览器里，用户不用注册就能使用；但换手机后看不到原来的记录。若要换设备继续，需要让不同设备识别同一个用户并访问同一份数据，也会增加使用步骤与维护工作。

可以顺带说明“这是本地存储方案”。默认不讲存储接口的语法、文件位置和实现细节。

### 示例：用户追问 API Key 的影响

> 这是项目调用模型服务时使用的凭证。把它暴露给网页访问者，可能让别人使用你的额度；应由受控的服务端保存和使用。是否有可用额度还需要另外确认。

这是用户求助时的概念解释，不表示本版会自动发现凭证暴露或推送安全告警。

### 交互与规则

在当前解释、项目结构节点或支持的主对话内容旁提供“为什么这样做”“还有其他办法吗”“这会影响什么”。追问保留所指内容和项目背景，主线继续开发。

技术词优先使用已审定词表和仍有效的项目说明；缺少说明时显示“解释这个词”入口。用户主动打开才补充，不为判断“用户是否看得懂”另调模型，也不因界面重绘逐词生成。

讲解不默认罗列技术百科，不把用户看过的内容标为“已掌握”。技术影响没有证据或取决于条件时，要把条件说清楚；费用示例必须注明估算依据或明确只是示意。

# 07 功能详述 · F3 / F4

## F3 目标关联与影响理解

**解决什么**：用户知道想改变的效果，却不知道它与项目哪些部分有关。

用户问“如果希望换手机继续，会影响哪里”，侧栏关联“识别用户”“回答保存”“进度读取”，说明当前限制和可能需要增加的能力。该表达属于讨论，不自动修改代码。

定位结果包含：当前事实、相关职责、可能影响、未知部分。避免直接承诺“不会影响其他功能”；可表述为“目前未发现会影响每日问题展示，修改后仍需检查”。

“我想改这里”用于帮助表达要求；用户若已明确说出目标，直接按 F5 转交，不强制重新填写计划。

## F4 方案与关键选择解释

**解决什么**：主 AI 提出的方案或问题过于技术化，用户无法判断。

主对话负责澄清和维护执行计划，选项本身先说明使用差别和关键影响。用户可以直接看懂并选择；仍有疑问时，侧栏按需补充已有问题与计划的解释。对新的模糊目标，主对话先问少量真正影响行为的问题，数量由不确定性决定；不固定套用问卷，不在澄清前自动搭建项目。

| 关键选择示例 | 应解释的差别 |
|---|---|
| 只在当前设备使用 / 支持换设备 | 注册与身份识别步骤、数据连续性、服务维护 |
| 回答仅自己可见 / 可以公开分享 | 谁能查看、分享后的可见范围和用户预期 |
| 固定每日问题 / 自动生成问题 | 内容可控性、等待时间、外部服务依赖与费用 |

追问随前面的答案变化。例如选择验证码登录后，不机械继续询问密码找回。明确且低歧义的修改直接推进。

主对话出现待回答的问题时，侧栏仅关联原题并提供“帮我理解这些选择”等轻量入口，默认不调用模型重复解释。用户点击入口或主动追问时，才针对具体疑问补充影响与取舍；不另调模型判断“用户是否看得懂”，不自动预生成每个选项的解释。开发中重要变化的摘要同样由用户主动请求，不作为后台自动任务。

再次查看同一问题时，优先复用依据仍有效的已有解释；选项或相关项目状态变化后，标明旧解释不再适用，等待用户需要时再生成。

**本版原题作答回主对话。** 侧栏不复制一套选项或权限审批控件。用户在侧栏输入“选第二个”时，先核对所指问题，再显示“请回主对话的这道题选择，刚才这句话没有作为新任务发送”，并提供可用的原题定位入口。无法定位时明确引导回主对话，不假装已经提交答案。

“第二个为什么”只解释；“把已经确定的功能改成第二种”若目标明确则按 F5 转交。阅读旧题时说“就按这个”，必须澄清所指，不能套用新题。宿主权限请求始终回原生审批入口，侧栏不代为批准。

**验收**：看懂选项后在原题直接作答，不产生额外的侧栏选项解释调用；主动求助时，无需先完成主 AI 回合就能解释当前选项。原题答案不产生新任务，旧题与新题不混用。用户能说出主要影响，侧栏只在观察到原题已回答后更新决定。

# 07 功能详述 · F5 修改要求转交

### 意图识别

| 用户表达 | 行为 |
|---|---|
| “为什么不用云端？” | 解释原因和取舍，不转交修改 |
| “用云端会不会更好？” | 帮助比较方案，不把讨论记成决定 |
| 既定方案已经是单设备，用户说“那就改成换手机也能看。” | 直接转交明确要求，显示实际回执 |
| 当前原题仍在等保存方案，用户说“选换手机也能看” | 引导回原题作答，不另发开发任务 |
| “第二个为什么？” | 解释所指选项；不是选择或修改 |
| “这个不太合适。” | 澄清具体想改什么，再处理 |
| “你记错了，只改说明，先别改代码” | 纠正记录，不发修改任务 |

### 转交内容

保留用户原话、所指功能、相关解释及必要的项目背景。系统补充的建议与用户要求分开标记，不擅自增加登录方式、收费服务或其他功能。用户不需要编辑技术字段，也不必每次点击第二次发送。

澄清时同时保留第一次完整原话与后续补充。例如“换手机也能看，但不要手机号”不能在用户补充登录方式后丢掉否定限制。引用、文档说明和 AI 自动建议都不能冒充用户新指令。

附带的历史仅限与本次目标相关、仍适用且可追溯的要求；适用的项目级限制也要保留。历史背景与本次原话分别标明，转交内容在主对话中可见。不会因为打开侧栏、换会话或纠正记录就自动把摘要交给主 AI。

若当前上下文已经变化，只有实质影响意图解释的部分才需要澄清。例如用户说“就用第二个”，但选项已经变化，不能凭旧位置转交。

同一句话既像回答原题又包含其他要求时，完整保留内容，无法确定通道或范围才澄清；不擅自拆成两次发送或丢掉后半句。有一道待答题也不代表所有新的明确修改都必须等它回答完。

### 可追踪的状态

| 状态 | 成立条件 |
|---|---|
| 正在发送 | 要求已先保存并进入发送流程，尚无可靠接收结果 |
| 已发送 / 待处理 | 宿主确认要求进入指定主会话 |
| 正在处理 | 主 AI 明确开始处理关联要求 |
| 已有改动 / 尚未验证 | 已关联实际改动，尚无适用检查；不能显示完成 |
| 检查已通过 / 等待你试用确认 | 适用检查通过，但用户尚未验收；主 AI 仍可继续开发 |
| 本次要求已完成 | 对应改动、适用检查和用户验收齐备，范围明确且无已知未满足项；只覆盖该要求 |
| 处理受阻 | 主 AI 已接收，但执行失败或仍需处理实际问题 |
| 发送失败 / 结果待核对 | 明确失败，或无法确认是否已进入主会话 |

主 AI 忙碌时，默认按宿主支持的待处理消息机制交付，不能因用户在侧栏阅读或提问而打断当前执行。排队能力和关联方式须实测；不得虚构回执。

### 重复与错误处理

同一要求使用稳定标识，避免重试产生重复任务。发送前未保存成功就不发送；发送开始后响应丢失或记录结果不确定时，先核对接收情况，不直接重发。重启后仍遵循此规则，不因界面重新打开就再次产生任务。

用户要纠正已发送要求时，把明确的业务纠正作为新消息关联原要求；只纠正侧栏记录不触发代码修改。不提供撤回入口，也不宣称已执行的操作被撤销。用户要立即叫停执行，回主对话处理。

**验收**：明确要求不因双击、重启或重试重复产生任务；普通追问和原题作答不发新任务；状态与可核对的实际结果一致。多项要求同时涉及一个文件，也不能把其中一次成功或反馈算作全部完成。

# 07 功能详述 · F6 当前进展与改动解释

### 解决什么

用户希望知道 AI 正在做什么、刚才改变了什么，以及这些变化是否符合自己的目标。

### 展示节奏

开发中根据宿主实际操作记录，显示“正在查看项目”“正在修改文件”“正在运行检查”“等待你选择”等简短状态。连续操作可合并成一条状态，避免逐条播报；这些状态不需要模型生成，不凭操作类型推断正在实现哪项业务能力。

取消默认自动摘要：重要改动、检查完成、回合结束、连续写文件、重新打开侧栏及旧解释失效，都只更新事实、状态或历史标记，不调用模型总结。用户点击“这意味着什么？”、“帮我总结这次变化”或主动追问时，才针对该请求生成，优先复用仍有效的已有解释；不必等待整个开发回合结束。达到解释预算时保留事实，并对本次请求说明暂未生成。

“为什么这样做”优先依据已记录的决定和主 AI 的说明。仅从代码推测理由时明确标注，不替 AI 编造原始动机。

### 用户主动求助后，一条解释的内容

| 内容 | 示例 |
|---|---|
| 变化 | 现在提交回答后，今天的打卡进度会更新 |
| 影响 | 再次打开时可以继续查看；当前方案仅覆盖同一浏览器 |
| 关键取舍 | 暂时无需注册；若要换手机继续，需要增加跨设备的数据访问能力 |
| 检查情况 | 同一浏览器刷新保留已检查；换设备同步尚未实现 |

示例仅用于说明结构。实际显示必须依据真实变化和检查结果。

### 发现意外变化

用户请求理解变化时，以产品行为判断是否偏离约定。例如“文章详情的字体也发生变化，可能超出你只调整首页的要求”。只有某个文件不在计划清单里，不足以认定改动越界；不为主动发现此类变化另开后台总结调用。

提供“问问原因”和表达修正要求的入口，不提供局部撤销按钮。用户也可以直接回主对话说明希望怎样修改。

### 阅读与更新

阅读历史解释时保持当前位置，新进展用提示显示；提供“回到最新”。如果当前所读解释的依据已变化，保留历史内容并标注过时，避免悄悄替换或继续充当现状。

**验收**：未主动求助时，连续修改、检查返回、回合结束、关闭重开及缓存失效产生的额外摘要与解释调用均为零；仍准确呈现已观察到的状态。用户主动求助后，能用自己的话说出变化及一个重要限制，无需阅读文件清单或代码差异。

# 07 功能详述 · F7 检查结果与用户验收

### 解决什么

帮助用户区分“AI 已经改了”“系统做过检查”和“产品行为符合自己的需要”。

主 AI 和宿主执行检查；VibeGuide 读取实际结果并呈现状态，用户主动求助时解释含义。没有运行记录时显示“尚未检查”，不由模型根据代码生成绿色通过状态。主 AI 不再使用额外的 VibeGuide 记账工具后，后台仍需取得真实调用、结果及其适用范围；无法确认检查针对哪个版本、哪条要求时，显示“检查与当前结果的关系待核对”。

| 状态 | 用户看到什么 | 不能推导出什么 |
|---|---|---|
| 尚未检查 | 该行为还没有验证记录 | 不能因为没有报错就称为正常 |
| 检查通过 | 检查对象、覆盖行为、时间和结果 | 项目可以启动不等于所有功能正确 |
| 检查失败 | 失败现象、影响与已知原因 | 未确认的猜测不能作为唯一原因 |
| 需要重新检查 | 相关代码或条件已改变 | 历史通过不能直接代表当前版本 |
| 检查范围待核对 | 看到了检查运行，但不能可靠关联当前要求或版本 | 一段成功日志不等于该功能已通过 |
| 用户体验确认 | 用户明确反馈某项行为符合预期 | 一项确认不能覆盖整个系统 |

### 可操作的体验检查

例如：“写一段回答并提交，刷新页面，查看内容是否仍然存在。”检查紧扣用户目标；用户可以稍后验证，不要求逐项打勾后才允许继续开发。

变化卡明确列出本次对应的要求、结果版本与试用步骤，提供“我试过了，符合要求”／“我试过了，不对”及可选说明。按卡片步骤试过后点“符合”即可保存反馈，不强制再填一遍操作过程；点“不对”可先记录不符，需要提出修正时再补充具体表现。按钮不能代表用户试过卡片未列出的行为。

### 什么时候显示完成

完成标签按具体要求计算。对应改动、仍适用的检查、该范围的用户验收都齐备，且没有已知未满足项，才显示“本次要求已完成”。点击验收不自动补造检查记录，主 AI 自称完成也不直接决定标签。

| 已有依据 | 界面表达 |
|---|---|
| 有改动但没有适用检查 | 已有改动，尚未验证 |
| 检查已通过但没有用户验收 | 检查已通过，等待你试用确认；开发可继续 |
| 用户说符合，但检查缺失或过时 | 已收到你的体验反馈，检查仍待补齐 |
| 用户已反馈，但无法确定对应哪条要求或哪个结果 | 已收到你的反馈，对应范围仍待核对 |
| 三项依据齐备、范围明确且无已知未满足项 | 本次要求已完成，并列出实际覆盖范围 |

例如“分享页能打开”和“回答仍然仅自己可见”同时修改时，用户确认前者不能替后者背书。联合验收要明确展示包含哪些要求；只试了其中一项就只记录该项。相关结果发生新变化，旧反馈保留历史标记，不继续支撑当前完成状态。

发现失败后可进入 F9 理解问题。若用户明确说“请修复这个问题”，按 F5 转交；只是查看失败详情时不自动创建修复任务。

### 影响解释与范围边界

本版不新增独立的面向用户风险提醒、凭证暴露检测或风险雷达。主 AI 正常说明执行影响、用户主动追问相关技术后果以及解释已有检查结果仍然保留；需要依据时说明限制，不宣称做过全面安全扫描或费用预测。模型输入中的敏感内容过滤和宿主权限流程继续有效。

本功能不包含存档、回退、文件恢复或“请 AI 改回”的专门入口，也不建设独立自动检查平台。

**验收**：用户能区分已改动、检查通过、自己试用确认和真正完成；反馈只作用于实际范围。未验收或验收过时不暂停主线，已有检查结果仍准确展示。

# 07 功能详述 · F8 项目记忆与了解过的

### 解决什么

在侧栏保存可核对的项目历史，帮助用户找回曾经讨论的选择，并在提出修改时附带相关背景。保存与转交分别可见，避免把“侧栏记得”误认为“主 AI 已收到”。

| 记录类型 | 记录内容 | 使用边界 |
|---|---|---|
| 用户决定 | 原话、来源、适用项目、后续纠正 | 只有明确表达的决定可作为要求；AI 建议不能冒充决定 |
| 当前事实 | 已观察的结构、变化和检查结果 | 关联证据与项目状态，失效后重新核对 |
| 项目日志 | 重要变化、决定及理由 | 按功能语言记录，保留来源和执行、验证的区别 |
| 了解过的 | 用户打开或追问过的解释 | 只表示有过接触，不推断掌握、认同或偏好 |
| 发送回执 | 要求标识、目标会话、实际附带的历史背景和处理状态 | 支持追踪及去重，不以记录保存代替发送成功 |
| 沟通偏好 | 语言、详细程度、讲解方式等 | 仅调整侧栏；项目偏好不擅自变成全局，不建立领域能力画像 |

### 换会话继续

新会话的侧栏可以读取已有项目记录，主 AI 不会因此自动获得 VibeGuide 摘要。没有转交记录时显示：“这些历史要求尚未由 VibeGuide 附带到本会话；从侧栏发送本次修改时会附带相关内容。”这只说明插件能确认的转交状态，不断言宿主自身历史也不存在。

例如昨天确定“回答仅自己可见”，今天从侧栏要求“增加分享页”，转交消息应附带这个仍适用的限制。用户可以查看实际附带内容，不需要手动搬运技术背景。若直接在主对话继续，侧栏不会偷偷补发历史，也不阻止开发。

| 状态 | 用户应理解什么 |
|---|---|
| 已保存、尚未转交 | 侧栏有记录，尚未由 VibeGuide 发送到本会话 |
| 正在随要求发送 | 已附带相关背景，但尚未确认接收 |
| 已随本次要求发送 | 宿主已接收这些背景；不等于主 AI 已理解、永久记住或执行 |
| 是否送达待核实 | 结果不确定，不自动重发 |

状态针对实际附带的要求版本和目标会话。只转交一部分时标明范围；纠正后的新版本不能沿用旧版本的成功回执；不会用“全部已同步”掩盖遗漏。只有相关、仍有效且可追溯的背景才附带，不整包发送长期历史。

用户可以纠正记录或要求不再使用某条记录。忘掉一项记忆不会修改业务代码；功能修改需要明确表达为开发要求。

### 存储与隐私

项目记录必须隔离，沟通偏好和项目需求分开处理。优先复用现有存储能力，具体目录与迁移方案在实施验证后确定；不能宣称仅复制一个目录即可完整迁移到任何宿主。

关闭侧栏不停止保存已提出的要求和必要回执，也不撤销已接受任务。本版不承诺关闭全部持久记录后仍保留可靠转交和续接能力；若增加记录开关，须先明确哪些记录可关闭及对功能的影响。保存失败时说明未保存；发送前失败则不发送，发送后的不确定按 F5 核对。主线开发不因此被误标为失败。查看过的解释按需加载，过时内容保留历史标记。

**验收**：换会话后侧栏能找回已确认要求，用户知道哪些已转交；明确修改所需的相关历史不遗漏。纠正后不再把旧结论作为当前依据，另一个项目不会读取到这些记录。不得宣称主 AI 已自动继承全部历史。

# 07 功能详述 · F9 卡住时的理解与沟通

### 解决什么

用户遇到报错、效果不符或多次修复仍未解决时，需要知道影响范围和可选处理办法，而不是继续盲目发送“再修一下”。

### 用户看到什么

1. **现象与影响**：谁在什么操作下遇到什么问题，哪些功能受到影响。
2. **已知与未知**：有证据的事实、可能原因、尚未排查的条件分别呈现。
3. **已尝试的办法**：主 AI 做过哪些相关尝试，检查是否显示改善。
4. **可选下一步**：继续定位、缩小修改范围或调整实现方式，并说明代价。

### 示例

> 新增登录后，未登录访客打不开原本公开的作品页。已有访问检查能够复现。可能是访问限制覆盖得过宽，还需要核对具体规则。可以先让主 AI 只处理“保持作品页公开”，暂不改变其他登录行为。

这是一项建议。用户问“为什么会这样”继续解释；用户说“就先修作品页公开访问”才直接转交。

若主 AI 正在用原题询问处理方向，用户的回答仍按 F4 回原入口作答；明确新增的修复要求才按 F5 转交，不能重复安排同一任务。

### 反复修复提示

仅在同一问题有多次关联尝试、且复现或验证仍显示未解决时，提示“这个问题仍未解决”。同一文件被多次修改本身不构成卡住证据，也不使用固定次数直接判断“越改越乱”。

### 传给主 AI 的问题背景

保留用户期望、实际现象、复现步骤、相关检查和已尝试方法。可以附必要的技术依据，但用户无需阅读或编辑这些字段。缺失信息由主 AI 或侧栏针对性询问，不凭空补齐。

本版不提供回退方案按钮，也不保证一次修复成功。用户想恢复旧效果时，直接在主对话中提出要求。

**验收**：用户能说清当前问题影响什么，并提出一个符合其目标的下一步要求；侧栏的问题解释不启动未经要求的修复。

# 08 完整使用旅程 · 从零新建

## 21 天思考小游戏

以下为目标体验示例，展示主对话和侧栏如何共同工作，不表示现有插件已实现。

| 时刻 | 主对话 | VibeGuide 侧栏 |
|---|---|---|
| 提出想法 | 用户：“做一个 21 天打卡思考网页，每天回答一个问题。” | 显示当前目标，尚无代码时不生成“已实现”的项目结构 |
| 澄清关键问题 | 主 AI 询问每日问题来源、回答是否公开、是否要换设备继续，并说明主要影响 | 默认关联原题；用户主动求助时补充解释，不重复生成整组选项说明 |
| 看完解释后作答 | 用户回原题选择保存方式 | 若在侧栏说“选第二个”，引导回原题，说明尚未提交；不额外发送开发任务 |
| 确定起步方案 | 用户选择固定问题、仅自己查看、先在当前设备使用；主 AI 给出易懂的计划并开始 | 展示已有计划与实际操作状态；需要整体职责概览时由用户主动请求 |
| 开发与解释 | 主 AI 实现提交和保存，继续其他工作 | 默认显示修改与检查状态；用户求助后解释保存范围及当前浏览器的限制，主线继续 |
| 讨论取舍 | 用户在侧栏问：“为什么换手机看不到？” | 解释当前保存范围，以及支持换设备会增加的身份识别和共享存储能力 |
| 明确修改 | 用户：“那就改成换手机也能看，仍然只给本人看。”主 AI 接收并调整任务，必要时澄清新的产品选择 | 直接转交原意并显示真实回执，不要求再填任务卡；结构先标“待实现” |
| 检查结果 | 主 AI 检查相关行为并提供结果 | 展示实际验证范围；若没有真实换设备检查，明确显示尚未验证 |
| 试用反馈 | 主 AI 可继续其他任务 | 卡片说明“提交后刷新，看回答是否仍在”等步骤；用户点符合无需重复填说明，只确认所试范围 |
| 下一天续接 | 用户在新会话继续开发 | 侧栏保留历史并说明尚未转交；从侧栏提出本次目标时附带相关限制，可查看实际内容 |

### 用户最终获得什么

用户理解单设备与跨设备方案的影响，知道保存和身份识别之间的关系，能提出“换手机继续但仍然私密”的真实需求。无需了解数据库表结构、浏览器接口语法或文件差异。

期间若仅追问或查看历史解释，开发继续。出现真正需要用户决定的新问题时，主 AI 按正常流程提出，侧栏协助理解。

## A 接手开源博客，改成作品集

| 步骤 | 目标体验 |
|---|---|
| 打开项目 | 侧栏先显示扫描范围和事实；有有效概览就展示，否则提供“帮我看懂这个项目”，不自动生成讲解 |

| 验证与继续 | 展示实际桌面和手机检查范围；用户试用并反馈。只确认首页不等于确认详情，未检查或未确认的范围不显示完成；主线仍可继续 |

## C 增加登录后，公开页面打不开

| 步骤 | 目标体验 |
|---|---|
| 遇到问题 | 用户说“分享出去别人打不开”；侧栏说明需要区分自己的登录状态与访客实际访问 |
| 查看依据 | 聚合真实的复现现象、相关改动和主 AI 已尝试方法；原因未知时明确保留不确定性 |
| 判断办法 | 解释“保持作品页公开、只限制私人内容”会怎样影响访问权限，避免向用户倾倒认证术语 |
| 明确要求 | 用户说“作品页继续公开，私人记录仍要登录”，直接转交并显示接收状态 |
| 主 AI 修复 | 侧栏解释新的访问行为；用户阅读和追问不影响修复进行 |
| 观察结果 | 分别显示未登录访客、已登录本人访问的检查结果；一次成功不代表所有访问场景都通过 |
| 试用确认 | 用户按步骤试过对应访问行为后反馈；若只试了公开页面，不将私人记录的权限要求一并标为完成 |

三个场景都需要真实端到端演示。仅有静态地图或模拟聊天不能作为该场景已经交付的证据。

- 阅读中出现新变化：保留当前位置，显示“有新进展”和“回到最新”。
- 当前解释已过时：显示过时原因，重新提问时使用最新上下文。
- 明确修改转交：显示正在发送、已发送或失败；已发送后可查看要求原文。
- 原题作答：引导回原题，不展示“修改已发送”；旧题指代不明时澄清，权限问题回宿主入口。
- 新会话有历史：区分尚未附带、正在发送、已接收、结果未知；只报告插件可确认的转交范围。
- 无项目概览：显示扫描覆盖范围与“帮我看懂这个项目”，不通过空白等待暗示后台正在自动讲解。
- 用户验收：当前卡片已绑定明确试用范围时可一键反馈；旧结果或范围不清时保留反馈并提示待核对，不能误标完成。
- 含糊表达：只询问不清楚的部分，不强制跳转到复杂草稿页。
- 模型不可用或内容生成中：显示真实状态，保留已有内容，主线开发继续。
- 关闭侧栏：不取消主任务；重新打开时加载正确项目、会话和当前状态。
- 重启与断线：先核对已有要求的接收状态，不重复发送；刷新后显示一致的最新记录，暂无法核对时说明数据截止范围。

# 10 系统设计概要

具体架构与接口见[技术设计 v2.2](VIBEGUIDE_TECHNICAL_DESIGN_V2_2.md)。本章用产品语言说明职责和正确性，不把拟定接口写成已完成集成。

| 模块 | 职责 | 必须守住的边界 |
|---|---|---|
| 宿主适配 | 获取事件、当前问题、侧栏、消息与回执 | 绑定项目和会话；原题回原入口；不自动代答权限请求 |
| 项目观察 | 读取结构、变化及检查证据 | 区分主 AI、用户和其他来源的改动；无法归因时明确未知 |
| 状态与证据 | 关联要求、改动、检查与用户反馈 | 逐项判断范围；代码变化使相关旧结论失效；不以工具成功或单次点击冒充完成 |
| 解释服务 | 仅按用户请求生成变化摘要、取舍、项目概览与问题解释 | 无自动摘要任务；旁路只读；有效内容复用；保留未知和推断；与主任务隔离 |
| 意图与转交 | 区分问题、讨论和明确修改；关联回执 | 保留用户原话，不扩张要求；去重和未知结果核对 |
| 项目记录 | 后台统一保存决定、事实、解释与侧栏偏好 | 项目隔离、用户可纠正；不把记录自动注入主 AI，不要求主 AI 调用记账工具 |
| 侧栏界面 | 当前进展、项目结构、了解过的 | 不抢走阅读位置；不以阅读状态控制开发 |

### 数据与更新

处理事件需有顺序、关联标识和重复处理保护。一次有意义的产品变化可能跨多个工具调用；同一文件也可能由多人修改。对无法获得的变化只说明观察范围，不能假装完整覆盖。

同一份记录在前期只允许一个活动后台工作者写入和发送。异常退出或热重载后，先恢复记录、核对已开始的发送，再继续处理；无法确认的发送保持待核实。界面读取同一提交边界下的完整状态，发现更新缺口就重新同步，不混合旧回执、新要求和未保存解释。恢复能力指插件记录恢复，不是业务代码回退。

### 模型与隐私

仓库保留在本地，但必要的代码片段、问题和上下文可能发送到所配置的模型服务。界面应说明使用的服务和必要的数据范围；过滤凭证及敏感配置内容，不把“本地仓库”描述成所有内容均不离开设备。

增量更新和缓存减少重复解释；并发追问不应使主任务失去响应。模型来源、限流和成本需要实测。文档只承诺有依据的费用说明，不提供无来源的价格或完成时长。

侧栏未求助时，额外摘要与解释调用应为零，包括重要变化后的总结。主线开发与既定后台记录整理的模型消耗仍须独立统计；记录整理不得借机生成面向用户的摘要。分别记录概览、术语、变化求助与其他主动追问的用量，“按需”不等于整个系统零 token。

### 本版本不包含

自动摘要、自动存档与恢复／撤回入口、逐步验收后放行、独立的面向用户风险提醒或风险雷达、独立自动检查平台、隐藏的项目／偏好上下文注入、主 AI 的 VibeGuide 记账工具、侧栏原题代答或权限审批、复杂计划编辑、计划模板库、第二宿主、整套宿主一键安装、自动汇报系统、多人共享地图、领域能力画像、术语熟练度或强制测验。

### 开发顺序

| 阶段 | 重点 | 必须拿到的结果 |
|---|---|---|
| P0 接入验证 | 真实侧栏、事件、独立追问、消息回执、原题和检查依据 | 原题未答也能求助；消息到正确会话；明确哪些检查证据可可靠取得，不以演示冒充可用 |
| P1 状态可信 | 停用动态注入和旧记账工具，后台统一记录、恢复与界面同步 | 检查观察链继续工作；不能确定时明确待核对；重启不重复发送，不混用项目或半更新状态 |
| P2 解释与修改 | 按需解释、首次概览、原题分流、原话转交、历史提示、基本结果关联 | 解释与修改各走正确路径；用户知道哪些历史已交给主 AI；改动和要求范围可核对 |
| P3 结构与历史 | 只读职责图、变化对比、了解过的、纠正、用户验收 | 按具体范围反馈；一项验收不扩大为全部完成；阅读稳定，概念认识围绕真实项目 |
| P4 加固 | 复杂意图、更多故障情况与并发支持 | 扩大可靠运行范围，保留既有未知不重发、范围关联和完成依据规则 |
| P5 交付 | 三类场景联调、安装说明、真实用户试用和课程展示 | 三类旅程均有真实证据，记录理解效果、调用量与未解决问题 |

基础去重、保存后发送、结果未知先核对、唯一活动写入者和明确验收范围不能推迟到 P4。P2 的概览可以先用职责清单呈现，P3 再接完整图形交互；最终课程范围仍包括结构图与等价清单。

阶段完成代表实现进度，不改变上表范围。范围调整需记录影响到的场景、原因和新的验收条件。

# 12 衡量成功与验收方式

核心观察是：用户能否在理解影响的基础上表达真实意图，并识别结果是否符合目标。功能完成率仍需关注，但不能单凭用户点“通过”、术语数量或模型自评证明效果。

| 维度 | 观察方法 |
|---|---|
| 变化理解 | 用户能否说出刚才改变的产品行为，并指出一个重要限制 |
| 方案判断 | 用户能否比较当前相关选项的实际后果，说明自己的选择理由 |
| 沟通准确 | 转交要求是否保留原意；是否存在漏项、扩张或把提问当任务 |
| 结构理解 | 用户能否描述相关部分的职责和联系，不要求复述技术名词 |
| 结果判断 | 用户能否区分已修改、检查通过、用户试用确认、完成与历史结果；是否知道本次反馈覆盖哪些要求 |
| 开发干扰 | 追问是否阻塞主任务、自动更新是否打断阅读、是否重复确认 |
| 连续性 | 侧栏是否保留要求，用户是否知道历史已否转交；相关背景是否随明确修改发送，旧事实是否失效，项目是否隔离 |
| 调用与等待 | 未主动求助时是否保持零额外摘要与解释调用；重要变化与检查完成是否也不触发生成；重复请求是否复用；各类调用量、等待时间与主任务响应是否可接受 |

### 三类场景的完成标准

A：看懂已有项目并提出一次准确修改；B：理解关键选择并跟随从零开发；C：理解一个真实故障的影响并提出有效下一步。每类都要出现一次旁路追问与一次明确修改转交，验证真实回执。

系统验收还需覆盖：普通问题和原题作答不发新任务、同一要求不重复转交、关闭侧栏不暂停、过时结果不显示为当前通过、发送失败不冒充完成、无证据不标功能成功、用户未验收不标完成。界面测试、真实集成与用户理解证据分别记录。

### 六项改进的产品验收

| 改进 | 试用情境 | 通过标准 |
|---|---|---|
| 原题作答分流 | 看完解释后说“第二个”，以及阅读旧题时说“就按这个” | 当前题回原入口；旧题歧义先澄清；不额外发任务或替用户批准权限 |
| 检查证据延续 | 主 AI 无旧记账工具时完成一次真实检查 | 侧栏能核对其结果与范围；依据不足就标待核对，不编造通过 |
| 验收准确对应 | 两项修改涉及同一处代码，只试用其中一项 | 反馈只覆盖该项；无检查、无验收或范围不明时不完成；不阻塞开发 |
| 新会话历史提示 | 昨天要求私密，今天从侧栏要求加分享页 | 先说明历史尚未转交；发送时附带相关限制；可查看实际内容和接收状态 |
| 主动项目概览 | 首次打开已有项目，再点“帮我看懂这个项目” | 打开时不自动讲解；一次请求得到整体职责概览，重复请求复用有效结果 |
| 恢复与界面一致 | 发送过程中断线、重启或切换项目 | 不因重开重复发送；未知保持待核实；界面最终与可核对状态一致，旧项目片段不混入 |

### 课程用户测试

建议招募 6-8 名非技术用户作为探索性可用性测试，安排难度相近的任务，交替使用普通主对话与 VibeGuide。测试顺序交错，使用隔离的工作区、会话与插件状态目录，提示和模型设置可比，避免前一组答案或记忆影响后一组。

包含原题作答、新会话续接、首次概览和部分验收四种真实操作。观察者核对原话与结果，询问用户理解了哪些影响、哪些背景已转交、哪些行为已确认；不能只问“好不好用”或用模型替自己评分。

评估依据由真实项目行为、检查记录和事先准备的标准共同确定，不只对照 VibeGuide 自己生成的地图。记录误解和失败案例；小样本结果用于改进，不宣称具有普遍统计结论。解释关闭率只作线索，需结合用户是否已经理解来判断。

# 13 风险与异常处理

| 风险或异常 | 用户可能遇到什么 | 产品处理 |
|---|---|---|
| 解释错误 | 依据存在，但总结或取舍讲错 | 区分推断，提供纠错；修正记录并重新核对关联解释 |
| 内容过时 | 主线已修改，侧栏还在讲旧方案 | 标记适用状态与过时原因，重新提问使用最新上下文 |
| 误识别意图 | 一句追问变成修改任务 | 问题和讨论不发送；对含糊或冲突部分先澄清 |
| 原题与新任务混淆 | 在侧栏选方案，主对话却仍等原题 | 引导回原入口作答；不发送第二份任务；旧题指代先核对 |
| 历史转交误解 | 侧栏显示昨天的要求，用户以为主 AI 已自动知道 | 明确显示实际附带与接收状态，不自动注入或补发 |
| 转交结果未知 | 网络超时，不知道要求有没有送达 | 显示待核对，查询接收结果后再决定是否重试 |
| 执行与保存不同步 | 任务已执行，回执记录未保存 | 分开说明两种结果，不重新执行已成功的任务 |
| 事件缺失或多人修改 | 无法确认变化由谁产生 | 标注观察范围和未知来源，不归功或归责给主 AI |
| 把检查当保证 | 页面能打开，被理解成所有功能完成 | 展示具体检查对象、版本和覆盖范围 |
| 验收范围扩大 | 只确认分享页，却连隐私设置也显示完成 | 验收绑定具体要求和结果；范围不明保留反馈并标待核对 |
| 讲解过多 | 抢阅读位置、堆叠概念、重复通知 | 默认简短，按需深入；固定阅读位置，聚合相关变化 |
| 模型慢或不可用 | 侧栏持续等待或失败 | 给出真实状态并保留内容；主线不因解释失败停止 |
| 宿主不兼容 | 侧栏或转交通道不可用 | 固定兼容版本，显示不可用项，修复接入后重新验证 |
| 隐私与成本 | 用户误以为所有分析均在本地 | 说明模型服务、必要发送范围与可能产生的调用费用 |
| 项目记录混用 | 另一个项目的选择影响当前项目 | 绑定项目和会话、限制检索范围，并覆盖隔离测试 |
| 重启或重复打开 | 同一要求再次发送、旧数据覆盖新回执 | 先恢复并核对；第二个后台实例不重复工作；有更新缺口时重新同步 |

### 接入失败不等于用户流程可以造假

当宿主尚不支持某项接入，产品设计目标仍在，交付状态应记为未完成或受限。静态界面、模拟事件和手动复制可以帮助调试，但必须明确标注，不能替代真实发送回执和运行结果。

### 恢复范围

本版不提供业务代码恢复功能，异常应对不依赖自动回退。用户希望纠正效果时，通过主对话提出修改要求；侧栏继续负责解释和状态呈现。插件自身的记录恢复、去重和状态核对是可靠运行要求，不意味着能撤销已经执行的业务操作。

### 实施中需要验证的事项

4. 复用本地项目存储的迁移、恢复、容量与隔离；后台独占运行和快照一致性。不能仅凭存储成功认定语义正确。
5. 三类真实样例中的理解效果、原题分流准确性、新会话提示是否清楚、验收是否被正确理解。
6. 主动概览、选项和术语解释的实际调用量、等待时间与主任务干扰程度。

这些事项需要实现与测试证据，不重新打开已确定的产品方向。若验证表明必须改变目标，记录具体限制、影响到的场景及替代方案，再更新产品决定。
