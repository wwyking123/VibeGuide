# VibeGuide v2.2 开发状态

更新：2026-11-17，版本 `0.2.0-alpha.13`。本文件描述实际代码和已有的验证，不描述目标；[产品设计 v2.2](VIBEGUIDE_PRODUCT_V2_2.md) 和 [技术设计 v2.2](VIBEGUIDE_TECHNICAL_DESIGN_V2_2.md) 仍描述最终目标，与后来的决定冲突时以 [reviews/](reviews/) 里的记录为准。

alpha.7 及之前各批的交付和验证记录原样保留在文末“历史记录”里。那部分描述的试用步骤、范围核对、“了解过的”页、结构关系图等已经删除或改掉，不代表现在的行为。

- 还没有做过真人试用。
- alpha.12 和 alpha.13 都在 2026-11-17 发布到 `release` 分支（一键安装的来源）。本机日常使用的 Harness `0.2.2-rc.3` 装的是 alpha.12，所有者确认正常。

## 当前能力

| 能力 | 现在的行为 | 边界 |
|---|---|---|
| 白话沟通规则 | VibeGuide 模式等于当前 Harness 的标准模式加一段静态的 [core.md](../prompts/core.md)；主 AI 的工具与标准模式相同。 | 侧栏不向主对话的提示里注入任何记录。在 Harness 的模式编辑器里改 VibeGuide 模式能否保存，没有验证。 |
| 侧栏入口 | 右栏唯一的 VibeGuide 标签；两个页面“进展”“项目结构”，齿轮进入设置。只在 VibeGuide 模式的会话里可用。 | 打开、刷新、切页不调用模型；界面每 5 秒读一次快照，不是增量订阅。 |
| 进展页 | 一个彩色圆点加一句话的状态；卡住时一张排障卡（失败的检查、最近尝试、下一步建议）；主对话里提过的要求按“还在做 / 可以试用了 / 已完成”列出。 | 状态来自真实的工具执行和回执，没有足够证据时显示无法确认。“可以试用了”指同一会话里有对应改动且没有失败的检查，不证明功能正确。“已完成”只在用户点“没问题了”之后出现。 |
| 要求识别 | 主对话里的用户消息按固定规则记为要求，包括“标题太长了”“登录老是失败”这类抱怨；问句、引用和“先别改”不计入。 | 规则只覆盖常见说法。漏判只是少一条要求，不会发出任何任务。 |
| 项目结构页 | 顶部是 AI 总结的产品名；各部分按“用户看到的 → 背后的规则 → 数据存在哪里 → 外部服务”四层列出，标出能用 / 模拟 / 还没做和“刚改过”；点某个部分，说明在它下方展开；文档、设计稿和测试脚本收在“开发用的资料”里。 | 概览只在用户要求时生成，保留最近 30 版。分层和成熟度是模型根据有限的文件摘录推测的，不是运行结果。旧格式的概览显示“按新方式整理”。 |
| 提问 | 底部输入框只用来问。讲解可折叠，默认展开最新一条，显示基本 Markdown；第一次打开有两个示例问题。看起来像在回答原题或批准权限的话，会提示回主对话处理。 | 相同依据的讲解走缓存；会话有新进展后旧讲解标为当时的讲解。对话原文中的秘密只做基础过滤。 |
| 划词提问 | 在 VibeGuide 模式的主对话里选中文字，旁边出现「问问这个」，点击后带着选中内容进侧栏；不写问题就问“这是什么意思？”。 | 选中内容最多带 1200 字。常见术语由本地 14 个词条直接回答，不调用模型。宿主页面里找不到对话区标记时，这个按钮不出现。 |
| 一键发到主对话 | 讲解或排障建议里有具体改法时显示按钮。点击后侧栏 AI 写好要求直接发出，不预览；这条要求算作用户本人的，并自动带上本项目相关的旧约定。 | 先保存记录再调用模型，写好后与发送记录一起保存再发送。中途失败或重启只标为未发送，不补发；结果不明时只核对，不重发。一次最多带 40 条、共 16000 字的旧约定，超出时不发送并提示去设置里停用。 |
| 设置 | 讲解方式（语言、篇幅、例子、顺序）；每日和每轮次数上限（默认 100 / 20，可设 0–1000）；历史记忆里可以停用某条旧约定。 | 同时保存两次时，后一次提示刷新，不覆盖前一次。 |
| 用量控制 | 提问、生成概览、一键代发都在调用模型前先占用次数；同时最多 2 个讲解，每个项目最多 1 个。 | 失败、取消和结果不明的调用也计数。提供方没有报告 token 时显示未知，不估算费用。 |
| 宿主版本 | `0.2.1-rc.2`、`0.2.1-rc.3`、`0.2.2-rc.3` 记为已验证；其他更新的版本一律照常加载，设置页提示“还没一起测试过”；只有比 `0.2.1-rc.2` 更旧的版本拒绝加载。 | “照常加载”只表示不主动拒绝，不保证侧栏用到的内部接口没变。`0.2.1-rc.2`、`rc.3` 是用 alpha.11 及之前的安装方式验证的，alpha.12 没有在这两个版本上跑过。 |
| 动效 | 切页、新讲解、展开说明有淡入；AI 工作或等待选择时状态圆点会跳动。 | 系统开启“减少动态效果”时全部关闭。 |

侧栏通过宿主认证后的 `/api` 通道访问自己的后台；每个请求绑定会话，只允许桌面所有者。浏览器不持有模型密钥，也不直接调用模型提供方。

## 跟随 Harness 更新

alpha.11 及之前有两处会让插件在 Harness 更新后失效，alpha.12 都改了：

- **安装时抄了一份标准模式。** 安装器把当时 Harness 的标准模式整份写进插件目录。Harness `0.2.2` 的标准模式里有一项配置要按文件所在位置找模块，抄到插件目录后找不到，VibeGuide 模式因此无法挂载；即使不出错，抄下来的那份也不会随 Harness 更新。现在插件目录里不再有标准模式的内容：新增的 `src/guide/host/preset.ts` 在每次启动时读取当前 Harness 自带的标准模式定义，原样加上沟通规则，从标准模式文件自己的位置注册成 VibeGuide 模式。
- **版本检查会拒绝加载。** 原来 0.2 以外的版本直接拒绝。现在只拒绝比最早支持的版本更旧的，其余都加载并尝试。

模式注册和侧栏后台是两个独立的插件，一个出错不影响另一个。

仍然会受 Harness 更新影响的地方，代码里无法消除：

- 侧栏后台用到 Harness 的内部服务（会话读取与控制、模型调用、工具执行前后的事件、发送队列、客户端通道）。这些接口改名或改形状，侧栏会出错或连不上，界面提示更新 VibeGuide；主对话和沟通规则不受影响。
- 模式注册依赖标准模式定义文件的位置（`dsh-web-app/presets/standard.patch.yml`）和注册接口。文件挪走或结构变了，VibeGuide 模式不会出现在模式菜单里。
- 安装时记下的 Harness 运行环境路径。应用换了安装位置需要重装。
- 划词按钮依赖主对话页面里的一个标记，找不到时按钮不出现。

已安装 alpha.11 及更早版本的用户需要重新安装一次才能得到新的方式。

## 记录与限制

- 记录在安装器指定的 `<storageRoot>/guide-v1/`。新安装默认是 `~/.dsh/vibeguide-p0-state/`（沿用旧路径），升级时沿用原来的位置。停用或移除插件都不会删除记录。
- 每个会话一个 JSON 文件，每个项目一个 JSON 文件，单个文件上限 8 MiB。会话记录最多 3000 次操作、200 条讲解、500 条输入、500 条发送、1000 条要求；项目记录最多 30 版概览。到上限时明确报错，不静默丢弃旧记录。
- 同一时间只允许一个写入者（用 Node 自带的 SQLite 持有锁，进程退出自动释放）。写入先写临时文件再替换。文件损坏时报错，不清空。
- 用于判断“检查是否仍然适用”的文件指纹：最多 500 个文件、共 8 MiB、单文件 1 MiB、扫描预算 120 毫秒。项目结构用单独的索引：最多 5000 个文件、共 64 MiB。发给模型的结构摘录共 24000 字符、每个文件最多 1800 字符。
- 扫描排除依赖、构建产物、秘密文件、符号链接、硬链接和插件自己的记录。扫描不完整时不会宣称覆盖了整个项目。

## 安装与发布

- macOS：[install.sh](../install.sh) 下载预先构建的包，用 Harness 自带的运行环境执行安装器，不需要 Node 或 git；GitHub 下载不动时换 jsDelivr 镜像。
- Windows：[install.ps1](../install.ps1) 有只读的环境检查模式（`VIBEGUIDE_CHECK=1`）。脚本是对照 Harness 源码写的。实际运行情况见“已知问题”第 2 条。
- 插件位置在 Harness 设置里记成 `file://` 地址而不是普通路径（alpha.13 起）。Harness 把这个值当网址解析，`C:\...` 这样的 Windows 路径会被读成协议为 `c:` 的网址而加载失败。
- 两个安装脚本依次尝试 GitHub 和四个 jsDelivr 镜像（`cdn`、`fastly`、`gcore`、`testingcf`）下载安装包。
- 安装器在改动任何 Harness 设置之前先自检：在临时文件夹里试存、试读记录和项目文件，不通过就停止。之后把插件放进 `~/.dsh/plugins/`（只有插件自己的文件和两行声明，不含 Harness 的内容），在 `profiles/desktop/cordis.patch.yml` 增加一项声明，原文件备份到 `~/.dsh/.vibeguide-backups/`。
- 发布：`sh scripts/release.sh` 先跑 `npm test`，再把构建好的包、`install.sh`、`install.ps1` 提交到本地 `release` 分支；`git push origin release` 之后一键安装才拿到新版本。发布脚本不跑 smoke 测试。

## 代码入口

- `src/index.ts`：把 `prompts/core.md` 注册成系统提示里的一节。
- `src/guide/plugin.ts`：后台入口。注册侧栏接口，监听工具执行前后和会话事件，卸载时取消在途请求并释放存储锁。
- `src/guide/host/adapter.ts`：读取会话、当前模型；独立的讲解、概览和代写调用；发送队列和回执查询。
- `src/guide/host/preset.ts`：每次启动按当前 Harness 的标准模式注册 VibeGuide 模式。
- `src/guide/host/compatibility.ts`：安装器与后台共用的宿主版本判断。
- `src/guide/host/choices.ts`、`lineage.ts`：当前原题的关联；用户消息与操作的来源。
- `src/guide/service.ts`：请求校验、依据核对、讲解缓存与取消。
- `src/guide/intent.ts`：侧栏提问的分流（`routeQuestion`）和主对话要求的识别（`isRequirement`）。
- `src/guide/communication.ts`：一键代发（`handoff`）、持久的发送状态、恢复与对账。
- `src/guide/progress.ts`、`files.ts`、`store.ts`：操作归类与回执、文件指纹、本地记录。
- `src/guide/project.ts`、`project-scan.ts`、`structure.ts`：项目概览、结构摘录、结构索引。
- `src/guide/work.ts`、`requirements.ts`、`outcomes.ts`、`trouble.ts`：要求状态、历史约定、改动与检查的关联、排障材料。
- `src/guide/support.ts`、`glossary.ts`、`quote.ts`：偏好与用量、本地词条、划词引用的格式。
- `src/client/index.tsx`：侧栏界面主体；`project-panels.tsx`、`work-panels.tsx`、`support-panel.tsx`、`analysis-card.tsx` 是各页面和卡片；`selection-ask.tsx` 是主对话里的划词按钮；`outbox.ts` 保存发送前的草稿和稳定标识；`rpc.ts` 把连接错误换成中文说明。
- `scripts/desktop.mjs`、`install-desktop.mjs`、`selftest.mjs`：安装器与安装前自检。
- `scripts/smoke-guide-desktop.mjs`：在隔离的真实 Harness 里用固定回答走完整流程。
- `scripts/eval-sidebar.mjs`、`evals/sidebar/cases.json`：真实模型评测。

## 已知问题

1. **alpha.11 及更早的安装需要重装一次。** 那些安装里抄了一份旧的标准模式，在 Harness `0.2.2` 上 VibeGuide 模式很可能打不开；重新运行一键安装命令即可。本机在 2026-11-17 重装为 alpha.12：装好的副本通过了 `smoke-guide-desktop.mjs --installed` 检查，所有者在日常应用里新建 VibeGuide 会话并打开侧栏，确认正常。没有其他用户重装后的反馈。
2. **Windows 还没有验证通过。** 2026-11-17 所有者在一台真实的 Windows 电脑上试装 alpha.12：不连 VPN 时三条安装命令（GitHub 地址和 `cdn.jsdelivr.net` 镜像）都不成功，具体报错没有拿到；连上 VPN 后安装器报告装好了，但 Harness 里没有 VibeGuide 模式。查到一个确定的缺陷：插件位置被记成 `C:\...` 路径，Harness 当网址解析时会失败，alpha.13 改成了 `file://` 地址。这是否是唯一的原因不确定，因为没有拿到那台电脑上的 Harness 日志；改完后也还没有在 Windows 上重新试过。另外 `package.json` 的 `os` 字段只列了 `darwin` 和 `linux`；安装走脚本而不是 npm，是否有实际影响没有验证。
3. 用户不点“没问题了”，要求会一直停在“可以试用了”。用户事后在主对话提出的不满意会成为一条新要求，不会把旧要求改回“还在做”。
4. `src/index.ts` 里的规则版本号仍是 `2026-10-21.2`，而 `prompts/core.md` 在 2026-11-02 改过（增加“可以重点看看”）。
5. 后台留有界面已不直接使用的部分：`history`、`annotate`、`analyze` 三个接口；`submit` 里旧的澄清与转交分支；项目记录里的试用、反馈、范围绑定字段（为读取旧记录保留）。
6. 技术设计文档里的“实现更新”段落还停在 alpha.5 / alpha.6。

## 还没做

- 真人试用，以及三类用户旅程的评测。
- 更多真实模型、更多用例的评测；统计多次运行的波动。
- 快照的增量订阅（现在是每 5 秒轮询）和持续的文件监听。
- 旧版“项目续接”记录的迁移（旧记录保留在原处，不读取）。
- 要求识别和历史约定的相关性判断仍是固定规则，不保证覆盖任意说法。

### alpha.7 时的说明

| 能力 | 当前实现及边界 |
|---|---|
| 原生侧栏 | Host 级服务、Client bundle、右侧唯一 VibeGuide Tab；对话顶栏按钮和右栏开始页入口。空白新会话的原生顶栏会隐藏自定义动作，仍可从右栏开始页进入。 |
| 提问布局 | 不展示主对话原文或“查看依据”，不添加替代求助入口；现有提问框固定底部。打开和刷新不请求讲解。 |
| 当前会话 | 从宿主不可变 observation cut 读取；项目按当前真实目录标识，使用当前 preset/model 投影；不把压缩摘要或继承的未答原题当作当前用户输入。 |
| 按需解释 | 通过宿主模型路由独立 prepareCall；没有业务工具，打开与刷新不生成解释；同一依据有效缓存，重复请求去重，限制并发、输入和输出，支持超时/取消。 |
| 原题解释 | legacy tool/call + timed projection；真实来源序号与派生问题/选项身份；解释只带选中的那一道题。侧栏提示回主对话原卡作答，不代答。 |
| 失效显示 | 会话有新进展，旧讲解标为当时讲解；同会话切换项目清理旧项目视图，在途结果不能进入新项目。Basis 现覆盖会话、模型/题目、实际操作结果及有界文件指纹；旧讲解恢复时重新核对。指纹范围不是完整依赖环境或业务需求范围。 |
| 单向阀接线 | 隔离 v2 预设仅增加静态 core.md，主 AI 工具与标准模式一致，无旧动态记录注入/记账工具。旧安装版仍保留原链路，尚未迁移用户数据。 |
| 统一输入与澄清 | 原输入框新增 submit 通道：明确追问只解释，明确修改直接转交，含糊或混合表达澄清，原题答案与权限回答回主入口。采用保守确定性规则，不让模型猜测决定是否发任务；复杂表达可能多问一次。 |
| 持久修改转交 | 输入、首次原话、所有澄清补充和 Delivery 同次保存；记录 dispatching 后才调用宿主 queue。显示正在发送、已排队、已送达、待核对或未发送成功。不会把接收等同于执行或验收。 |
| 去重与恢复 | 稳定请求 ID 绑定项目、会话与完整内容；浏览器草稿保留同一 ID；热重载恢复 pending，dispatching/unknown 只对账不重发。核对原生 rpcId、原文及接收项目，重复或内容不符显式标为待核对。 |
| 实际操作状态 | 监听真实工具执行与回执，区分读取、修改、检查、等待及空闲；重启不沿用旧的正在执行状态。没有活动工具但宿主仍运行时显示工作中，状态缺失时明确无法确认。 |
| 改动与检查 | 执行前持久化有界文件基线，执行后记录文件指纹变化及原生命令退出结果。命令正常结束不等于功能完成。文件变化、扫描不完整、并发修改或来源不明确时标明检查范围的适用限制。 |
| 本地恢复 | 按项目和会话持久保存操作与主动讲解；单写者锁、原子写与读回、事件任务登记和启动补读。重开载入已保存的讲解，失效的标为历史，不重新生成。不同项目隔离；当前进展保持会话隔离，“了解过的”明确展示本项目其他会话的历史讲解。 |

客户端通过宿主认证后的 `/api` 通道访问自有 Gateway；请求绑定 session resource，并只允许桌面 owner。浏览器不持有模型密钥，也不直接调用模型提供方。边界有输入字段校验，不额外返回绝对项目目录字段；会话原文可能包含路径，秘密过滤只是补充处理，不能承诺识别任意秘密。
