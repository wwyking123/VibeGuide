# 01 现状、目标与交付边界

### 已有基础与新增工作

| 能力 | 源码现状 | 本版实现工作 |
|---|---|---|
| 易懂沟通与需求澄清 | `src/index.ts` 与 `prompts/core.md` 已提供主 AI 规则 | 延续并验证规则，不把解释责任全部移到侧栏 |
| 项目续接与记录 | `continuity` 已有项目记录、来源验证和动态上下文 | 增加事件处理状态、语义核对与纠正链路 |
| 事实与检查证据 | `workbench` 已有事实、检查、工具回执和适用性判断 | 统一失效传播，提供可读的查询视图 |
| 偏好与隔离 | 已有个人／项目偏好和按项目目录隔离的存储 | 复用并限制作用域，补充侧栏阅读状态 |
| 原生侧栏与独立解释 | 当前包没有客户端入口；HTML 原型独立存在 | 新增客户端插件、服务端接口及只读解释链路 |
| 修改要求转交与回执 | 当前没有侧栏消息发送闭环 | 新增意图处理、持久发送记录、对账及状态关联 |

现有 `receipts.json` 记录的是**工具执行证据**，不能当作“修改要求已送达主对话”的回执。旧版静态影响提示、服务使用引导等可以保留，但不替代本版三类侧栏内容。

### 本版完整目标

支持从零开发、接手已有项目、开发中卡住三个场景。提供“当前进展／项目结构／了解过的”，将解释、结构认知与需求沟通连成完整流程；开发可分阶段，最终范围不缩减为单个场景。

### 明确不实现

不建立产品回退存档，不提供回退或局部撤销入口；不新增独立执行代理、通用代码教学系统、第二套审批计划、跨宿主适配产品或独立自动化验收平台。宿主安装脚本的配置备份属于安装安全措施，不是业务项目恢复功能。

### 两条独立工作链

**解释链：** 观察主线 → 整理变化 → 读取有效依据 → 生成解释 → 更新侧栏。只读分析不占用主对话输入，不调用开发工具，不等待用户阅读。

**修改链：** 用户输入 → 判断表达性质 → 保存明确要求 → 交给目标主会话 → 核实接收 → 跟踪执行和检查。只有这条链可以产生主会话新任务。

两条链共享项目事实和身份校验，但使用独立任务、取消信号与队列。解释失败、侧栏关闭或重新生成解释，均不能停止主 AI 的开发任务。共享模型额度仍可能造成资源竞争，需要限流。

# 03 技术选型与宿主接入

| 层次 | 本版选型 | 原因与约束 |
|---|---|---|
| 服务端 | TypeScript、Node.js ESM、Cordis 插件 | 复用现有代码；沿用宿主服务和依赖注入 |
| 界面 | React／TSX 客户端插件，挂载原生右侧栏 | 本机客户端实现使用 React；必须使用宿主兼容的模块加载方式 |
| 通信 | 宿主客户端与服务端桥接 | 复用会话身份；不另开无认证的本地 HTTP 服务 |
| 状态 | 现有 JSON Ledger + 新增项目内 `guide.json` | 课程规模下减少迁移；保留锁、版本、读回确认 |
| 模型 | 通过宿主已配置的模型服务发起独立调用 | 不向前端暴露密钥；不假设默认自动继承主会话模型 |
| 项目分析 | 本地文件索引、路径关系、任务与事件 | 不依赖向量数据库；按相关范围增量分析 |

开源接入路线见第 23-27 章：优先使用宿主接口，局部改造讲解与扫描能力；结构图首选验证 React Flow。所有候选仍需通过打包与真实宿主验证，不默认增加整套外部服务。

### 宿主当前证据

2026-10-26 对本机应用进行只读检查：安装版本为 **0.2.1-rc.2**。`dsh-client-ui-sidebar-right` 的客户端实现提供 `sidebarRightTabs`、`sidebarRight`，并使用 `ctx.slots`；会话控制实现具有 `prompt`、`requestId` 去重检查和 `followup`／`steer` 分支。

这些证明安装包内存在相关实现。第三方客户端打包、服务注入、正确会话绑定，以及跨重启去重等行为，仍需最小插件实测。不能仅凭包名、导出声明或官方示例宣称集成完成。

### 兼容策略

先锁定该宿主版本完成适配。当前项目开发依赖仍含 `0.1.0-rc.6` 的宿主类型包，不能用其编译通过证明桌面兼容。开发前统一适配器的类型与运行时来源，避免打包第二份宿主服务注册表或 React 运行时。更新宿主前重新执行兼容验证。

# 04 模块职责与生命周期

| 模块 | 主要职责 | 明确边界 |
|---|---|---|
| `HostAdapter` | 读取会话与事件、识别项目、投递主线消息、调用模型 | 宿主版本差异集中处理；不依靠界面点击模拟消息发送 |
| `GuideService` | 组织查询、追问、修改请求和订阅 | 每次校验项目／会话绑定；客户端不能指定任意目录 |
| `EventWorker` | 持久待处理记录、回放、去重、重试 | 不在主 AI 事件回调里执行模型推理 |
| `ProjectProjection` | 项目结构、变化、检查、任务状态的读模型 | 是可重建视图，不覆盖用户原始要求 |
| `ExplanationService` | 生成当前影响、取舍和问题解释 | 无代码写入、终端、部署或自主转交权限 |
| `IntentService`／`DeliveryWorker` | 区分追问与修改；可靠投递和对账 | 保留用户原文，不能靠模型“自行授权” |
| `ContextResolver` | 统一处理来源、适用性、失效依赖 | 主 AI 上下文与侧栏使用同一套有效性规则 |
| `GuidePanel` | 三个入口、阅读位置、问题输入和回执 | 展示状态，不自行推断执行成功 |

### 生命周期

**宿主级：** 注册服务和客户端入口，维护工作队列；卸载时释放监听与订阅。**项目级：** 按规范化目录建立状态空间，串行提交同一项目的状态变更。**会话级：** 绑定原生会话 ID、事件游标和当前目标；仅对启用 VibeGuide 的会话持续跟踪。**视图级：** 管理阅读位置、选中内容和问题流。

服务端统一负责投递，不能因同时打开两个面板而重复发送。跨进程使用持久租约与递增领取代号；旧工作者不能写回新租约的结果，发送租约过期后先对账再重领。后台工作者可以并行读取和生成，但写回必须经过项目锁及版本核对；不跨模型调用长期持锁。

主 AI 的沟通规则继续通过唯一 `vibeguide` preset 注入。客户端模块与服务端模块是技术分层，不在产品中增加第二个模式。

# 05 核心数据模型

以下为新增模型的关键字段；实际实现使用运行时 schema 校验，不只依赖 TypeScript 类型。

```ts
type Scope = {
  projectId: string; sessionId: string; taskId?: string;
};
type SourceRef = {
  sessionId: string; eventId: string; seq: number;
  contentHash: string; kind: 'user' | 'assistant' | 'tool';
};
type Basis = {
  requirementRevision: number; projectionRevision: number;
  files: Array<{ path: string; hash: string }>;
  sourceRefs: SourceRef[];
};
```

| 实体 | 关键字段／关系 | 用途 |
|---|---|---|
| `EventJob` | 会话、seq、事件 ID、处理器版本、状态、尝试次数 | 发现漏处理、重复事件和重启后的待处理工作 |
| `ChangeSet` | 事件范围、文件摘要、涉及模块、`Basis` | 将连续实现动作归为一次用户可理解的变化 |
| `ProjectNode/Edge` | 职责／关系、关联文件、来源、观察或推断标签 | 呈现项目结构与数据经过的部分 |
| `Explanation` | 变化、影响、取舍、限制、来源、`Basis`、版本 | 可追溯并能判断是否已过时的解释 |
| `Intent/Delivery` | 用户原文、明确范围、稳定请求 ID、接收记录 | 保存修改要求并区分发送与执行 |
| `LearningEntry` | 看过／问过、解释版本、关联主题、时间 | 记录真实交互，不推断掌握程度 |

### 原文与派生内容分开

`userStatement` 保存用户实际表达，`interpretedGoal` 是模型的候选理解，`technicalSuggestion` 是实现建议。三者不能压成一段并标为用户决定。

需求来源必须由服务端获取。侧栏原文先作为受认证的侧栏输入保存；送达主会话后关联原生消息 ID。未送达的记录仍是用户提出的要求，但不能显示“主 AI 已收到”。

# 06 持久化、隔离与一致性

### 沿用本地项目存储

项目标识继续由工作目录的 `realpath` 规范化结果计算摘要。默认沿用安装器配置的 `vibeguide-p0-state` 目录，旧名称不表示还存在第二种模式。

```text
<storageRoot>/
  personal/preferences.json          # 已有个人偏好
  <projectId>/
    project.json                    # 已有需求与任务
    workbench.json                  # 已有事实与检查
    receipts.json                   # 已有工具证据回执
    guide.json                      # 新增队列、投递与侧栏视图
```

`guide.json` 内保存 schemaVersion、revision、事件游标、待处理任务、发送记录、解释与结构视图。**新增工作流中需要原子提交的状态放在同一个 Ledger 内**，例如“收到侧栏输入”和“创建待发送记录”。原始宿主历史只保存引用和必要摘录，避免全量复制。

### 写入规则

继续使用独占锁、预期版本、临时文件替换、fsync 和读回确认。锁内只处理短事务。冲突时重读并重算；`unknown` 时先核对写入结果；失败不能声称“已记住”。

现有多个 Ledger 没有跨文件事务。写入旧需求库时采用稳定操作 ID：先保留待提交工作，再写目标文件，最后记录完成；崩溃后按记录 ID／内容摘要对账。现有短操作缓存不能替代持久发送去重记录。

### 容量与项目变化

现有通用 Ledger 上限为 8 MiB；ProjectStore 的项目记录上限为 4 MiB，且有条目数量限制。新增记录应设明确容量预算，归档已完成历史、保留检索索引；不得删除未完成发送和待处理任务以腾空间。达到上限时停止新增派生内容并显示记录异常，主线继续。

项目移动会改变目录身份，不能按相同名称自动合并。迁移必须核对旧项目身份；切换项目后不复用前一个项目的队列、解释或要求。

# 07 事件采集与后台处理

<div class="flow"><div>主线持久事件</div><span>→</span><div>待处理记录</div><span>→</span><div>变化与有效依据</div><span>→</span><div>解释／结构视图</div></div>

### 采集与回放

以宿主持久会话事件作为可恢复依据。实时流只用于“正在处理”等短暂状态，不写成最终结论。订阅回调只登记轻量唤醒，不等待模型；工作者从宿主历史按游标补读并先写入待处理记录。

去重键由 `sessionId + eventId/seq + processorVersion` 组成。维护“已登记游标”与“连续完成游标”，不能因后一个事件处理成功就跳过前面的失败事件。若宿主不能按游标查询，适配器读取受限历史并按稳定 ID 去重；无法覆盖缺口时显示跟踪不完整。

未决问题单独维护 `PendingChoice`：项目、会话、原生问题 ID、原文与选项、版本、待回答／已回答／已取消状态及可用来源坐标。字段映射以宿主验证结果为准；尚无持久 seq 时不伪造来源。读取和关联问题采用宿主状态与事件，不为此调用解释模型，也不等待 `turn/end`。问题被替换或会话切换时更新绑定；只有用户主动求助才进入选项解释链。

### 处理状态

| 状态 | 含义与恢复规则 |
|---|---|
| `pending` | 已登记，等待处理 |
| `processing` | 有工作者租约，记录到期时间；重启后可重新领取 |
| `processed` | 需要的持久记录已保存，或明确记录“无需变更”的理由 |
| `needs_clarification` | 意图含糊；不阻塞其他可独立处理的事件 |
| `failed` | 有错误类别和重试次数；可重试或等待用户处理外部条件 |

### 合并与背压

将同一任务内短时间连续文件操作合并为一个 `ChangeSet`，在产生重要变化的主线回复完成、重要检查返回或用户主动追问时触发解释。仅出现或更新澄清选项，不触发后台选项解释；不能因纯澄清回合结束绕过这一限制。起始合并窗口可设 800 ms，后台解释同时最多一个／项目；这是待测默认值。

只合并重复的派生解释工作，不能丢弃用户要求、检查结果和发送记录。全局模型并发受限；积压时先保障用户主动提问，再生成后台摘要。若历史无法读取，展示已有状态的截止时间，不能编造缺失过程。

# 08 项目结构与变化归纳

### 项目索引

首次接入已有项目时，读取目录、依赖清单、配置、入口和相关源文件，建立“页面／交互、业务处理、数据存储、外部服务”的职责视图。排除依赖、构建产物、二进制和敏感文件；默认限制文件数与总字节，超出时显示覆盖范围。

以相对路径和内容摘要做增量索引。优先分析当前任务相关文件；文件监听用于提示重新扫描，接入、任务结束、窗口恢复时重新核对，防止漏掉外部编辑。所有读取必须限制在当前工作区，符号链接不能绕过范围限制。

### 关系从哪里来

| 关系 | 实现依据 | 表达方式 |
|---|---|---|
| 页面引用组件、模块导入 | 确定性路径解析和依赖引用 | 已观察关系，保留出处 |
| 点击后保存到服务 | 代码调用、配置和执行证据组合 | 区分静态关联与已运行验证 |
| 某模块承担业务职责 | 代码／文档摘要与当前任务 | 模型归纳，允许用户纠正 |
| “这一改动会影响登录” | 依赖传播与需求关联 | 标为潜在影响，不能等同于已发生故障 |

不要求首版完成所有语言的 AST 分析。先支持课程示例使用的 Web 项目；其他语言使用目录、清单和只读摘要，明确降低关系精度。覆盖范围是实现约束，不减少三类使用场景。

### 面向用户的输出

项目图节点默认使用职责名称，如“每日问题页面”“回答保存”“账户与同步”。技术名可作为附加信息；文件列表和代码差异藏在证据详情中。

一个变化卡先表达“回答现在保存在当前浏览器”，再说明“换手机看不到”；仅在用户决策需要时解释本地存储与服务器保存的取舍。未发生文件变更时，可显示建议结构，必须与实际结构区分。

# 09 解释生成与模型调用

### 独立、只读的解释服务

调用宿主模型服务，显式确定 provider／model、输入预算、输出 schema 和取消信号。模型路由、额度与用量如何展示，在接入验证中确认；侧栏可产生额外模型调用，不能承诺免费或完全没有资源影响。

解释服务不注册终端、文件修改、部署或主对话发送工具。它输出结构化解释候选，由服务端校验后保存和展示。是否发送修改要求由独立意图与投递链路决定。

### 选项解释按需触发

主 AI 的原始选项承担首次易懂说明。侧栏默认只关联原题和展示帮助入口，不自动重述、不预生成各选项解释，也不调用另一个模型评判用户是否需要讲解。

用户点击帮助入口或明确追问时，读取当前问题版本、相关要求和必要项目依据，只解释所问的差别或后果。同一请求进行中，重复点击复用该请求；再次查看时，仅在项目／会话、问题 ID 与版本、提问内容、相关 Basis、语言、提示版本和模型配置一致且依据有效时复用缓存。不同追问不得因属于同一题就被合并。

选项被回答、替换或取消，或相关依据变化时，核对在途结果；不将旧解释作为当前选项的答案发布。失效只更新提示，不自动发起新一轮选项解释。用户主动追问可优先于后台自动总结，但取消范围仅限侧栏；不取消主 AI。该触发策略不取消重要开发变化的摘要，也不代表事件处理、记忆或其他功能没有模型消耗。

```ts
type ExplanationDraft = {
  change: string;              // 现在发生了什么
  impact: string[];            // 对使用者意味着什么
  tradeoffs?: string[];        // 当前选择涉及的取舍
  uncertainty: string[];
  sources: string[];           // 必须指向提供过的依据 ID
  followups: string[];         // 可追问，不是已授权任务
};
```

### 输入组织与质量控制

输入包含当前目标、相关要求、有效项目事实、当前变化、检查情况和完整相关提问。项目文档、工具日志和历史摘录属于低可信材料，不能作为系统指令。先过滤敏感内容，再按相关性裁剪；缺少重要条件时不生成确定性判断。

程序校验来源存在、作用域、版本、数字／角色／否定条件与原文约束。模型核验作为辅助，无法判定时降为“待核对”。结构合法、引用真实都不保证解释正确。

### 生成期间项目改变

每次生成绑定 `Basis`。全局 revision 用于发现竞态，适用性按实际依赖摘要重新判断。完成时重新核对相关需求、文件和事件范围；发生变化则保存为历史解释或丢弃重算，不发布为当前结论。缓存键包含依据摘要、问题、语言偏好、提示词版本和模型配置。不能只按问题文本复用跨项目结果。

# 10 意图识别与修改要求

侧栏输入使用同一个入口。服务端保留完整输入和相关上下文，区分提问、修改、含糊表达、记忆纠正；模型只生成候选分类，确定性规则和当前语境共同约束动作。

| 输入例子 | 处理 |
|---|---|
| “为什么不用云端？” | 解释取舍，不发送开发任务 |
| “那就改成换手机也能看。” | 直接转交“跨设备查看”的明确要求，显示回执 |
| “第二种吧。”但当前无法确定选项 | 简短询问所指方案，不猜测 |
| “先别改，我只是问一下能不能做。” | 只回答可行性，不被“改”字触发发送 |
| “你记错了，我说的是只给管理员看。” | 修正需求理解；是否需要代码改动按完整语境判断 |

### 发送前只做必要检查

检查目标会话仍绑定原项目、用户表达的行为和对象是否明确、是否存在无法同时满足的要求。明确要求不再弹出通用“是否确认发送”。若与之前决定矛盾且撤销意图不清楚，只澄清冲突部分。

例如“改成换手机也能看”足以成为主线任务；具体登录方式或服务选型仍可由主 AI 澄清，侧栏不能因此强制用户先补完技术方案。若用户同时说“不要任何网络连接”，则应先解释冲突。

### 主线消息内容

传递用户原话、必要上下文、所针对的解释／变化版本及请求 ID。辅助摘要显式标记为 VibeGuide 的理解；不得偷偷补入“使用某数据库”“同意付费”“批准部署”等决定。

发送后记录 `userStatement → nativeMessageId` 对应关系。自动建议、引用文本、模型自问自答和工具输出均不具备用户授权效力。混合提问与明确要求可分别处理，但含糊部分不能被默认扩展成开发范围。

# 11 发送回执与执行状态

### 先持久化，再投递

1. 保存用户原文与稳定 `requestId`，创建 `pending` 发送记录；保存失败则不开始发送。
2. 服务端工作者领取发送任务，核对会话绑定；默认使用宿主后续输入机制，不主动中断当前任务。
3. 根据宿主接收响应及原始事件核对送达状态，保存原生消息 ID／来源关联。
4. 观察后续主线事件，分别更新处理、变更与检查证据。进程崩溃后先对账再决定重试。

| 内部状态 | 用户看到的状态 | 判定依据 |
|---|---|---|
| `pending / dispatching` | 正在发送 | 本地记录已保存，接收尚未确认 |
| `accepted` | 已发送，等待主 AI 处理 | 宿主明确接受；忙碌时可显示已排队 |
| `unknown` | 发送结果待核实 | 响应丢失或超时；不当作明确失败 |
| `rejected` | 未发送成功 | 宿主明确拒绝，提供可重试原因 |
| 执行 `handling / blocked` | 正在处理／暂时无法继续 | 关联任务的事件或明确阻塞说明 |
| 执行 `completed` | 本次要求已完成 | 对应改动及适用检查／验收依据，无已知未满足项 |

送达、执行和验证是三个维度。例如可以同时是“已发送”“已有代码改动”“尚未验证效果”。主 AI 声称完成、工具退出码为零、用户看过结果，都不能单独生成最终完成状态。

### 去重和不确定结果

本机宿主源码包含按 `requestId` 检查日志及待处理消息的逻辑，但跨断线、重启和并发行为仍需实测。适配器复用同一请求 ID，发送重试不能生成新 ID。无法可靠对账时保留 `unknown`，阻止自动再次投递；清楚说明限制，不能承诺任意故障下严格恰好一次。

执行关联保留请求 ID 与任务 ID；主 AI 提供的任务关联只是候选，需对照原始事件、相关改动和检查。无法确认关联时保持待核实，不能将任意下一次成功归给该要求。

用户切换项目后，已有记录仍绑定原会话；不能跟随当前界面发送到新会话。取消尚未发送的请求需要工作者领取状态校验；已接受的任务不能假装通过删除记录撤销。

# 12 前后端接口契约

下面是 VibeGuide 自身的服务接口设计。传输层映射到宿主桥接能力，实际注册方式由接入验证确定；浏览器不直接操作文件或持有模型密钥。

| 接口 | 输入重点 | 返回／事件 |
|---|---|---|
| `getSnapshot` | 会话、可选已知 revision | 当前目标、结构、变化、检查、解释和回执 |
| `subscribe` | 会话、最后收到的事件序号 | 有序更新；缺口时要求刷新快照 |
| `ask` | 会话、问题、正在阅读的解释版本 | 解释流 ID；结束后给出完整解释及依据版本 |
| `submitInput` | 会话、原文、稳定 clientRequestId、阅读上下文 | 提问结果、澄清请求或发送记录 ID |
| `getDelivery` | 会话、发送记录 ID | 送达／执行／验证三个维度 |
| `correctRecord` | 记录 ID、用户原话、预期 revision | 已保存、冲突、待澄清或失败 |
| `markViewed` | 解释 ID／版本、交互类型 | 查看／追问历史，不产生掌握标签 |

```ts
type UpdateEnvelope<T> = {
  scope: Scope;
  streamSeq: number;
  stateRevision: number;
  type: 'snapshot' | 'change' | 'explanation' | 'delivery';
  payload: T;
};
```

### 服务端校验

由宿主会话元数据解析项目目录；不信任前端传来的路径或 projectId。每个请求验证会话可访问、记录属于该项目、请求 ID 没有绑定不同内容。重复请求返回已有结果；同 ID 不同内容返回冲突，不能静默覆盖。

错误需区分：会话不可用、项目绑定改变、版本冲突、记录忙碌、模型不可用、保存失败、发送未知、跟踪不完整。前端用可理解的话说明影响，原始诊断仅在详情中展示。

订阅采用“快照 + 后续序列”协议：先建立更新缓冲，再读取快照与基准序号，最后补齐之后的更新。断线发现序号缺口时重新取快照，不能假定漏掉的消息不重要。

# 13 侧栏状态与交互实现

### 三个入口共用同一份项目状态

| 入口 | 主要组件 | 状态来源 |
|---|---|---|
| 当前进展 | 当前目标、变化卡、影响、检查提示、追问与回执 | 任务、ChangeSet、Explanation、Delivery |
| 项目结构 | 职责图、关联高亮、数据经过路径、证据详情 | ProjectNode／Edge 与当前变化 |
| 了解过的 | 看过／问过的主题、历史解释、重新查看和纠正 | LearningEntry 与解释版本 |

前端保留 `activeSession`、`selectedTab`、`pinnedExplanationVersion`、`lastSeenRevision`、滚动位置和输入草稿；服务端保存事实与回执。不要把“这个面板正在显示什么”写成项目事实。

### 阅读时收到新进展

正在阅读的解释保持版本和滚动位置，顶部提示“有新的进展”。用户选择“回到最新”后切换。若当前解释依据失效，立即显示“依据已变化，以下为之前的说明”，但不直接替换正文。

主线继续运行时，侧栏问题可以独立返回；回答应标明针对的是用户正在阅读的版本还是最新状态。若两者不同，说明变化。取消某次解释请求，只取消侧栏生成，不发送主 AI 的停止命令。

### 切换、重连与关闭

切换会话时解除旧订阅、清理正在显示的项目数据，再载入新快照。所有流式片段携带作用域，过晚返回的旧项目结果不得出现在新项目中。重新打开恢复阅读位置，并重新核对依据是否仍适用。

关闭侧栏时停止非必要的后台解释生成；已登记的明确修改要求继续发送或对账。后台仍维护必要事件游标，重新打开时补充变化摘要。不能把关闭视为撤销任务或已理解内容。

### 入口与可达性

原生右侧栏注册一个 VibeGuide tab，内部呈现三个入口。保留键盘导航、文本选择、可读的加载／错误状态和无数据提示；不抢占主输入框，不把宿主原生问题卡搬到另一套审批界面。

# 14 证据、检查与失效传播

### 修复现有上下文缺口

当前 `evidenceStatus()` 能判断部分证据已过时，但 `currentFacts()` 不会据此过滤关联的 observed 事实。这会让“依据已失效”的观察继续进入上下文。应在新增侧栏前统一处理，避免把旧结论用更漂亮的界面再次展示。

新增 `ContextResolver`：读取来源 → 计算适用性 → 沿依赖关系传播 → 输出当前有效事实、历史事实和待核对项。主 AI 动态上下文、项目结构和侧栏解释都调用它，不能各自实现不同过滤规则。

```text
文件／需求／检查条件变化
  → 对应证据不再适用
  → 依赖该证据的观察标记 needs_review
  → 依赖观察的结构结论、摘要与解释标记过时
  → 重新检查或生成后，建立新版本与新依据
```

### 三类状态分开

| 维度 | 示例 | 规则 |
|---|---|---|
| 检查结果 | 通过／失败／无法判定 | 依据检查内容与原始结果，不只读退出码 |
| 证据适用性 | 当前适用／过时／需重新在线检查 | 依据相关文件、要求、配置及外部环境 |
| 用户要求 | 当前要求／被用户明确替代 | 代码偏离或检查失败不能删除要求 |

现有工具证据绑定机制可复用，但须检查其覆盖范围；没有检查准备记录的普通开发不能被误报成“已验证”。对外部服务，历史成功并不保证现在可用，应显示检查时间与限制。用户体验检查记录具体操作、观察结果及原生用户来源，只支撑其实际检查过的行为。

图关系的失效使用显式依赖 ID 做传递，处理环和重复节点。解释只绑定真正引用的依据；无关文件变化不应让全部知识变灰。依赖范围未知时保守标为待核对，并说明原因。

# 15 记忆、偏好与纠正

### 自动处理每条相关用户事件

工作者逐条登记、提取和核对，而不是完全依赖主 AI 记得调用保存工具。保留 `pending／processed／needs_clarification／failed`，在重新打开时补处理。多要求输入拆为可独立纠正的记录；每条记录关联原始事件与完整相关语境。

### 四层含义必须区分

| 层次 | 能说明什么 | 不能推出什么 |
|---|---|---|
| 来源校验通过 | 引文来自真实用户事件 | 摘要没有歪曲用户意思 |
| 语义核对通过 | 未发现数字、角色、否定、条件等冲突 | 模型理解永远正确 |
| 保存成功 | 记录可读回且版本匹配 | 主 AI 已执行或用户已验收 |
| 上下文注入 | 当前记录提供给模型 | 模型输出必然遵守记录 |

新增工作者与原有记录工具共用校验和写入入口；按源事件、原文片段位置及记录类型去重，保留多要求的独立编号，避免双重抽取。

原文是权威表达，摘要是辅助索引。约束核对使用完整相关原文，不能只信模型截取的短引文。无法可靠归纳时保留原文、标记待核对，不把不确定摘要写成确定要求；明显清楚的表达不重复请求确认。

### 偏好与“了解过的”

继续支持语言、详细程度、讲解方式、技术程度、工作方式。项目偏好覆盖个人偏好；“这个项目”不能被推广成全局。用户没有明确持续偏好时，不因一次追问就永久调整所有项目。

查看和提问记录只能说明发生过这些交互。可以减少重复讲解，并允许重新解释；不能显示“已经掌握数据库”，也不能把“用户看过方案”记录为同意。

### 纠正链路

记录保留 `replaces/supersedes` 关系；修正事实使相关解释重新核对。明确修改业务要求按第 10 章转交；“只纠正说明，先别改代码”仅修改记录。保存失败时保留可重试状态，并明确跨会话记录尚未更新。

</div>

### 技术上的关键判定

需求澄清由主 AI 的沟通规则和当前任务上下文负责。侧栏可解释原题，但不增加第二份问卷或逐步放行流程。具体小改动、已有明确要求的续做，不能被模板化重新访谈。

跨设备查看是用户目标；云端数据库、登录机制等是后续实现选择。转交消息不得将某个供应商或付费方案包装成用户已经同意。若主 AI 需要用户作出关键选择，仍在原生主对话中提出。

此场景验收需同时观察主线回答是否易懂、侧栏是否只是解释，以及修改原话是否准确到达同一会话。单独展示一段模拟侧栏对话不算完整验证。

# 16 三类场景：已有项目与卡住

### 接手已有项目

| 步骤 | 系统行为 | 用户感受到的价值 |
|---|---|---|
| 绑定项目 | 核对目录身份、历史和已有记录 | 不混入其他项目的要求 |
| 建立概览 | 受限索引，生成职责节点及依据 | 看懂页面、业务、保存和外部服务 |
| 提出修改 | 关联涉及的节点和当前要求 | 知道修改大致影响哪些部分 |
| 明确转交 | 发送原话和必要上下文 | 不必把自己的话翻译成技术任务 |
| 跟随实现 | 增量更新、证据校验、旧解释标记 | 看见真实变化，原阅读位置不被打断 |

接手时若历史缺失，只说明当前代码能观察到的状态；不能把代码推测成用户原来的要求。外部编辑造成变化但找不到对应主线事件时，标注“检测到文件变化，来源未确定”。

### 开发途中卡住

1. 主线错误、失败检查或用户描述进入事件上下文。
2. 读取相关结果、已有尝试和受影响功能，分别记录事实与可能原因。
3. 解释“谁／什么功能受到影响”“已试过什么”“还不知道什么”，给出少量可理解的处理选择。
4. 用户普通追问只得到解释；明确选择处理方向后，通过同一投递链路转交。
5. 主线修复后，旧错误保留为历史；重新检查前不显示已经解决。

### 禁止混淆的情况

“可能是网络问题”不能变成确定诊断；重复出现的日志不能直接等同于同一个故障；用户说“为什么又失败了”不能被当成“允许换技术栈重写”。要求明确而实现细节尚未定时，交由主 AI 继续处理，不让侧栏变成额外的技术门槛。

两类场景与从零开发共享模块和数据模型。无需用户切换另一个模式，项目发展阶段改变时自然衔接。

# 17 异常处理与性能预算

| 情况 | 系统处理 | 用户反馈 |
|---|---|---|
| 模型不可用／超时 | 终止本次解释，保留有效快照；有限重试 | 说明解释暂未生成，主线继续 |
| 记录忙碌／冲突 | 释放锁，重读后重算；超限保留待处理 | 说明记录尚未更新，不假称保存成功 |
| 事件缺口／无法回放 | 标记跟踪不完整，尝试补读 | 显示数据截止时间和缺口 |
| 发送超时 | 保留 unknown，按请求 ID 对账 | 显示待核实，不自动重复发送 |
| 会话被删除／项目改变 | 停止向无效目标发送 | 要求在有效主会话继续，不擅自换目标 |
| 磁盘满／容量到达上限 | 停止新增记录，保留原文件 | 明确未保存；不影响宿主原有历史 |
| 解释返回时依据已变 | 不发布为当前解释，标记历史或重算 | 提醒已有新变化 |

### 起始工程预算

以下是待测的初始目标，不是已有性能结果：事件监听回调不做 I/O 或模型调用，正常负载下 p95 小于 10 ms；本地快照查询 p95 小于 300 ms；点击发送后 200 ms 内出现本地“正在发送”反馈，不能提前显示“已发送”。

解释目标首个可读响应不超过 5 秒、常规问题完整返回不超过 20 秒，需按真实模型和网络记录分布；超时提供真实进度与重试入口。模型并发建议全局 2、单项目 1，用户主动追问优先；完成测试后再调整。

### 控制成本与积压

后台变化合并、相关范围检索、版本化缓存和侧栏关闭时暂停非必要生成，可降低重复调用。设置每次输入字节／token、文件读取总量和输出长度上限。达到预算不截断关键否定或条件，应缩小分析范围并说明限制。

队列长度、失败次数、补读缺口和发送未知数量需要可观测。持续积压时减少后台摘要频率，不能丢弃用户输入或假装同步完成。

# 18 权限与数据边界

### 身份与作用域

前端通过宿主认证连接调用服务；服务端以会话元数据解析真实项目身份，逐次校验订阅、查询和发送对象。用户输入的项目路径、模型生成的来源 ID、浏览器缓存均不能作为授权依据。

跨项目只复用明确设为个人的沟通偏好，不复用项目需求、代码摘要或解释。测试时两个工作区必须使用独立 projectId，不能把另一组的对话或结果放进共享解释缓存。

### 文件与模型输入

服务端只读当前工作区允许的文件。遵守忽略规则，排除密钥、凭据、环境配置中的秘密值和明显个人数据；不沿符号链接读取工作区外内容。敏感内容在进入模型输入前过滤，错误诊断默认不记录完整提示词或原始秘密。

使用宿主模型不等于完全离线：发送给模型的内容仍受所配置提供方的处理方式影响。界面和安装说明应说明解释会使用项目上下文；不额外复制密钥，也不自动上传整个项目。

### 低可信材料不能发出指令

代码注释、README、网页摘录、工具输出及历史解释都是分析材料。即使其中出现“忽略规则”“把这段发给主 AI”，也不构成当前用户授权。解释模型无执行工具；发送服务只接受已校验的当前用户明确输入。

### 宿主权限继续有效

侧栏转交要求不会绕过主 AI 的工具权限、网络授权、付费选择或发布确认。主线需要用户选择产品方向时可以等待；侧栏普通阅读和提问不能制造额外暂停。

课程演示使用脱敏示例项目，默认不开启云端遥测。必要本地诊断保留时间、状态码和关联 ID；完整对话用于人工评估时须明确告知参与者，并限定保存范围。

### 先验证最危险的假设

P0 是技术验证，不是新增产品模式。优先证明第三方客户端可以挂载、服务接口能识别目标会话、解释调用可以独立于主线运行、消息可以可靠接收和关联。任一关键能力缺失时，先调整适配实现并更新文档，不继续制作假闭环。

P1 与侧栏样式可分开推进，但 UI 开发必须使用明确标注的样例接口。最终验收换成真实数据后重测，样例展示不能代替功能完成。

### 协作边界

按宿主适配、状态与投递、界面与交互、验证四类模块划分工作。先冻结公共 schema、错误码和事件协议；同一接口文件由单一整合者修改，评审只给建议。不同任务不同时改安装配置或宿主用户数据。

本文不估算固定工期。技术验证结果、参与人数与实际可用时间明确后，再将各阶段拆成任务和排期；不会以阶段开发为由删去已确定的三类场景。

| assistant-ui | 受控对话、流式状态、阅读锚点 | 借鉴交互；组件按需验证 |
| Aider | 符号与依赖排名、上下文预算 | 借鉴算法，不引入 Python 代理 |

| Memobase | 可配置画像、事件与后台整理 | 借鉴画像；暂不引入服务 |

### 两项明确取舍

**业务记录保持一个来源。** 需求仍由 continuity 管理，事实与证据仍由 workbench 管理，新队列与投递由 guide 管理。外部记忆工具不能再维护一套可独立改写的需求。

# 24 宿主与独立讲解的接入

### HostAdapter 直接接宿主

官方 [files 侧栏实现](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/client/ui-sidebar-files/src/client/index.ts)采用“类型注册 + keyed slot 内容注册”，并清理插件生命周期。VibeGuide 参考这一结构注册独立 Tab，内部承载三个入口；不复制 dockkit 或第二份 React。服务端从宿主会话确认 projectId，不接受前端自报路径作为权限。

官方 [消息实现](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/api/session-controller/src/commands.ts)检查 requestId 对应的 inbox／用户事件 rpcId，并区分 followup 与 steer。普通明确修改优先使用 followup；收到 accepted 只更新接收状态，不能显示执行完成。持久 outbox、超时对账和执行关联仍由我们实现。

本轮所读上游侧栏包为 **0.2.1-rc.3**；本文既有本机基线为 **0.2.1-rc.2**。新增源码证据不替代该基线实测，也不构成升级要求。先核对实际安装版本，再验证打包、服务注入及重启后的投递去重。

### ExplanationService 改造 dsh-explain

参考其 [来源观察器](https://github.com/yuezengwu/dsh-explain/blob/15504c26fe018008208c9975228763a4b523edaa/src/observer.ts)、独立模型调用与预算控制，集中封装为 VibeGuide 内部适配器。其会话视图、全局学习记录和复习机制不直接进入产品。

| 上游机制 | VibeGuide 必须增加或调整 |
|---|---|
| 完成回合的来源材料 | 绑定事件 seq、真实消息 ID、projectId 和 Basis；另建未决问题读取通道，用户求助才解释；另处理外部文件变化 |
| 自动候选“保留最新” | 原始事件先持久化；仅可重建的解释任务允许合并，用户输入不得丢弃 |
| 全局学习上下文 | 项目级上下文；个人偏好必须明确授权为跨项目 |
| 独立生成与取消 | 独立 requestId／AbortSignal；取消不调用主会话停止接口 |
| 生成解释 | 输出变化、影响、取舍和限制；结束时重新核对 Basis |

其 [候选队列](https://github.com/yuezengwu/dsh-explain/blob/15504c26fe018008208c9975228763a4b523edaa/src/queue.ts)使用内存 Map，不替代 EventWorker 的持久队列。仓库 main 与 v0.3.1 标签的兼容范围也不同，实际改造锁定完整提交，不仅记录包内版本号。

# 25 侧栏组件与项目结构

### 事实提取与显示分开

`ProjectScanner → ProjectProjection → ContextResolver → StructureView`。扫描可改编 Memmy 的[稳定读取与清单解析](https://github.com/MemTensor/memmy-agent/blob/74b26fc78ebd14a784981ba8e83bebf878c20865/Memory/src/service/project-environment/manifest-parsers.ts)，保留文件路径与哈希；去掉默认运行时命令探测。借鉴 Aider 的[符号排名与预算选择](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py)，优先读取当前问题相关的文件。

清单和语法解析提供技术事实，模型补充业务职责候选。不能从“存在数据库依赖”推出“已经实现跨设备同步”。缓存按 projectId、内容哈希和解析器版本失效，不能只检查 mtime。初版语言覆盖与未解析范围须明确显示。

### React Flow 的只读结构图

使用稳定 nodeId／edgeId，节点包含业务名称、职责、来源、观察或推断标签；图只消费有效投影，不写业务记录。[组件 API](https://github.com/xyflow/xyflow/blob/bb63f4cc345acf4e6c73e0371be3ea3ca01b2a18/packages/react/src/types/component-props.ts)支持选择与交互开关，接入时应：

- 禁止拖拽编辑、连线、重连与删除；校验节点级配置也不能重新开启编辑。
- 保留点击、键盘选择和缩放，并提供等价的职责清单。点击节点调用解释查询，不触发修改。
- 新变化只更新相关节点，不自动重置布局或 fitView；来源过时的节点显示待核对。

参考 Archify 的[来源绑定](https://github.com/tt-a1i/archify/blob/81c6be8d87090670c45d08a8f97f9d29c5af0bec/archify/renderers/shared/repository-evidence.mjs)和讲解高亮。图上可达仅表示已有关系的可达；影响分析仍需证据，不把图形遍历当作运行时验证。

### 对话组件保持受控

assistant-ui 的 [ExternalStoreAdapter](https://github.com/assistant-ui/assistant-ui/blob/7beac6fc271435b8c60e842a8e5ba327725d25e2/packages/core/src/runtimes/external-store/external-store-adapter.ts)可连接外部消息状态。先借鉴阅读锚点和流式状态，再评估是否引入最小组件。`onNew` 只能交给 GuideService；`onCancel` 只取消解释。禁用前端工具执行，不创建第二份主会话历史。

不论是否引入该库，都保留“正在读旧内容时不滚动、新变化仅提示、输入草稿不丢”的约束。其前端队列不能替代持久发送记录；云服务不作为前置依赖。

# 26 记忆、解释与修改记录

### ContextResolver 借鉴分层读取

参考 Mnemon 的[三层策略](https://github.com/omdsh-dev/dsh-mnemon/blob/5a890e2c2ceb395b4aeb61f2ee60ceffb1136608/plugins/dsh-mnemon-strategy-default-three-tier/src/strategy.ts)：有效的当前要求和少量偏好常驻；项目文档、历史解释及证据按问题读取。所有层使用统一预算、来源和适用性规则，检索相关性不能提高材料的权威性。

Mnemon 支持工作区存储，但默认配置为 global；不能直接照搬到双项目测试。其自动记录指引也不保证每条用户事件被处理。仍由我们的持久 EventWorker 追踪处理结果，保留原文、语义核对和纠正关系。

界面可展示“本次参考了哪些要求”，并让用户纠正。若以后接入 Mnemon Source SDK，先做只读适配；写入仍通过 VibeGuide 的业务校验，不允许两边独立改写要求。

### 画像只服务沟通

参考 Memobase 的[受限画像配置](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/src/server/api/example_config/only_strict_profile/config.yaml)，仅保留语言、解释深度、先讲影响等字段。其默认提取允许隐含推断，不直接用于需求或知识掌握；本版不增加 Postgres／Redis 服务。

Techie 的[解释结构](https://github.com/dhpwd/techie/blob/ffb92c7b6b58e69d9dec0fca9cd462020ea48110/skills/explain/SKILL.md)适合改写为“发生什么 → 对你意味着什么 → 可以怎样处理”。保留不确定性、来源和验证限制，技术名词只在帮助判断时出现。

### 变更记录与转交保持闭环

借鉴 OpenSpec 的[行为规格与设计分离](https://github.com/Fission-AI/OpenSpec/blob/6d04a1b58dedc95729d34e4f223d9d483aae210a/schemas/spec-driven/schema.yaml)，将原话、要求、实现建议、ChangeSet 和检查关联。用户无需填写规格文档或经过第二份审批。

| 用户输入／系统结果 | 必须发生的行为 |
|---|---|
| “为什么不用云端？” | 仅解释，不记成选择、不投递修改 |
| “改成换手机也能看” | 保存目标原话并转交，不夹带已选供应商或付费授权 |
| “只改说明，先别改代码” | 仅纠正说明及相关记录 |
| accepted／存在任务记录 | 只证明已接收或已有记录；完成与验证另取证据 |

任何候选都不能替代：意图判断、语义保真、持久 outbox、接收对账和证据失效传播。这些仍是第 10、11、14 章的自有实现职责。

# 27 引入顺序、验证与维护

### 依赖进入正式代码的条件

调研对象不自动成为依赖。每项先在隔离样例中验证最小路径，通过后再引入对应模块。不得借复用增加模式、恢复入口、知识测试或跨宿主产品范围。

| 阶段／候选 | 最小验证 | 不通过时的处理 |
|---|---|---|
| P0 官方宿主 + dsh-explain 模式 | 原生 Tab、同会话接收、独立调用、关闭与卸载 | 调整 HostAdapter；核心接入仍标未完成 |
| P1 自有状态 + Mnemon 方法 | 双项目隔离、重启回放、来源与语义、旧证据失效 | 修复状态层，不换记忆库掩盖问题 |
| P2 讲解 + Memmy 扫描 | 三类场景的有效事实、受限读取、明确修改回执 | 缩小单次读取范围并展示覆盖限制 |
| P3 React Flow／可选 assistant-ui | 窄栏、键盘、固定阅读、单份 React、资源加载 | 同契约改用 SVG 或自有受控组件 |
| P4-P5 已采用模块 | 双击、超时、接收后崩溃、旧流晚到、真实用户试用 | 修复并复测，不提前宣布完成 |

### 接入时保存的工程记录

每次引入记录上游完整提交、实际发布包及完整性摘要、复用文件、修改点、许可、传递依赖、目标宿主与实际结果。对宿主包使用其兼容加载方式，避免捆绑另一份服务注册表或 React。固定版本升级时重新执行相关集成用例。

直接复制或改编的文件保留归属和变更说明；第三方声明仅列真正分发的内容。MIT／Apache 项目仍需遵守对应通知要求。Archify 主体现为 Apache-2.0，历史 MIT 和单独 Harness 适配器有例外，不能把 LICENSE-MIT 当作整个当前仓库的任选许可。

### 维护边界

上游类型只进入适配边界；业务层继续使用第 5、12 章的自有 schema。先实现本地 JSON Ledger，不因上游用 SQLite 就迁移，也不默认新增 Memobase 服务、Memmy 运行系统或完整 OpenSpec CLI。

**验证结果分别记录：** 静态源码支持什么、样例运行证明什么、真实宿主完成什么、用户试用改善什么。没有执行的测试标为未执行；README 的作者测试结果不能写作本项目通过。

完整固定来源与逐项目分析见 [开源复用调研与接入依据](OPEN_SOURCE_REUSE_RESEARCH_2026_10_26.md)。本次文档修改只确定接入路线，依赖清单和正式插件代码保持原状。
