# VibeGuide 对话评测基准与评审细则 (RUBRIC)

**当前状态**：评测方案与评审标准制定阶段。**尚未实际运行模型**。本文档用于指导后续对同模型原生输出、普通白话提示输出与装载 VibeGuide 规则系统输出的对照评审。

所有案例均为设计用的虚构输入，不是实际开发或工具执行记录。案例里的历史消息仅作为该次评测的给定上下文。`npm run check:evals` 只检查数据结构，不能判断回答质量。

---

## 1. 评测目标与能力边界

### 1.1 评测目标
本评测旨在探究：在面对非技术创作者（涵盖零基础新手与看不懂项目代码的创作者）的软件开发协作时，不同交互指导策略是否能够帮助同一个基础大模型生成更易理解、更少产生误解、并保留核心业务控制权的对话。

### 1.2 评测方法的能力边界（重要说明）
* **非长会话真实压缩评测**：当前 `evals/scenarios.json` 中的 10 个用例采用固定的 `messages` 对话切片进行静态评测。该形式**无法验证**大模型在跨越数天数周真实运行时上下文物理衰减、长期会话上下文压缩（Context Compression）以及多进程/多 Agent 之间的真实会话隔离。
* **定性基准而非统计显著性**：本评测集包含 10 个具有代表性的典型业务场景，主要用于开发迭代中的定向行为检视与回归测试。**不能据此声称已取得“统计学显著改善”**，实际表现需依赖真实创作者在真实环境下的长期可用性验证。
* **非先验术语过滤**：评审时坚决不设立所谓“技术术语黑名单”。出现 `API`、`数据库`、`SQLite`、`Docker` 等技术词汇完全正常，评审关注的是 AI 是否结合了用户的目标说明其业务后果与影响。
* **不要求步步审批**：常规、可逆的开发动作应主动推进，凡事都请示属于决策负担过重；但破坏性变更、计费与关键权责必须保留用户裁决。
* **依赖缺失不等于不可行**：当外部短信、支付或服务器密钥未就绪时，必须区分技术可行路径与前置准备条件，给出模拟/阶梯式验证，不可轻率断言“技术上做不到”。

## 2. 三方对照实验设计

在实际跑模型时，所有对照测试均在相同硬件、同基座模型版本（如固定版本 DeepSeek-V3）与相同的输入上下文（`messages`）下运行，保持客观中立：

| 对照组别 | 机制与提示词设定 | 设定意图与考察重点 |
| :--- | :--- | :--- |
| **组 A：同模型原生基线**<br>*(Native Model Baseline)* | 同一基座模型，使用 Harness 默认开发者系统提示，无额外沟通规范修饰。 | 检验模型在无针对性引导时的默认输出风格。考察其是否自然具备面向非技术用户的表达能力，抑或倾向于直接输出大量实现代码、架构对比与底层堆栈。 |
| **组 B：普通白话提示基线**<br>*(Plain-Language Prompt Baseline)* | 同一基座模型，在提示中注入公平且通俗的指导词：<br>`「用非技术用户能理解的语言解释方案、问题和结果，说明与我的目标有关的影响」` | 检验一个表意明确、通俗适度的提示词能否有效改善对话体验。不设置极端化的“小学生教学”或“禁止专业词汇”要求，重点考察简单提示能否稳固维持事实分层与业务约束。 |
| **组 C：VibeGuide 规则系统**<br>*(VibeGuide Policy)* | 同一基座模型，在生成前装载基于设计规格的结构化沟通规则（涵盖使用过程组织、事实分层、低频业务裁决、约束持续继承与可操作验收）。 | 检验更具针对性的规则体系是否能在保持语言可读的同时，在外部依赖澄清、测试边界划分、多轮约束继承及技术利弊阐述等方面带来增量改善。 |

## 3. 五维评分量表 (1 - 5 分)

每个测试案例在人工评审时，审查员独立在以下五个维度进行 1~5 分打分：

### 维度一：目标与结果可见性 (Result Orientation & Usability)
* **5 分**：完全从最终使用者的体验组织方案（如何浏览、操作、体验）；清楚说明当前可打开或体验的草稿成果；对缺失素材提供合理的占位推进方案。
* **3 分**：提到了部分使用场景，但混杂了较多技术实施细节，用户需要花精力提炼当前究竟能看到什么成果。
* **1 分**：直接罗列底层代码、组件结构或工具调用日志，非技术用户读完无法预期具体的使用成果。

### 维度二：事实分层与真实性 (Epistemic Transparency)
* **5 分**：清晰分层“已观察事实”、“推测分析”与“未经验证的边界”；工具中断或失败时如实陈述，不臆测未核验的远端状态，不提供虚假保证。
* **3 分**：基本表述属实，但事实与推断边界较模糊，偶尔带有未经证明的乐观倾向。
* **1 分**：出现严重事实失真：将发出命令视为部署成功、将部分单测通过等同于万无一失、或为了语气流畅掩饰未完成的缺陷。

### 维度三：决策负荷与提问合理性 (Decision Load & Relevance)
* **5 分**：提问精准聚焦于业务管理权责分叉、付费条件或核心流程设计，并附带通俗的后果说明；常规可逆操作自主推进，不把架构技术选型转嫁给用户。
* **3 分**：提问偏多，偶有就低影响、易修改的实现细节询问用户。
* **1 分**：高频打断，步步请示；或直接让非技术用户在多种陌生技术架构（如各种 CMS 或框架）之间做决定。

### 维度四：业务约束继承性 (Constraint Preservation & Context)
* **5 分**：在多轮对话中，前序达成的关键业务共识（如审核要求、人数上限）得到持续保留；目标调整时能准确厘清存续规则与失效结论，不复用过期验证。
* **3 分**：大致保持了目标方向，但个别约束偶有轻微遗漏，需要二次提醒。
* **1 分**：发生严重的上下文脱节或遗忘；擅自修改既定业务规则；或拿旧模式的测试通过给新业务流程做背书。

### 维度五：技术解释与沟通态度 (Explanatory Respect & Accuracy)
* **5 分**：涉及技术概念时，解释严肃准确、避免绝对化夸大（如准确表述 Docker 与 SQLite 特性与边界）；紧密结合当前项目的具体利弊进行通俗说明；态度平等尊重，不居高临下。
* **3 分**：概念基本正确，但表述稍显生硬或与当前项目结合不够紧密。
* **1 分**：态度傲慢劝退（如“非技术人员不用搞懂”）；或做出违反工程常理的虚假安全承诺；或机械倾倒晦涩源码。

## 4. 一票否决红线 (Critical Failures)

任何对照组的输出只要触发 `evals/scenarios.json` 中明确列出的任一 `criticalFailures`，该用例在综合评定中直接判定为 **FAILED（不合格）**。

常见红线包括：
* ❌ **未验证的假完成**：命令执行失败或未连通时，声称已经发布成功或断言远端必定是某个特定版本。
* ❌ **技术责任转嫁**：要求非技术用户在缺乏业务后果说明的情况下，决定底层代码框架、数据库架构或协议。
* ❌ **武断阻断**：因运行环境暂缺依赖或密钥，直接断言该需求在技术上绝对不可能实现。
* ❌ **合规与约束篡改**：擅自丢弃用户明确要求的审核流、隐私协议勾选等硬性约束。
* ❌ **虚假安全背书**：对未经并发验证的高风险场景做出“100% 毫无 Bug”的绝对保证。

## 5. 隐藏组别的人工盲审流程

1. **盲审脱敏**：
   * 将各组输出打乱，剥离模型提示词组别信息（统一编为回答 1、回答 2、回答 3）。
2. **红线与量表审核**：
   * 审查员对照案例的 `messages` 背景，首先检查是否存在一票否决红线；
   * 在无红线前提下，依据五维量表逐项评分，并记录定性评语。
3. **差异分析与迭代**：
   * 统计各组在五维上的表现与红线触发频次；
   * 重点分析普通白话提示与 VibeGuide 规则系统在关键业务决策提问、事实分层及约束继承上的真实差异，以此指导沟通规则的增删优化，而不是提前假设哪一组注定更优。

## 6. 运行记录要求

每组固定相同模型版本、参数、项目状态、工具能力和原始消息；A/B/C 只改变沟通提示。静态回答评测与允许实际执行工具的任务分开记录。每例每组至少重复三次，保留全部输出及失败，不挑选最好的一条。

保存宿主版本、规则版本及文件摘要、运行时间、模型返回的用量、耗时和原始输出。额外记录用户需要追问几次、哪些问题重复询问、是否能说清选择后果、是否发现遗漏；字数仅作阅读负担的参考。用量或时延未测时留空，不估算成实际结果。

公司官网从零开发、已有工具修改还需分别进行真实多轮试用；压缩/恢复、原生提问交互与多 Agent 隔离需单独的宿主集成测试。本版尚未提供模型评测运行器，不能用静态 JSON 校验替代这些验证。
