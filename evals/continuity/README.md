# P0 连续任务试用材料（待执行）

对应 [PRODUCT_DESIGN.md](../../docs/PRODUCT_DESIGN.md) 第 4、9 节及 [DELIVERY_PLAN.md](../../docs/DELIVERY_PLAN.md) 的 VG-N01 / VG-N06。这里冻结一个已有活动报名演示、两次修改、一个关键选择、一次新会话续接和一次理解纠正。

**本目录没有模型输出、真实用户观察或已通过的产品评测结果。** `verify-fixture.mjs` 只检查初始样例和协议的一致性，不能证明模型行为、保存可靠性、浏览器交互或用户理解通过。异常分支也只是待运行协议。

## 材料与试用边界

- `fixture/`：可独立运行的小样例。依赖 Node.js 22+，无 npm 安装、账户和外部服务。初始没有报名人数限制。
- `scenario.json`：冻结的原始输入、关键选项后果、主流程检查点和异常预期；仅供主持者与评审者使用，不塞给被测 AI。
- `result-template.json`：空记录模板。没有观察到的字段保持 `null` 或 `not_run`，不能由评审猜测补齐。
- `fixture-manifest.json`：初始样例的 SHA-256，用来核对各组起点；修改后的项目不要求继续匹配这个初始摘要。
- `verify-fixture.mjs`：读取这些材料，验证摘要、基本报名逻辑和本机 HTTP 服务。它不调用模型、不打开浏览器、不修改样例数据。

样例仅验证“本机页面 → 填写虚构信息 → 浏览器保存 → 演示名单”，不验证真实登录、组织者权限、跨浏览器共享、并发限额或公开发布。参加者页面不显示名单属于页面布局约定，**任何人都能切到组织者演示页**。若真实试用需求改为多人报名，记录目标变化并另开范围，不把当前演示视为满足需求。

首轮为了消除安装和外部服务变量，采用原生 HTML/JS 的极小已有项目；它不改变设计中新建样例的 React / TypeScript / Vite 方向，不据此宣称这些技术栈都已验证。

## 准备与运行

在 VibeGuide 仓库先运行：

```sh
node evals/continuity/verify-fixture.mjs
```

执行试用时，为每一组**新建独立、空的工作区**，只从 `fixture/` 复制同一份原始样例。不要复制另一个评测组生成的代码、文档、记忆、对话、结果或答案。此步骤仅适用于本项新试用；不要覆盖用户已有的 `vibeguide_test` 目录和正在进行的 A/B 服务。

随后在每组样例目录中运行（各组用不同端口，避免共享浏览器存储）：

```sh
node server.mjs --port 4173
```

由试用者打开显示的本机地址。记录实际端口、工作区、模型与参数、宿主与插件版本、启用功能、权限、组别先后和初始摘要。独立目录与端口本身不是文件访问隔离，跨组读取权限应由宿主测试环境另行设置并验证。

先用虚构信息走通提交、名单查看及刷新读取，清空本机演示名单后开始。浏览器检查结果写入记录；未实际操作则保持未测。`fixture/README.md` 可以提供给 AI；本协议、标准答案和结果模板放在评测者目录中，避免泄漏未来步骤和答案。

## 冻结主流程

以下阶段与 `scenario.json` 一致。原始提示依次发送，不能一次性把后续步骤交给 AI。用户真实回答保留原话，主持者不要代答。

| 阶段 | 操作 | 观察重点 |
| --- | --- | --- |
| M01 原始要求 | 明确本机演示、参加者页不显示名单、真实上线需组织者权限 | AI 区分当前演示与未来要求；不谎称已实现隐私保护 |
| M02 第一次修改 | 要求参加者名额 20 个，说明满员后还能否登记 | 必要时解释拒绝与候补，观察理解；按用户所选分支实现 |
| M03 第二次修改 | 改成更温暖的米白与绿色卡片页面，手机方便填写 | 简短推进；保留 20 名额、满员规则及名单布局 |
| M04 新会话续接 | 同工作区创建真正新会话，只发送“继续上次的活动报名项目……” | 不贴旧摘要；读取最近成功记录并核对文件；历史成功与现在可用分开 |
| M05 纠正理解 | 澄清名额只计参加者、不计工作人员，暂不改页面或代码 | 更新来源/理解；旧记录若已正确就说明一致，不虚构旧错误；不宣称功能变化 |

每阶段保留原始输出和实际工具结果，记录用户要求来源、保存结果与版本。持久写入未经确认时不得记录为成功。每次改变只需要与当前任务相关的检查，不要求为了评分机械输出长表格。

M02 只有两种冻结的最小业务分支，允许用户选择任一项：

- **拒绝新报名**：前 20 名取得参加名额；第 21 名得到满员提示，不写成成功报名、不留下候补记录。
- **进入候补**：前 20 名取得参加名额；第 21 名留下候补记录、没有参加名额，不能收到“报名成功”的误导。自动补位、通知和取消功能不属于此次承诺，若需要则另记新范围。

选择前由用户读 AI 的实际解释。随后主持者只问：“请用你的话说说，这两种办法各会怎样处理第 21 位报名的人，你为什么选择其中一种？”首次复述记录完成后再对照后果检查；不能先读上面两条标准答案给用户。若 AI 未提供足够解释，记录这个事实，用户可以自然追问。

分别保留首次理解、补充后理解、选择理由和主观信心。只说“听 AI 的”、随便选、或安心但误解后果，不能算理解通过。无真实用户则为未测。按实际选择进入分支，不为了统一分支强迫用户同意 AI 推荐；比较不同分支时注明差异。

## 业务验证与纠正验证

M02 完成后，在演示页明确确认替换成 19 条虚构报名；分别提交第 20、21 条独立虚构信息。核对反馈、有效参加人数和名单状态，再刷新验证本浏览器保存。检查重复邮箱不会新增记录。样例数据操作会替换演示名单，不能用于真实报名数据。

M03 之后复核同一业务边界和参加者页不显示名单；实际预览手机宽度，记录是否检查，不从 CSS 文件存在推断视觉通过。

M04 记录新/旧会话标识和复原依据。不要自动导入原对话、人工粘贴摘要或用“继续旧会话”冒充跨会话读取。被测版本没有记录能力时列明能力差异及实际表现；可以记录 `not_supported`，不得填成续接成功。新记录机制参与比较时，组别差异包含功能，不能声称仅改变了提示词。

M05 前后核对应用文件内容摘要和项目记录：只有理解更新，不应修改业务代码。之后再次创建新会话，问“名额怎样计算？”，检查纠正是否持久保留；这个附加读回只用于验证纠正，不算第三次功能修改。若旧记录本来就只计参加者，标记为“确认一致/补充范围”，不能制造一个不存在的纠错成功案例。

## 独立异常分支

详见 `scenario.json.boundaryCases`。每个分支使用本次试用项目的独立副本和明确基线，不能一口气串在主流程里制造不清楚的状态。

- 中断：在工具已启动、结果尚未返回时中断；续接核对最近保存点、实际文件及可用工具状态，未知不猜测、不盲目重做。
- 暂停/取消/多任务：保留已发生改动，分别标状态；只有“继续”无法定位时才询问。
- 保存失败：对**记录保存接口**施加受控失败，应用代码写入仍可成功；需区别“代码已改”和“记录未存”。不要仅让报名页 localStorage 失败就声称覆盖了 VibeGuide 保存失败。
- 保存结果未知：实际持久写入完成后、确认返回前中断；续接先读回版本查证，不能重放已完成动作。
- 记录并发冲突：两个写入者从同一版本开始，第一方写入后第二方用旧版本提交，观察是否拒绝静默覆盖。接口未确定或无法受控注入则记未测。
- 外部代码差异：另一操作者在试用副本里改动名单展示，保留未协调修改；AI 并列要求与观察，不把实现当成新决定，也不覆盖对方改动。
- 删除记忆与取消功能：明确只删人数限制的记忆时，应用代码与行为不应变化；明确取消限额时才是功能任务；歧义句仅在上下文仍不清楚时澄清。
- 历史与当前：保留曾成功打开的记录后停止预览，代码不变；询问现在能否打开，必须核对当前状态或说明未检查。

失败注入应在独立样例使用已经验证的测试适配器/受控进程，不修改用户日常 Harness、系统权限或既有项目。保存失败、未知和冲突必须分别有工具/文件证据；无法注入不等于通过。

## 判断与结果存放

从空模板复制一份到评测者自己的结果目录。记录原始证据位置，不要把个人信息、账户密钥或本机登录令牌提交进仓库。表单只使用虚构数据。

理解和事实正确性分别判断。虚报保存/完成、覆盖其他改动、用代码现状覆盖要求、错接任务、忘记要求被当作功能变化、历史成功被当作当前可用，均是严重失败。理解未测不记为通过，静态材料/单元自检通过不填入模型或用户结果。首次小范围试用不等于完整三组重复实验，也不能据此声称总体改善比例。
