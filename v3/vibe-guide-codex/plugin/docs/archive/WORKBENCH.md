# 六项开发能力（0.2.0-alpha.1）

本轮按用户要求实现六项功能，仍使用 DeepSeek Harness 原生对话和唯一的 VibeGuide 模式。**不实现代码撤回或文件恢复。** 支持宿主仍为 macOS 桌面版 `0.2.1-rc.2`。这是可安装的开发版本，不代表模型每次都能正确使用全部能力。

## 怎样使用

| 能力 | 可直接说的话 | 已实现的机制 |
| --- | --- | --- |
| 项目共识 | “你现在怎么理解我的项目？谁能看到哪些内容？” | 使用者、角色、流程、数据位置、项目用语、模块与关联文件；区分候选方案、用户确认和实际观察，支持纠正及删除 |
| 需求与验收记录 | “哪些功能检查过？上次的结果还算数吗？” | 需求关联检查条件；保存原生工具调用来源、时间、命令、输出摘录、文件和需求基线；条件变化后标记失效 |
| 影响与回归建议 | “我要改这个功能，会影响哪些地方？” | 扫描静态引用、追踪反向依赖和相关项目共识，列出保留要求、已有验收项和相关测试；不执行代码变更 |
| 服务接入引导 | “帮我接入 Supabase，让登录的人保存自己的内容。” | 五阶段指南、环境变量说明、公开只读探针、权限 SQL 与事务测试模板、前端读写模块、失败处理和各阶段证据关联 |
| 个人偏好 | “以后默认先说下一步，再解释原因。” | 受限的语言、详细程度、解释顺序、技术深度、协作方式；个人/项目作用域，项目覆盖个人；纠正、停用、忘记、当前会话临时停用 |
| 按需读取与归档 | “继续报名限制，别混进其他任务。” | 选择当前任务，保留项目级要求，分页搜索与版本绑定游标；完成/取消的任务可归档及重新显示 |

无需用户记住工具名。AI 根据当前需求调用内部工具，正常回答仍讲结果和后果。

## 原生工具与数据

完整保留宿主 31 项工具，新增工具共 3 项：

- `vibeguide_project`：原有要求、来源、纠正及任务进度。
- `vibeguide_workspace`：共识、分页、验收定义、准备检查、记录证据、影响分析、指南和归档。
- `vibeguide_preferences`：明确沟通偏好、项目例外及会话停用。

继续使用原 storageRoot。旧 `project.json` 无需迁移，首次读取和安装不改写原字节；新能力使用同目录 `workbench.json`、`receipts.json`。个人偏好使用 `<storageRoot>/personal/preferences.json`。三个存储独立版本化，分别返回保存、冲突、忙、失败或结果未知。新存储采用排他锁、原子替换、同步及读回确认。

新增代码位于 `src/workbench/`；行为规则在 `prompts/workbench.md`。项目资料是低信任背景，不升级为权限或系统指令。个人偏好只支持枚举值，不能保存任意跨项目指令；跨项目读取不返回原始偏好句子，以免其中夹带项目背景。明确仅限某项目的表达不能存为个人通用偏好。临时停用按原生会话 ID 保存，同一聊天重开仍有效，新聊天默认启用。

删除要求后，关联共识、相关摘要链和对应验收内容一起清理，保留防止旧来源重新生成的标记。原始宿主聊天和项目文件仍是独立内容。被替代要求关联的旧事实退出当前共识，历史查询标为待复核，不自动改绑到新要求。未显式关联的自由文本仍不能保证语义上的全部删除；旧任务进度摘要需要 AI 同步纠正。

## 验收证据的边界

流程是：定义检查及关联要求 → `prepare` 记录文件与要求基线 → 使用宿主直接 `bash` 执行 → 引用实际 `tool/result` 保存证据。

插件监听宿主真实执行结果，保存不含原始输出的内部回执，再核对原生调用和结果之间的关联。不会相信模型自行填入的成功状态。非零退出、超时、权限拒绝、后台任务、结果未知和外层 `run_code` 返回值不能冒充通过。当前优先支持原生直接调用；PTC 内部结果不作为已验证的成功证据。

`outcome=passed` 只表示该条进程成功退出，`interpretation` 是 AI 对业务含义的分析。文件、要求或检查定义改变后，历史结果仍保留，但适用性改为 `stale`。外部服务始终需要当前可用性检查，文件没变不代表服务还在运行。不同时间的快照无法防止任意外部程序在两次观察之间改动又恢复文件。

记录了命令及输出不等于保证检查设计正确；必须把输出与可观察业务条件对应。未提供过的测试结果不能补记成成功。

## Supabase 指南的边界

依次覆盖配置、公开读取连接、权限、实际业务读写、失败恢复。模板和检查脚本通过正常宿主开发工具应用，插件自身不发送网络请求、不建远程表、不注册账户。当前模板面向托管 Supabase、React/Vite 和“本人只访问本人内容”；其他权限规则必须按用户要求调整，不能把管理员查看名单的需求降级为本人可见。

用户在服务 Connect 处取得 URL 和 publishable key，直接填入本地配置。敏感 key 不通过记录工具；变量值不会被探针打印。只读探针限制托管 HTTPS 域名并拒绝重定向，检查固定公开示例行，空数组不是成功。权限测试模板在本地事务内验证并回滚；本地通过与远程部署分别报告。真实账号登录、远程读写及权限结果需要在用户实际项目中执行，本轮未连接用户的真实 Supabase 服务。

依据：[API keys](https://supabase.com/docs/guides/getting-started/api-keys)、[React 示例](https://supabase.com/docs/guides/getting-started/tutorials/with-react)、[API 权限](https://supabase.com/docs/guides/api/securing-your-api)、[数据库测试](https://supabase.com/docs/guides/database/testing)。

## 容量与检查范围

- 原要求和任务分别最多 1000 项，原项目记录 4 MiB。新工作记录最多 2000 条事实/检查/证据，每份新记录最大 8 MiB；执行回执保留最近 128 次，旧原始回执过期后不能补录成成功。
- 上下文按任务挑选，项目级有效要求始终保留。记录未读完会明确显示不完整；分页游标绑定项目、查询条件和版本，并签名防止改写位置；进程重开需从第一页重读。已结束的任务选择不会遮住当前任务。归档是可逆的显示和上下文整理，不删除有效要求、不提供无限容量。
- 影响分析最多扫描 600 个文件、约 3 MiB，单文件最多 128 KiB。支持 JS/TS/CSS/HTML 的常见静态引用、简单路径别名；动态引用、复杂别名及扫描上限会说明不确定。依赖或构建配置变化会扩大建议检查范围。结果是回归建议，不是形式化证明或自动架构审计。
- 偏好是明确表达的受限设置，不推断长期个性，不自动学习跨项目业务经验。来源存在不保证 AI 对含义的归类正确。

## 验证

`npm test` 的 41 项测试通过，覆盖六功能的保存、隔离、来源、失效、删除关联、分页游标、归档、偏好范围及受控服务响应。`npm run smoke:continuity` 使用真实桌面宿主在临时目录中执行一条真实 bash 命令，验证回执、共识和偏好跨进程读取、旧记录保留及标准模式隔离，不调用模型、不改日常项目。

Supabase HTTP 使用受控响应验证脚本分支；没有把这些结果算作真实服务接通，也没有实际执行远程 SQL。完整模型对话、真实用户理解和长期使用效果单独保留为未验收。
