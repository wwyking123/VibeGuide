### 第四批落地说明（2026-10-28，alpha.5）

- `OriginalRequirement` 只来自 native `user/message` 的明确修改，或侧栏 Delivery 的首次原话及全部补充；不把主 AI 解释提升为需求。修订用 `previous/version` 链保留原始文本，停用不删除旧记录。
- `Delivery.background` 冻结本次实际附带的要求引用、版本和原话；内容参与消息摘要及原生回执核对。发送前重验约定版本，串行存储锁中再核对项目修订号后才进入 `dispatching`。之后不改消息、不因未知结果重发。客户端显示携带内容和送达状态。
- Native `turn/start → user/message → tool/call` 关联候选要求；嵌套工具使用真实 `rootCallId`。同轮多用户输入、继承历史或来源缺失不强行关联。操作前后捕获文件哈希和有限脱敏摘录；并发改动不授予独占归属。
- `OutcomeBinding` 由 owner 明确核对试用范围及逐项候选产生，包含要求版本、试用卡、文件基线和操作引用。每步必须有当前实际变更、变更后的有效检查和正反馈才得到限定范围 `complete`。语义覆盖不由模型或来源序号自动证明；用户不确定时保留待核对，主开发继续。
- `Analysis` 支持 `changes/goal`，结构化模型返回必须引用提供过的文件和既有节点；来源、版本、需求摘要、缓存键随结果保存。改动解释使用实际 before/after，目标定位区分已有职责、可能新增和未知。无 before/after 时直接返回未知、不调用模型；刷新和原生事件始终不生成分析。
- 新增 owner-only API：`reviseRequirement`、`bindOutcome`、`analyze`，所有请求校验项目/会话及稳定请求 ID。现有 `prepareReview` 支持 `requirement:{id,version}`；旧调用兼容。结构分析从统一输入框按只读意图路由，不引入执行工具。
- 本版采用有界本地 JSON 与规则检索，没有引入向量库或远端服务。能力限制和真实模型/用户评测缺口见开发状态，下面完整目标契约不等同于全部已实现。

### 第一批实现说明（2026-10-28）

- 新记录保存为 `<storageRoot>/guide-v1/<scopeHash>.json`，按项目真实目录与会话分开；不迁移或覆盖旧续接记录。JSON 包含操作、事件处理水位、待处理任务和用户主动请求的讲解。使用临时文件、同步、原子替换和读回核对。
- 内置 `node:sqlite` 只提供进程持有的单写者锁，实际业务记录仍为 JSON；进程退出或崩溃释放锁。不新增数据库运行时依赖，不把 SQLite 数据库宣称为完整 guide Ledger。
- 工具执行前保存有界文件指纹，执行后读取原生回执。仅识别明确的检查命令；复杂脚本、无法核对的历史执行或并发修改标为未知。内层检查失败不能被外层 `run_code` 的成功覆盖。
- 文件扫描最多 500 个文件、总量 8 MiB、单文件 1 MiB，扫描预算 120 ms（单次系统读取不保证硬截止）；跳过构建产物、依赖、秘密文件和符号链接。不完整扫描不宣称版本适用。该基线是保守的项目文件范围，不是需求级 `OutcomeScope`，也不覆盖远程数据与外部服务。
- 后台处理宿主事件并持久登记任务，启动补读；客户端暂按 5 秒轮询快照，包含记录版本与宿主事件水位。完整 `SnapshotEnvelope` 增量订阅、迁移和跨会话学习导航仍待实现。
- 打开、刷新、工具返回、恢复与讲解失效均不调用解释模型。恢复的旧讲解保留正文并标为历史，不重写，不添加原文依据区域或替代快捷入口。

### 第二批实现说明（2026-10-28）

`0.2.0-alpha.3` 新增统一 `submit`，保留只读 `ask` 供原题解释。`intent.ts` 使用保守确定性规则，仅从用户主动提交的原话判断通道：明确修改直接发送，追问只解释，含糊/混合表达澄清，原题与权限答案引导回主对话。规则不额外调用模型；复杂意图覆盖不作保证。

`communication.ts` 在同一次本地提交中保存输入、完整澄清链和 pending Delivery；持久记录 dispatching 并读回后才调用宿主 queue。稳定 requestId 绑定项目、会话和完整内容，不复用不同内容。宿主原生 rpcId、消息原文、接收项目用于对账；同 ID 多条记录、内容不符或缺失均保留待核对。pending 可在恢复后首次发送，dispatching/unknown 只能查询，不能自动重发。超时后的底层调用仍保留所有权，晚到结果重新对账。

客户端提交前在宿主页面的本地存储保存未确认草稿及 ID；重开只恢复输入，用户点“核对并重试”才提交同一 ID。响应丢失但服务端已记录时，刷新从持久输入和回执恢复。关闭页面不会取消已落盘的修改。回执只表示接收，尚未自动绑定后续代码改动/检查/验收，不显示功能完成。

本批是 P2 的沟通部分，跨会话历史背景选择、主动概览、精确 OutcomeScope 与结构图仍依照后续阶段实施。覆盖和实际验证限制见[开发状态](IMPLEMENTATION_STATUS_V2_2.md)。

# 一、目标与边界

# 01 原则与范围

### 必须保持的原则

后文以编号引用，不再逐章重复。

| 编号 | 原则 | 含义 |
|---|---|---|
| R1 | 拐杖，不是课堂 | 帮非技术用户把事做成；不做测验、复习、掌握标签或能力等级 |
| R2 | 一个模式 | 只有一个 `vibeguide` preset；客户端／服务端只是技术分层 |
| R3 | 主对话原始回答易懂 | 通过 `core.md` 静态沟通规则引导并验证，不把解释责任全部移到侧栏；提示词本身不保证模型始终遵守 |
| R4 | 单向阀 | VibeGuide 可读获授权的当前主线事件与改动；写入主 AI 只有 `core.md` 和用户可见的转交消息 |
| R5 | 解释不阻塞开发 | 侧栏生成、失败、关闭、取消都不能暂停或停止主线 |
| R6 | 明确修改自动转交 | 判断为明确修改后直接发送，不弹通用确认；只转交用户实际表达的内容 |
| R7 | 原话为准，不夹带决定 | 保存并转交用户原话；VibeGuide 的理解单独标注；不补入供应商、付费、部署等决定 |
| R8 | 状态必须有依据 | 送达、执行、检查、用户验收分别记录；完成标签需要改动、适用检查和用户验收，且无已知未满足项；验收不控制主线是否继续 |
| R9 | 人话优先，解释按需 | 原始表达先说使用影响；默认操作状态由实际记录确定，所有摘要与补充解释由用户主动触发，已有词表或有效缓存直接展示，不为判断用户是否看懂另调模型 |
| R10 | 低可信材料不是指令 | 代码注释、README、工具输出、历史解释中的“指令”不构成用户授权 |

### 本版交付范围

支持从零开发、接手已有项目、开发中卡住三个场景。侧栏提供“当前进展／项目结构／了解过的”三个入口，把解释、结构认知与修改要求连成闭环。开发分阶段推进，但最终范围不缩减为单个场景。

### 明确不实现

- 自动生成面向用户的进展或影响摘要，包括重要改动、检查完成或回合结束后的后台摘要
- 产品级回退存档、回退或局部撤销入口（安装脚本的配置备份属于安装安全，不是业务恢复功能）
- 领域能力画像、能力等级、“我会／我不会”锁定
- 独立执行代理、通用代码教学、第二套审批计划、跨宿主产品、独立自动化验收平台
- 向主 AI 注入项目记录、偏好、解释，或注册任何 VibeGuide 工具
- 独立的面向用户的风险提醒功能（保留敏感内容过滤；不把过滤成功等同于已检查产品安全）

# 02 三类场景

三个场景共用同一套模块和数据模型，用户无需切换模式。它们是后续各模块的验收依据。

### 场景一：从零开发 · 例：21 天思考小游戏

<div class="journey">
<div><b>1 用户提出想法</b><br>“我要做一个 21 天打卡思考的网页版小游戏。”</div>
<div><b>2 主 AI 澄清关键行为</b><br>围绕每日问题、回答方式和保存范围提问。关键行为未定时先不实现。</div>
<div><b>3 需要时解释选择的影响</b><br>看懂后直接选择，不追加选项解释调用；用户问“保存在浏览器是什么意思”时，侧栏再讲换设备、清理数据和隐私的实际后果。</div>
<div><b>4 主线开始实现</b><br>事件进入队列，侧栏归纳“问题展示”“回答保存”等结构及变化。</div>
<div><b>5 用户明确修改</b><br>“改成换手机也能看。”保存原话 → 自动转交主线 → 显示已接收／排队回执。</div>
<div><b>6 结果与依据更新</b><br>分别展示实际改动、检查和用户验收；没有用户验收不显示完成，主线不因此暂停。</div>
</div>

**关键判定：** 需求澄清由 `core.md` 和主会话自身上下文负责，侧栏不增加第二份问卷或逐步放行流程。“跨设备查看”是用户目标，云数据库、登录机制是后续实现选择；转交时不得把某供应商或付费方案包装成用户已同意（R7）。主 AI 需要用户作关键选择时，仍在主对话中提出。

**宿主限制：** 早期原型观察到侧栏要等会话发出第一条消息后才能打开（第 3 章，待复测）。若属实，第 1 步时侧栏为空是正常状态，不需要另做入口。

### 场景二：接手已有项目

| 步骤 | 系统行为 | 用户感受到的价值 |
|---|---|---|
| 绑定项目 | 核对目录身份、历史和已有记录 | 不混入其他项目的要求 |
| 建立概览 | 先做受限索引；有有效概览直接展示，否则用户点“帮我看懂这个项目”后生成职责节点及依据（第 8 章） | 一次请求看懂项目，不必逐文件提问 |
| 提出修改 | 关联涉及的节点和当前要求 | 知道修改大致影响哪些部分 |
| 自动转交 | 发送原话和必要上下文（第 11 章） | 不必把自己的话翻译成技术任务 |
| 跟随实现 | 增量更新、证据校验、旧解释标记 | 看见真实变化，阅读位置不被打断 |

历史缺失时只说明当前代码能观察到的状态，不把代码推测成用户原来的要求。外部编辑造成的变化找不到对应主线事件时，标注“检测到文件变化，来源未确定”。

同一项目的新会话会显示已有项目记录，但须区分“侧栏保存了”与“已由 VibeGuide 转交到本会话”。用户从侧栏提出本次修改时才附带相关历史背景，打开面板或创建会话不自动发送（第 11 章）。

### 场景三：开发途中卡住

1. 主线错误、失败检查或用户描述进入事件队列。
2. 读取相关结果、已有尝试和受影响功能，分别记录事实与可能原因。
3. 用人话解释“什么功能受影响”“已试过什么”“还不知道什么”，给出少量可理解的处理方向。
4. 普通追问只得到解释；用户回答主 AI 的待答原题时回原入口作答，另行提出明确修改要求时才经修改链自动转交（第 11 章）。
5. 主线修复后，旧错误保留为历史；重新检查前不显示“已解决”。

**禁止混淆：** “可能是网络问题”不能变成确定诊断；重复出现的日志不等于同一故障；“为什么又失败了”不等于“允许换技术栈重写”。要求明确而实现细节未定时，交给主 AI 继续澄清，侧栏不成为额外的技术门槛。

# 03 现状基线

### 团队代码已有什么

| 能力 | 源码现状 | 本版工作 |
|---|---|---|
| 易懂沟通 | `src/index.ts` + `prompts/core.md` | 保留，作为 R4 唯一例外 |

### 两条独立工作链

**观察链：** 观察主线 → 归并实际操作与检查记录 → 更新确定性状态和已有视图，不调用解释模型。

**解释链：** 用户主动求助 → 读取有效依据与缓存 → 必要时生成解释 → 更新侧栏。只读，不占用主对话输入，不调用开发工具，不等待用户阅读。

**修改链：** 用户输入 → 判断性质 → 保存原话 → 自动转交目标主会话 → 核实接收 → 跟踪执行和验证。**这是唯一能影响主 AI 的通道**（R4）。

# 06 模块、生命周期与单向阀

### 模块职责

| 模块 | 主要职责 | 边界 |
|---|---|---|
| `HostAdapter` | 宿主差异、会话、事件、投递、模型 | 不靠模拟界面点击发送消息 |
| `GuideService` | 组织查询、追问、修改请求和订阅 | 每次校验项目／会话绑定 |
| `EventWorker` | 待处理记录、回放、去重、重试；提供项目串行提交入口 | 各服务产出状态变更命令，统一经此入口写入；不在宿主回调或持锁期间做模型推理、网络发送 |
| `ProjectProjection` | 结构、变化、检查、任务状态的读模型 | 可重建视图，不覆盖用户原话 |
| `Translator` | 技术词 → 人话三层（第 9 章） | 词表／缓存和表达规范；需要模型的补充统一由 ExplanationService 按需调度，不另开逐词生成队列 |
| `ExplanationService` | 根据用户请求生成变化、影响、取舍解释 | 无自动摘要任务；无写代码、终端、部署或发送权限 |
| `IntentService`／`DeliveryWorker` | 区分追问与修改；投递与对账 | 只接受当前用户输入 |
| `ContextResolver` | 统一来源、适用性、失效传播 | 只服务侧栏与转交消息，没有通往主 AI 上下文的出口 |
| `GuidePanel` | 三个入口、阅读位置、输入、回执 | 只展示状态，不自行推断成功 |

### 生命周期

- **宿主级：** 注册服务和客户端入口，维护工作队列；卸载时释放监听与订阅。
- **项目级：** 按规范化目录建立状态空间，串行提交同一项目的状态变更。
- **会话级：** 绑定原生会话 ID、事件游标和当前目标；只跟踪启用 VibeGuide 的会话。
- **视图级：** 阅读位置、选中内容和输入草稿，只存前端。

### 单向阀落地：停用现有注入

| 现有注入 | 位置 | 处理 |
|---|---|---|
| 每轮动态上下文（项目记录、任务、用户来源，最长约 26 KB） | `continuity/plugin.ts` 的 `system-prompt/assemble` | 删除；内容改由侧栏解释模型读取 |
| 记录工具 `vibeguide_project`、`vibeguide_workspace`、`vibeguide_preferences` | `continuity`、`workbench` 的 `tools.register` | 不再注册给主 AI；写入全部由 `EventWorker` 完成；复用与工具调用无关的校验与存储，依赖旧 prepare／check 的证据入口按第 15 章重建 |
| 指导主 AI 使用上述工具的提示段 | `prompts/continuity.md`、`prompts/workbench.md` 及对应 `systemPrompt.section` | 随工具移除 |
| 静态沟通规则 | `prompts/core.md` | **保留**，R4 唯一例外，不含任何用户或项目状态 |

**代价：** 主 AI 不再自动“记得”跨会话的项目要求。续接时由侧栏整理当前有效要求，用户转交修改时随消息带上（第 11 章“必要上下文”）。同一会话内主 AI 自身上下文不受影响。

侧栏打开、新会话创建、偏好变化或记录纠正都不自动向主线发送摘要。转交时所附历史要求必须有来源、仍适用且与本次修改相关，明确标为历史背景，不冒充用户新说的话。同一会话中的宿主原始历史、原生工具和权限流程照常工作；移除范围仅为 VibeGuide 动态注入与记录工具。

`EventWorker` 的“唯一写入者”是统一提交边界，不意味着模型调用、文件扫描和消息发送串成一个长事务。GuideService、DeliveryWorker、证据观察器均将短状态变更交给同一项目队列；工作完成后核对预期版本再提交。前端双面板共用服务端工作者，不能各自启动发送循环。

# 三、核心模块

# 07 事件采集

### 做什么

把主线持久事件变成可恢复、可去重的待处理记录，为主线变化提供统一来源。当前未决问题是额外的只读状态入口；侧栏输入与验收先经受认证的服务入口保存，再由同一提交边界处理，不假装它们已经出现在主线历史中。

<div class="flow"><div>主线持久事件</div><span>→</span><div>待处理记录</div><span>→</span><div>变化与有效依据</div><span>→</span><div>确定性状态／已有视图</div></div>

### 数据

`EventJob`：会话、seq、事件 ID、处理器版本、状态、尝试次数。去重键 `sessionId + eventId/seq + processorVersion`。待处理记录与已登记／连续完成游标保存在 `guide.json`；内存队列只调度这些记录。

`PendingChoice`：projectId、sessionId、原生问题 ID、原题与稳定选项标识、版本、状态（待回答／已回答／被替换／已取消）和实际可取得的来源坐标。补充 `originKind: product_choice | permission | other`、`answerChannel: original_card | main_conversation | unavailable` 和经宿主校验的 `answerTarget`。它是当前问题的视图，不是新增问卷或自动解释任务；字段映射由 HostAdapter 在 P0 验证，缺少稳定标识时不伪造。

**本版作答边界：** 侧栏负责解释和定位，原题答案回宿主原卡或主对话提交，`canReplyFromSidebar = false`。统一输入框识别到原题作答时返回 `redirect_to_choice`，不创建 Delivery，不复制一套答题或权限审批控件。P0 验证可定位的入口；无法定位时说明需回主对话，不模拟点击或猜测接口。以后增加直接代答须另行验证身份、原题版本、可见回执与去重，不能作为 followup 的隐式降级。

| 状态 | 含义与恢复 |
|---|---|
| `pending` | 已登记，等待处理 |
| `processing` | 正在处理；重启后重新领取 |
| `processed` | 需要的记录已保存，或已记录“无需变更”的理由 |
| `needs_clarification` | 意图含糊；不阻塞其他事件 |
| `failed` | 有错误类别和重试次数 |

### 实现要点

- 以宿主持久会话事件为恢复依据；实时流只用于“正在处理”等短暂状态，不写成结论。
- 订阅回调只登记轻量唤醒，不等模型；工作者按游标从宿主历史补读并先写入待处理记录。
- 维护“已登记游标”与“连续完成游标”，不因后一个事件成功就跳过前面失败的事件。
- 宿主不能按游标查询时，读取受限历史并按稳定 ID 去重；无法覆盖缺口时显示“跟踪不完整”。
- **当前问题：** 从宿主当前问题状态和已落定事件关联原题，不等 `turn/end`；尚无持久 seq 时不伪造。只做关联和状态更新，不调用解释模型。已回答／替换／取消时更新版本；无法可靠读取时说明限制，不拿上一轮问题顶替。
- **合并：** 同一任务内短时间连续文件操作合并为一个 `ChangeSet`。起始合并窗口 800 ms（待测），仅用于归并事实和更新状态；窗口到期、重要改动、检查返回或回合结束均不创建摘要任务。用户主动追问可以读取已落定事实，不等 `turn/end`；有效缓存优先，无有效缓存时才调用解释模型。
- **背压：** 只合并可重建的事实视图更新，不丢弃用户要求、检查结果、发送记录或主动提问。不建立自动解释队列；积压时优先处理用户主动请求。

**主路径简化：** P1-P3 用单进程内存调度队列 + 持久 EventJob／游标 + 启动补读，不引入分布式队列。先恢复本地未完成记录，再补读宿主历史；侧栏尚未发送的用户输入并不存在于宿主历史，必须从本地恢复。跨进程租约放 P4（第 19 章）。此前仅允许一个写入工作进程使用同一状态根；检测到另一个活动持有者则不启动第二个写入／发送者，不能把不支持的并发当成功。

### 借用来源

[dsh-explain 的来源观察器](https://github.com/yuezengwu/dsh-explain/blob/15504c26fe018008208c9975228763a4b523edaa/src/observer.ts)可借鉴“完成回合 → 采集来源材料”。其[候选队列](https://github.com/yuezengwu/dsh-explain/blob/15504c26fe018008208c9975228763a4b523edaa/src/queue.ts)是内存 Map 且“保留最新”，不能替代持久的 `EventJob`：用户输入不得被合并丢弃。

未决问题读取是补充通道，不能直接用完成回合采集器替代。来源读取、预算与取消可局部借鉴，不搬入全局学习线程、复习、SQLite 运行时或与其耦合的整套调度器。

### 验证

重复、乱序事件不产生重复记录；处理中崩溃重启后不漏主线和侧栏用户输入；事件缺口显示“跟踪不完整”及截止时间。待回答阶段即可追问原题；没有主动求助时，文件改动、检查返回、回合结束、打开或刷新侧栏均不产生摘要或解释调用；切换会话后不展示旧题。

# 08 项目结构

### 做什么

为“项目结构”入口和解释提供职责视图：页面／交互、业务处理、数据存储、外部服务，以及它们之间有依据的关系。

### 数据

`ProjectNode／Edge`：稳定 ID、职责名称（人话）、技术名、关联文件及行号、来源、“观察”或“推断”标签。

| 关系 | 实现依据 | 表达方式 |
|---|---|---|
| 页面引用组件、模块导入 | 确定性路径解析 | 已观察，保留出处 |
| 点击后保存到服务 | 代码调用、配置和执行证据组合 | 区分静态关联与已运行验证 |
| 某模块承担业务职责 | 代码／文档摘要与当前任务 | 模型归纳，允许用户纠正 |
| “这一改动会影响登录” | 依赖传播与需求关联 | 标为潜在影响，不等同已发生故障 |

### 实现要点

`ProjectScanner → ProjectProjection → ContextResolver → StructureView`，事实提取与显示分开。

- **扫描：** 首次接入读取目录、依赖清单、配置、入口和相关源文件。排除依赖、构建产物、二进制和敏感文件；限制文件数与总字节，超出时显示覆盖范围。
- **增量：** 以相对路径和内容哈希索引，缓存按 projectId、内容哈希、解析器版本失效，不只看 mtime。接入、任务结束、窗口恢复时重新核对，防止漏掉外部编辑。
- **范围：** 读取限制在当前工作区，符号链接不能越界。
- **语言：** 首版只保证课程示例使用的 Web 项目做导入解析；其他语言只用目录、清单和摘要，并明确显示精度较低。
- **推断边界：** 不能从“存在数据库依赖”推出“已实现跨设备同步”。
- **变化对比：** 改动前后各存一份投影，对比后高亮变化节点。
- **结构图：** 只读 React Flow。禁止拖拽、连线、重连和删除，节点级配置也不能重新开启编辑；保留点击、键盘选择、缩放，并提供等价的职责清单。新变化只更新相关节点，不自动重置布局。来源过时的节点显示“待核对”。点击先查询已有职责说明，用户要求补充时按第 10 章生成，不触发修改。
- **粒度：** 按业务职责聚合文件，默认展示少量相关节点，再按需展开。目标需要但尚未实现／验证的职责可展示为计划或待核对节点，不能从静态 import 关系直接推导完成；底层模型不依赖 React Flow 类型。

**已有项目首次概览：** 受限扫描先显示能确定的事实、覆盖范围和“帮我看懂这个项目”入口；没有可信职责归纳时不把文件名列表冒充易懂概览。已有有效概览直接展示；没有时，由用户点击或明确提出同等请求后，经 `ask(kind: project_overview)` 一次生成职责概览，附来源、推断标识与 `Basis`。重复请求复用在途作业或有效缓存，不逐节点调用。生成失败保留扫描结果和重试入口；概览过时显示限制，用户再次请求才补充，不因打开面板、切页签或缓存缺失自动生成。

# 09 人话翻译

### 做什么

让侧栏原始表达就能帮助非技术用户判断（R9）。结构图、变化卡、解释和回执共用词表与表达规范；不把每个出现的技术词都变成额外讲解任务。

### 三层表达

| 层 | 内容 | 例：Webhook |
|---|---|---|
| 1 一句话 | 它在**这个项目**里做什么 | 支付平台主动通知网站“有人付款了”的入口 |
| 2 对你意味着什么 | 影响你的哪些决定或风险 | 这里出错，可能出现“钱付了但会员没开通” |
| 3 技术细节 | 默认折叠，想看才展开 | 第三方向公开 URL 发 POST，需要校验签名 |

已打开的解释优先呈现第 1、2 层；第 3 层默认折叠，用户点击或既定详细程度偏好可控制已生成内容的显示。偏好不自动预生成所有词条，也不改变“选项按需解释”的触发规则，不依据能力画像。

### 数据

`Term`：id、技术名、一句话、对你意味着什么、可选日常类比、技术细节。分两类来源：

- **词表：** 常见概念（组件、接口、中间件、环境变量等）的人工审定条目，随插件发布。
- **项目化：** 描述“在本项目里做什么”时必须基于第 8 章的节点与出处。需要模型时在用户主动请求的解释中一并生成，经校验后缓存在 `guide.json`；不因重要变化自动补充，通用词表不能冒充已核实的项目事实。

### 实现要点

- 渲染前只做词表／有效缓存查询和轻量规则检查，不调用模型扫描“用户能不能看懂”。已有易懂原文直接使用；无现成说明的必要技术词提供“解释这个词”入口，用户主动打开才补充，不因缓存未命中或侧栏重绘自动生成，也不阻塞已有状态展示。
- 节点名称、变化卡标题一律用职责名，技术名只作附加信息。
- 翻译只改表达不改事实：数字、否定、条件、角色不得在翻译中丢失（与第 10 章共用校验）。
- 类比只在有帮助时使用，不为每个词硬造比喻。
- 模型生成解释时直接遵循上述表达规范，Translator 不在前后各做一次全量模型翻译。缓存绑定项目、术语、实际依据、语言及提示版本；依据失效后标记旧说明，用户需要时再生成。

### 验证

在真实开源项目（如 tailwind-nextjs-starter-blog、vercel/nextjs-subscription-payments，固定提交）上抽查侧栏文本：核心标题与操作不依赖术语才能看懂；必要术语有已有说明或按需入口，第 2 层说清实际影响。无主动求助时不产生逐词补生成调用，由非技术参与者判断是否看得懂（第 20 章）。

# 10 解释服务

### 做什么

只在用户主动求助时生成解释：发生了什么 → 对你意味着什么 → 可以怎样处理。“当前进展”默认通过实际操作记录映射状态，不经过解释模型。解释只读，独立于主线运行（R5）。

### 数据

```ts
type ExplanationDraft = {
  change: string;              // 现在发生了什么
  impact: string[];            // 对使用者意味着什么
  tradeoffs?: string[];        // 当前选择涉及的取舍
  uncertainty: string[];
  sources: string[];           // 必须指向提供过的依据 ID
  followups: string[];         // 可追问，不是已授权任务
};
```

保存为 `Explanation`：上述内容 + 来源 + `Basis` + 版本。

关键结论另保留可验证的 `Claim`：类型（用户要求／观察／计划／推断／检查结果）、文字、依据引用和不确定性。状态标签由服务端证据状态渲染，不从模型的“已经完成”字样直接推导。自然语言 schema 合法也不等于语义正确。

### 按需解释与调用触发

| 场景 | 默认行为 | 何时调用模型 |
|---|---|---|
| 主 AI 提出易懂选项 | 关联 PendingChoice，展示轻量帮助入口；用户可直接选择 | 用户点“帮我理解这些选择”或主动追问，且无有效缓存时 |
| 纯澄清回合完成、选项被替换 | 更新原题版本／状态，旧解释标记历史 | 不因此自动重新解释；等用户再次求助 |
| 技术词出现、节点被选中 | 展示现有职责、词表和有效缓存；缺失时提供解释入口 | 用户明确请求补充说明时，不因缺词或重绘逐词生成 |
| 已有项目首次打开、概览缺失或过时 | 展示扫描事实、覆盖范围和“帮我看懂这个项目”入口；有效概览直接展示 | 用户点击或明确要求项目概览，且无有效缓存时；一次请求组织整体职责，不逐节点生成 |
| 产生重要开发变化 | 归并操作记录、更新状态，失效的说明标为历史 | 不自动调用；用户点“这意味着什么？”、“帮我总结这次变化”或主动追问，且无有效缓存时 |
| 检查返回、回合结束、侧栏重开或刷新 | 更新已有事实与有效缓存，缺失依据时说明未知 | 不因此创建摘要或解释任务 |
| 用户追问某个影响或原理 | 绑定所指内容和版本 | 有效缓存优先，缺失时针对该疑问生成 |

选项首次易懂说明由主 AI 完成；侧栏不另调模型判断用户是否看懂，不预生成每个选项的讲解。用户主动求助时可以读取尚未结束回合的原问题和已落定事件，不能以等待回合结束作为解释的前置条件。本版原题作答按第 7、11 章引导回宿主正确入口，不将选项回答误投递为新的修改任务。

请求与缓存按 projectId、sessionId、原问题 ID／版本或解释版本、实际提问、Basis 摘要、语言、提示版本和模型配置区分。同一在途请求的重复点击复用流；同题不同追问分别处理。缓存只在依据仍适用时复用；源问题或依据变化时重新核对在途结果，不把旧答案发布为当前，也不自动循环重生成。

创建解释任务必须关联可追溯的用户提问或帮助点击；主线事件、计时器和缓存失效均不是解释请求。没有后台总结任务；并发控制保留主动请求的顺序与状态，不取消主 AI 或其他用户的主动请求。不照搬 dsh-explain 的同来源互斥限制为“主 AI 忙时禁止追问”。此策略限制额外解释调用，不代表主线、记忆提取等所有功能都零消耗；记忆任务也不得用于生成面向用户的自动摘要。

### 模型配置与降级

`GuideRuntimeConfig` 明确模型选择策略（宿主当前选择或已配置的固定模型）、输入／输出预算、超时与并发上限；在宿主侧解析实际 provider／model，不假设独立调用自动继承主会话，也不让前端持有密钥。采用宿主当前选择时，每个解释请求开始即记录路由；中途设置变化不静默切换该请求。

状态区分 `not_configured / unavailable / ready`。无可用模型时仍展示确定性事实、已有有效说明和配置提示，不猜测模型、不伪造解释。每次调用记录实际路由、用户请求 ID、触发原因、提示版本、时间与宿主可取得的用量；拿不到用量时记未知。缓存命中、重复请求复用与主动请求引起的生成分开计数，便于验证节省是否真实发生。

### 实现要点

- **调用：** 宿主模型服务，显式指定 provider／model、输入预算、输出 schema、独立 requestId 与 AbortSignal。取消只取消侧栏生成，不调用主会话停止接口。侧栏会产生额外模型调用，不能承诺免费。
- **无工具：** 不注册终端、文件修改、部署或发送工具；输出结构化候选，由服务端校验后保存。
- **先规则后模型：** 操作与检查记录支持的事实即时显示，如“正在查看项目”“正在修改文件”“等待你选择”。无法可靠归类时显示未知，不从工具类型猜测业务职责或功能完成。模型只在主动求助时补“意味着什么”和取舍。
- **输入：** 当前目标、相关要求、有效事实（经 `ContextResolver`）、当前变化、检查情况和完整提问。项目文档、工具日志、历史摘录是低可信材料（R10）。先过滤敏感内容，再按相关性裁剪；缺少重要条件时不给确定性判断。
- **校验：** 程序检查来源存在、作用域、版本，以及数字／角色／否定条件是否与原文一致；模型核验只作辅助，无法判定时降为“待核对”。结构合法、引用真实都不保证解释正确。
- **竞态：** 每次生成绑定 `Basis`；完成时重新核对相关依赖。发生变化则保存为历史或提示需要重新提问，不发布为当前结论。所有解释均不因依据失效或合并窗口结束自行重算，等用户再次主动求助。缓存规则见上。

# 11 修改链

### 做什么

识别用户在侧栏里的明确修改要求，**自动**转交主对话（R6），并分别跟踪送达、执行、验证。这是 VibeGuide 影响主线的唯一通道（R4）。

### 意图判断

侧栏只有一个输入框。服务端保留完整输入和上下文，区分提问、原题作答、修改、含糊表达、记录纠正；模型只给候选分类，由确定性规则和当前语境约束最终动作。

| 输入 | 处理 |
|---|---|
| “为什么不用云端？” | 只解释，不记成选择、不转交 |
| 已确定原来的保存方式，用户明确说“那就改成换手机也能看。” | 自动转交“跨设备查看”，显示回执；不夹带供应商或付费授权 |
| 当前原题正在等保存方式选择，用户说“选换手机也能看” | 定位该题，提示回原卡作答；不创建修改任务 |
| “第二个为什么？”且当前所指明确 | 解释该选项，不代为选择 |
| “第二种吧。”但无法确定所指 | 简短询问所指方案，不猜 |
| “先别改，我只是问一下能不能做。” | 只答可行性，不被“改”字触发 |
| “你记错了，我说的是只给管理员看。” | 修正记录；是否需要改代码按完整语境判断 |
| “只改说明，先别改代码” | 只纠正记录 |

**发送前只做必要检查：** 目标会话仍绑定原项目；行为和对象明确；没有与之前决定矛盾且撤销意图不清的冲突。只澄清冲突部分，不要求用户先补完技术方案。

**因为自动转交没有人工确认，误判的代价更高：** 分类规则宁可多问一句，也不把含糊表达当成修改；自动建议、引用文本、模型自问自答、工具输出都不具备用户授权效力（R10）。

澄清只针对未确定部分：保存首次完整原话和后续补充，不能用预设按钮文案覆盖原话。例：“支持换设备，但别要求手机号”即使需要澄清，也必须保留否定约束。不用问号、单个动作词或“如果”硬分流；礼貌请求可能是修改，条件表达也可能包含明确指令。

### 原题作答与修改的分流顺序

1. 服务端重新核对 Scope、当前 `PendingChoice`、用户实际阅读的问题／解释版本；前端传来的阅读背景只是引用，不能决定授权。
2. “第二个／就按这个”等指代关联到已替换、取消或不明的问题时，返回澄清，保留原文，不把旧题答案套到新题。明确询问旧解释时仍可按历史版本解释并标注。
3. 涉及宿主权限问题时，只解释影响或引导原审批入口；输入“同意”不成为开发任务或侧栏授权。
4. 对普通产品选择，纯追问进入解释；明确回答当前原题时返回 `redirect_to_choice`；已有功能的明确修改才进入 Delivery；只纠正说明时进入记录纠正。存在待答问题不代表所有新输入都属于该题，也不能仅凭“改”字判为修改。
5. 无法区分答题与修改时，问一个简短的产品问题。一次输入既含作答又含其他要求时保存全部内容；通道或范围不明确就澄清，不擅自拆成两次发送或丢弃后半句。

同一输入只提交一个经确认的处理分支。`redirect_to_choice` 显示“请回主对话的这道题选择，刚才这句话没有作为新任务发送”；引导后不自动提交原题，原题被回答时由宿主事件更新状态。记录纠正不具有隐含改代码授权，明确同时要求修改的完整原文仍按修改链处理。

### 转交消息内容

用户原话 + 必要上下文（当前有效要求摘要、所针对的解释／变化版本）+ 请求 ID。VibeGuide 的理解单独标注；不得补入“使用某数据库”“同意付费”“批准部署”等决定（R7）。消息在主对话中对用户可见。

附带摘要只包含与本次目标相关、来源可追溯且仍有效的背景，并与本次原话区分。不自动把长期记忆整包发出，不通过隐藏 prompt 或额外工具让主 AI 读取记录。尚未确定登录方式等实现细节不阻止一个明确产品目标转交。

### 新会话的历史转交状态

`Delivery.contextRefs` 保存实际附带的要求 ID／版本、来源和摘要内容校验值，与消息内容一起固定；发送后不得用新摘要覆盖旧记录。适用于本次目标的项目级约束计入相关背景，不因它不是某个功能的专属要求而漏掉，也不整包附带所有历史。

侧栏按“目标会话 + 要求版本”从 Delivery 推导 `not_forwarded / pending / accepted / unknown`，不创建第二套需求真相。新会话已有历史但尚无对应转交时显示“这些历史要求尚未由 VibeGuide 附带到本会话；从侧栏发送本次修改时会附带相关内容”。只报告 VibeGuide 已知的转交记录，不断言主 AI 完全不知道历史。

- `pending`：相关背景随本次要求正在发送；尚不能显示已收到。
- `accepted`：相关背景已随本次要求发送，等待主 AI 处理；展示实际附带内容，不能标成已理解、长期记住或已执行。
- `unknown`：相关背景是否送达仍待核实；不自动补发。
- 要求被纠正产生新版本时，新版本重新计算转交状态；旧版本的成功不代表最新内容已发送。只发送了部分背景时标明范围，不显示“全部历史已同步”。

此提示不阻止用户直接在主对话开发，不因打开侧栏、创建会话或纠正记录自动发送摘要。

### 数据

`Intent／Delivery`：`userStatement`（首次原话）、`clarificationStatements`（澄清补充）、`interpretedGoal`（候选理解）、稳定 `requestId`、`contentDigest`、`contextRefs`、目标会话、侧栏输入来源、接收状态、可选原生消息关联。投递后不可用同一 ID 改写内容；送达、执行、检查、用户验收独立存储。原题作答的引导只保存输入处理记录，不占用 Delivery 状态机。

### 投递流程

1. 保存原话与 `requestId`，创建 `pending` 记录；保存失败则不发送。
2. 核对会话绑定后，用 followup 投递，不打断当前任务。
3. 根据宿主接收响应和原始事件确认送达，记录 `userStatement → nativeMessageId`。
4. 观察后续事件，分别更新执行与验证。

每条要求单独排队并显示原话，排队期可显示“已提出，当前任务仍在继续”，不能把目标变化当作代码已实现。`accepted` 不要求此时已有原生消息 ID；观察到对应原生事件后再建立关联。宿主只返回接收确认时，不虚构 `seq`，也不承诺在未验证的固定时点开始处理。

| 内部状态 | 用户看到 | 依据 |
|---|---|---|
| `pending / dispatching` | 正在发送 | 本地已保存，未确认接收 |
| `accepted` | 已发送，等待主 AI 处理 | 宿主明确接受；忙碌时显示已排队 |
| `unknown` | 发送结果待核实 | 响应丢失或超时；不当作失败，也不自动重发 |
| `rejected` | 未发送成功 | 宿主明确拒绝，给出可重试原因 |
| 执行 `handling / blocked` | 正在处理／暂时无法继续 | 关联任务的事件或明确阻塞说明 |
| 执行 `completed` | 本次要求已完成 | 见第 15 章：改动 + 适用检查 + 用户验收 |

- 重试复用同一 `requestId`；同 ID 不同内容返回冲突。
- 执行关联：主 AI 提供的任务关联只是候选，须对照原始事件、改动和检查；无法确认时保持“待核实”，不把下一次任意成功归给该要求。第 15 章的最小 `OutcomeScope` 在 P2 建立、P3 接入验收，不能等 P4 才做基本范围关联。
- 用户切换项目后，已有记录仍绑定原会话。已接受的任务不能靠删除记录“撤销”。

**P2 即生效的发送边界：** 本地先持久化 `pending`，串行领取并记录 `dispatching` 后才调用宿主；进程在该边界后退出或超时，重启先核对宿主事件，无法证明未发送则保持 `unknown`，不自动再次投递。同请求稳定绑定会话与内容摘要；发现多个原生事件匹配时标记重复异常，不挑一个掩盖。短 operation 缓存不能替代持久 Delivery。

P4 再补多进程租约、递增领取代号和更完整的并发／断线对账；租约过期不等于发送失败，旧工作者结果必须被代号校验拒绝。即使宿主有 requestId 检查，也不能据此承诺任意故障下严格恰好一次。此安排保留单进程先行的取舍，不推迟最基本的未知结果处理。

### 借用来源

[OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/6d04a1b58dedc95729d34e4f223d9d483aae210a/schemas/spec-driven/schema.yaml) 的“行为规格与设计分离”：原话、要求、实现建议、ChangeSet、检查分开关联；用户不填规格文档。[dsh-task-supervisor](https://github.com/gosomea/dsh-task-supervisor) 的侧栏咨询区：普通提问不暂停执行，明确控制请求才转发，交互骨架可参考。

### 验证

普通问题、否定句、引用不误触发发送；不明代词先澄清，明确原题作答只引导原入口；原要求的数字、角色、范围不丢失；双击不产生两条任务；超时保持 `unknown`；主线忙碌时消息排队而不打断。新会话能区分历史已保存、正在附带、已转交和待核实，旧要求版本的回执不会替新版本背书。

# 12 偏好与记录

### 做什么

保存用户需求原话与纠正、沟通偏好、“了解过的”历史，只供侧栏使用（R4）。

### 需求记录

- `EventWorker` 逐条登记、提取和核对用户事件；主 AI 不再持有保存工具。保留 `pending／processed／needs_clarification／failed`，重新打开时补处理。
- 多要求输入拆成可独立纠正的记录；每条关联原始事件与完整相关语境。按源事件、原文片段位置、记录类型去重。
- `userStatement`、`interpretedGoal`、`technicalSuggestion` 三者分开，不能压成一段标为用户决定。
- 原文是权威，摘要只是索引。无法可靠归纳时保留原文、标“待核对”；明显清楚的表达不重复确认。

| 层次 | 能说明 | 不能推出 |
|---|---|---|
| 来源校验通过 | 引文来自真实用户事件 | 摘要没有歪曲意思 |
| 语义核对通过 | 未发现数字、角色、否定、条件冲突 | 理解永远正确 |
| 保存成功 | 记录可读回、版本匹配 | 主 AI 已执行或用户已验收 |
| 提供给侧栏模型 | 记录进入解释输入 | 解释必然遵守；主 AI 知道这条记录 |

**纠正：** 记录保留 `replaces／supersedes`；修正后相关解释重新核对。明确的业务修改走第 11 章；“只纠正说明，先别改代码”只改记录。保存失败时保留可重试状态。

### 沟通偏好

只保留：语言、详细程度、讲解方式、先讲影响还是先讲过程、工作方式。**不做领域能力画像或能力等级。** 项目偏好覆盖个人偏好；“这个项目”不能推广成全局；一次追问不永久调整所有项目。

### 了解过的

`LearningEntry` 只记录真实交互：看过、问过、哪个解释版本、关联主题、时间。用途是减少重复讲解、方便回看。不显示“已掌握”，不把“看过方案”记录为同意（R1、R8）。

### 借用来源

| 来源 | 借用 | 不借 |
|---|---|---|
| Mnemon [三层策略](https://github.com/omdsh-dev/dsh-mnemon/blob/5a890e2c2ceb395b4aeb61f2ee60ceffb1136608/plugins/dsh-mnemon-strategy-default-three-tier/src/strategy.ts) | 组织侧栏模型输入：当前要求和少量偏好常驻，文档与历史按问题读取 | 默认 global 存储；它不保证每条事件都被处理 |
| Memobase [受限画像配置](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/src/server/api/example_config/only_strict_profile/config.yaml) | 只保留沟通偏好字段的思路 | 隐含推断；Postgres／Redis 服务 |

检索相关性不能提高材料的权威性。若以后接 Mnemon Source SDK，只做只读适配，写入仍经过 VibeGuide 校验。

多要求拆分后可独立纠正；纠正后相关解释标为待核对；双项目偏好不串；没有任何界面出现掌握程度。

# 13 侧栏界面

### 做什么

原生右侧栏注册一个 VibeGuide Tab，内部三个入口共用同一份项目状态。

| 入口 | 主要组件 | 状态来源 |
|---|---|---|
| 当前进展 | 已知目标、操作状态、检查与验收、按需影响解释、历史转交提示、追问与回执 | 任务、ChangeSet、Explanation、Delivery、OutcomeScope |
| 项目结构 | 职责图与清单、首次概览入口、扫描范围、关联高亮、证据详情 | ProjectNode／Edge、概览 Explanation 与当前变化 |
| 了解过的 | 看过／问过的主题、历史解释、重新查看和纠正 | LearningEntry 与解释版本 |

### 前端状态

前端只保留 `activeSession`、`selectedTab`、`pinnedExplanationVersion`、`lastSeenRevision`、滚动位置和输入草稿；事实与回执在服务端。不把“面板正在显示什么”写成项目事实。

当前视图与历史详情各自保留选择状态。历史解释可固定阅读，但必须显式标为历史；回到“当前进展”或点“回到最新”时清楚切回当前数据，不能把旧快照无标识地写入当前状态。用户停留阅读时仍遵守不强行替换正文的规则。

### 交互规则

- **阅读时有新进展：** 保持当前版本和滚动位置，顶部提示“有新的进展”，用户点“回到最新”才切换。依据失效时显示“依据已变化，以下为之前的说明”，不直接替换正文。
- **追问：** 回答标明针对的是正在阅读的版本还是最新状态；两者不同时说明差别。
- **切换会话：** 解除旧订阅、清空显示，再载入新快照。所有流式片段携带作用域，过晚返回的旧项目结果丢弃。
- **关闭：** 取消当前视图的在途解释；已登记的修改继续发送或对账。重新打开只刷新事实和有效缓存，不自动重发解释请求或补充摘要。关闭不等于撤销任务或已理解。
- **默认进展：** 显示记录支持的操作与检查状态；不展示主对话原文或“查看依据”区域，也不添加替代的快捷求助入口。保留现有底部提问框；后台仍读取当前对话供主动提问使用，不能把主 AI 自述当作验证结果。第一批已接入实际操作与命令检查状态；命令成功不等于功能验收通过，具体覆盖范围见开发状态文档。
- **可达性：** 键盘导航、文本选择、可读的加载／错误／空状态；不抢占主输入框，不把宿主原生问题卡搬进侧栏。
- **转交回执：** 自动转交后，在输入框下方显示原话、送达状态和“已在主对话中发出”的位置链接。
- **选项求助：** 默认只关联主对话的待回答问题；用户点击或追问才补充解释。问题已被替换时标明变化；不会因打开侧栏或进入“项目结构”自动讲解整组选项。
- **原题作答：** 侧栏输入“选第二个”等明确答案时，定位原题并引导回主对话选择，不另建任务；阅读旧题时不猜新题的选项。
- **新会话：** 项目历史照常可见，同时展示第 11 章的转交状态；提示不是继续开发的门槛，也不会自动发送历史。
- **首次概览：** 无有效概览时显示“帮我看懂这个项目”，主动请求后生成；打开页签或节点不自动调用讲解模型。
- **验收：** 卡片明确展示本次对应的要求、结果版本与试用步骤，按钮预绑定该范围；点“符合”可继承步骤并保存反馈，不强制填写可选说明。未验收仍可继续开发、关闭侧栏和提出新要求，不发停止主线的命令。

### 前后端接口契约

以下是 VibeGuide 自有接口，具体映射到宿主桥接服务的方式在 P0 验证，不是现成 SDK。浏览器不直接读写文件或持有模型密钥。

| 接口 | 输入重点 | 返回／事件 |
|---|---|---|
| `getSnapshot` | 会话、可选已知版本向量 | `SnapshotEnvelope`：当前目标、结构、变化、检查、用户验收、解释、PendingChoice、历史转交状态和多条回执 |
| `subscribe` | 会话、streamId、最后收到的 streamSeq | 有序更新；缺口或流身份变化时要求重新取快照 |
| `ask` | 主动问题／帮助入口、kind（含 project_overview）、稳定 clientRequestId、所指问题或解释 ID／版本 | 解释流或有效缓存；不能发开发任务 |
| `submitInput` | 会话、完整原文、稳定 clientRequestId、阅读背景 | `InputResult` 的单一分支；不让前端自报“已获授权”决定执行 |
| `getDelivery` | 会话、发送记录 ID | 接收、执行、检查、用户验收分别返回 |
| `correctRecord` | 记录 ID、用户原话、预期 revision | 已保存、冲突、待澄清或失败；明确代码修改仍进入修改链 |
| `markViewed` | 解释 ID／版本、真实交互类型 | 查看／追问历史；不产生掌握或同意标签 |
| `submitAcceptance` | 稳定 clientRequestId、OutcomeScope ID／版本、验收项 ID、结果依据版本、符合／不符、可选补充说明 | 已保存的 Acceptance、版本冲突或需补充；操作范围可继承服务端保存的卡片步骤，不凭笼统勾选推断全部通过 |

```ts
type InputResult =
  | { kind: 'explanation'; requestId: string }
  | { kind: 'redirect_to_choice'; questionId?: string; questionVersion?: string;
      channel: 'original_card' | 'main_conversation' | 'unavailable'; target?: string }
  | { kind: 'needs_clarification'; inputId: string; question: string }
  | { kind: 'record_correction'; operationId: string }
  | { kind: 'delivery'; deliveryId: string };

type SnapshotEnvelope<T> = {
  scope: Scope;
  streamId: string;
  throughStreamSeq: number;  // data 已反映的更新边界
  revisions: RevisionVector;
  data: T;
};
type UpdateEnvelope<T> = {
  scope: Scope;
  streamId: string;          // 本次作用域内服务流身份，重启后变化
  streamSeq: number;         // 该流的更新序号，与宿主事件 seq 不混用
  revisions: RevisionVector;
  type: 'change' | 'choice' | 'explanation' | 'delivery' | 'acceptance' | 'context';
  payload: T;
};
```

`InputResult` 表示输入进入哪个处理分支，不保证保存、发送或纠正已经成功；各分支仍须返回或查询实际处理状态。服务端保留原文与处理结果，重复 clientRequestId 不重新分类并产生另一副作用。`redirect_to_choice` 的目标由服务端验证，前端不能自报任意 URL 或通过该结果直接调用宿主答题接口。

采用“快照 + 后续序列”：先建立该作用域的更新缓冲，再获取快照和 `throughStreamSeq`，丢弃不大于基准序号的重复更新，依次应用其后的更新。同一流内序号连续且单调；客户端发现缺口、重连或 streamId 改变时重新握手取快照，不能静默跨过遗漏；旧项目的晚到片段按 Scope 丢弃。

**一致性边界：** 快照从项目串行提交入口维护的已提交读模型取得，数据、版本向量与序号属于同一个提交边界。只在持久状态提交成功后发布相应更新；跨 Ledger 操作尚未对账完成时保留上一完整读模型并标明待更新，不能把分别读取的半完成状态拼成成功快照。完整快照发布前必须完成所需对账与读模型刷新；版本向量相同本身不是跨文件事务完成的证明。

解释流的未保存片段单独作为临时流传输，携带 Scope、streamId、requestId、片段序号与 Basis，不推进上述持久更新水位；最终解释落盘并复核依据后才发布 `explanation` 更新。重启或依据变化时终止旧临时流，不能把中途文字当成已保存结论。

所有查询、订阅与变更均由服务端核对会话权限、项目绑定与记录归属。稳定请求 ID 绑定内容摘要；重复请求复用结果，同 ID 不同内容返回冲突。错误至少区分会话不可用、项目改变、版本冲突、记录忙碌、模型不可用、未保存、发送未知和跟踪不完整。前端保留可重试的草稿，不提前显示成功。

### 借用来源

assistant-ui 的 [ExternalStoreAdapter](https://github.com/assistant-ui/assistant-ui/blob/7beac6fc271435b8c60e842a8e5ba327725d25e2/packages/core/src/runtimes/external-store/external-store-adapter.ts)：先借鉴阅读锚点和流式状态，再评估是否引入最小组件。`onNew` 只交给 GuideService，`onCancel` 只取消解释；禁用前端工具执行，不建第二份主会话历史；其前端队列不能替代持久发送记录。

窄栏可读；固定阅读不被打断；输入草稿不丢；切换会话无串项目；关闭重开后无重复监听。

```ts
  collections: Array<{ scopeId: string; membershipHash: string; coverage: string }>;
  sourceRefs: SourceRef[];
  sidebarInputs: SidebarInputRef[];
  parserVersion: string; promptVersion: string;
};
```

这些是需要冻结的自有契约，不改变宿主事件结构。`SourceRef` 只用于真实宿主持久事件；尚未送达的侧栏输入和不必发给主 AI 的验收使用服务端认证取得的 `SidebarInputRef`，不得由模型或前端伪造。来源真实与动作授权分开判断：当前用户的明确修改可转交，历史引文、模型说明和验收点击不能被扩大为新的开发授权。

版本向量用于发现跨文件读取竞态：读取前后核对 revision，不一致时重读或保留待核对。判断解释是否适用则看实际依赖、文件和集合，不能因 guide 自己保存缓存导致全局失效。集合依赖用于“只有这些模块／尚无某能力”等结论，覆盖新增或删除文件、任务要求集合变化；没有完整覆盖时不作绝对不存在的结论。

|---|---|---|
| `EventJob` | 会话、seq、事件 ID、处理器版本、状态、尝试次数 | 07 |
| `ChangeSet` | 事件范围、文件摘要、涉及模块、`Basis` | 07 |
| `PendingChoice` | 原问题 ID、原题与选项、版本、状态、来源、问题类别、原生作答入口 | 07、10、11 |

| `Explanation` | 变化、影响、取舍、限制、来源、`Basis`、版本 | 10 |
| `Claim` | 结论类型、文字、依据引用、不确定性；与系统状态分开 | 10、15 |

### 存储布局

项目标识沿用工作目录 `realpath` 的摘要；沿用安装器配置的 `vibeguide-p0-state` 目录（旧名称不代表还有第二种模式）。

```text
<storageRoot>/
  personal/preferences.json          # 已有：个人沟通偏好
  <projectId>/
    project.json                     # 已有：需求与任务（continuity）
    workbench.json                   # 已有：事实与检查（workbench）
    receipts.json                    # 已有：工具证据回执
    guide.json                       # 新增：队列、发送记录、解释、结构、词条、验收
```

**一个事实一个来源：** 需求归 continuity，事实与证据归 workbench，队列、投递、解释、结构归 guide。外部工具不能再维护一套可独立改写的需求。

### 写入规则

- 沿用独占锁、预期版本、临时文件替换、fsync、读回确认；锁内只做短事务，不跨模型调用持锁。
- 冲突时重读并重算，写入返回 unknown 时先读回核对；失败不声称“已记住”。单进程内所有写入走项目串行提交入口，不把模型和网络等待放进该入口。
- 需要原子提交的新状态放在同一个 `guide.json` 内，例如“收到侧栏输入”和“创建待发送记录”。
- 现有多个 Ledger 没有跨文件事务：写入旧需求库时用稳定操作 ID，先记待提交、再写目标、最后记完成；崩溃后按 ID／内容摘要对账。
- 宿主原始历史只存引用和必要摘录，不全量复制。
- 新增 `schemaVersion` 与迁移器；迁移前保存可恢复副本；遇到更高未知版本时停止写入。

**单进程恢复最低要求：** 现有 O_EXCL 锁文件需要识别异常退出后遗留的持有者。只在能确认旧进程已结束、且取得独占接管资格时恢复；不能仅凭锁年龄或未收到心跳就删锁。无法确认时报告记录忙碌并阻止新写入／发送，保留已有状态。跨进程并行工作、租约和旧工作者 fencing 在 P4 实现，不能靠自动删锁提前宣称支持。

### 单写者身份与启动顺序

`WriterGuard` 覆盖规范化后的同一 `stateRoot`，由宿主级服务持有，所有项目队列、个人偏好写入和发送工作者共享。记录 `ownerInstanceId`（随机实例 ID）、PID、可核实的进程启动标识、stateRoot 与取得时间；PID 或时间不能单独证明所有权。进程内服务注册还需区分插件实例，热重载不能因 PID 相同就同时启动两个工作者。

1. **取得资格：** 使用能随持有进程结束释放的宿主／平台排他锁；持有期间不删除、替换锁文件路径。元数据用于核对，不代替排他锁。P1 验证运行环境可用的实现；若不能可靠取得独占资格，就停止后台写入与发送，保留只读状态和主对话开发，不退回“看起来过期就删锁”。
2. **恢复记录：** 取得 guard 后核对身份，处理本地跨 Ledger 未完成操作与遗留短事务锁。只接管已确认失效且不属于活动实例的锁；无法确认则保持忙碌，不开放发送。
3. **对账投递：** 扫描本地 `dispatching / unknown`；查询宿主同请求的接收与事件证据。无法确认已发送或未发送时保留 unknown，不把它重新置为 pending。
4. **恢复事件：** 登记新事件唤醒但暂不开始发送；补读宿主历史并按稳定 ID 去重，恢复本地 pending 和旧 processing 作业，建立一致读模型及快照边界。
5. **开放服务：** 本地恢复完成后开放写入与调度；某条投递仍为 unknown 不阻塞其他无关请求，但该条不能重发。读取到的宿主历史缺口仍须展示，不能当完整恢复。

卸载或热重载先撤销旧实例的调度资格，停止领取任务，并处理其在途提交；已开始的投递无法确认结果时保存 unknown。释放 guard 前确保旧实例不会继续提交或发起新发送，晚到回调按实例身份丢弃；新实例取得 guard 后按上述顺序恢复。异常退出由排他锁释放持有资格，持久记录仍须对账，不能因锁释放推断投递未发生。这不新增跨进程并行执行能力。

`EventJob`、输入和 Delivery 自身的稳定 ID 与内容摘要承担业务去重；原 Ledger 最后 128 条、ProjectStore 最后 64 条 operation 记录只是短期缓存。完成事件的连续水位、缺口和归档索引须一起维护，历史裁剪不能使旧输入成为新任务。

### 容量

现有通用 Ledger 上限 8 MiB，ProjectStore 4 MiB。`guide.json` 设明确预算，归档已完成历史，保留索引；不得为腾空间删除未完成发送和待处理任务。达到上限时停止新增派生内容、显示记录异常，主线继续。

在同一个 guide Ledger 内给用户输入、未完成工作和发送状态保留容量，解释／词条／结构历史设更低的软上限，先停止派生内容增长。容量预算按允许输入大小和待处理上限计算，不能承诺无限保存。核心容量也耗尽时明确未保存并禁止投递，前端保留待重试内容；不改变本版单 guide Ledger 的起步方案。

项目移动会改变身份，不按同名自动合并；切换项目不复用前一个项目的队列、解释或要求。

# 15 证据、验收与失效

### 修复现有缺口

`evidenceStatus()` 能判断部分证据过时，但 `currentFacts()` 不据此过滤关联的 observed 事实，导致失效观察继续进入侧栏解释输入。先修复，再做侧栏，避免把旧结论用更漂亮的界面再次展示。

### ContextResolver

读取来源 → 计算适用性 → 沿依赖关系传播 → 输出当前有效事实、历史事实和待核对项。项目结构、人话翻译、解释和转交消息里的“必要上下文”都调用它，不各自实现过滤规则；它没有通往主 AI 上下文的出口（R4）。

```text
文件／需求／检查条件变化
  → 对应证据不再适用
  → 依赖该证据的观察标记 needs_review
  → 依赖观察的结构结论、摘要与解释标记过时
  → 重新检查或生成后，建立新版本与新依据
```

图关系失效用显式依赖 ID 传递，处理环和重复节点。解释按第 14 章记录具体依赖和必要的集合摘要，无关文件变化不让全部内容变灰；依赖范围未知时保守标“待核对”并说明原因。查询时核对适用性，后台失效传播只用于提速，不能是防止旧事实进入解释输入的唯一保障。

### 三类状态分开

| 维度 | 示例 | 规则 |
|---|---|---|
| 检查结果 | 通过／失败／无法判定 | 看检查内容与原始结果，不只读退出码 |
| 证据适用性 | 当前适用／过时／需重新在线检查 | 看相关文件、要求、配置及外部环境 |
| 用户要求 | 当前要求／被用户明确替代 | 代码偏离或检查失败不能删除要求 |

没有检查记录的普通开发不能显示“已验证”。外部服务的历史成功不保证现在可用，显示检查时间与限制。

### 停用主 AI 记录工具后的证据来源

保留原生工具事件观察和已存工具回执的校验能力；后台观察器将实际调用、返回、涉及文件与版本提交给 EventWorker。旧版依赖主 AI 调用 prepare／check 等记录工具建立的关联，不能假定在移除工具后仍会自动存在。先验证哪些关系可由原生事件可靠重建；不能可靠关联要求或检查范围时记为“待核对／尚未验证”，不要求把 VibeGuide 记账工具重新装回主 AI，也不把任意成功退出当功能通过。

新增只读 `NativeCheckCapture` 作为证据输入，提交仍经 EventWorker：

| 字段组 | 内容与约束 |
|---|---|
| 原生身份 | Scope、真实调用 ID、工具名、调用与结果 SourceRef；未持久化的事件只保存可核验临时标识，不伪造 seq |
| 执行前依据 | 可证明属于执行前的文件哈希／不可变快照、要求版本、检查目标与范围、取得方式和时间；缺失时明确标记 |
| 执行结果 | 真实回执、内容校验值、执行结局与时间；安全过滤不破坏可核对的原生关联 |
| 适用性 | 结果与原调用匹配、基线完整性、相关文件／要求是否变化、外部依赖限制；状态为待结果、待核对或可供检查判定 |

实现顺序为：解耦 `workbench/plugin.ts` 中“主 AI 可见旧工具才观察”的条件 → 观察真实调用并取得可靠基线 → 关联真实返回 → 核对检查范围与当前依据 → 保存检查证据。旧准备记录及历史回执仍按原有范围读取，不能因迁移补造新的执行前基线。

**P0 能力验证：** 核对宿主是否提供可靠执行前入口、不可变执行快照或等效的版本证据。异步收到 `tool/call` 后开始读文件，不保证读到执行前状态；不能为了取快照拦停主线。只有能证明检查运行所对应版本与范围时才建立适用检查，否则保存实际运行事实并标“基线或关联待核对”。若该能力无法取得，记录产品影响并保留未完成状态，不能把“看到了成功日志”当成已通过验收出口。

移除旧工具与重建观察链在 P1 同步实施。检查前后改文件、主 AI 并行操作、观察器中途退出、启动补读都必须验证；一次成功退出只证明该工具调用的结果，不自动证明某项用户要求实现。

### 要求、改动、检查与验收的最小关联

P2 引入 `OutcomeScope`，P3 在此基础上提供验收；P4 只扩展复杂关联与故障对账。字段至少包括稳定 ID／版本、Scope、要求 ID／版本集合、Delivery ID 集合、ChangeSet ID 集合、检查及各自覆盖的验收项、Basis、关联依据和 `resolved / unresolved` 状态。用户直接在主对话提出的要求可没有 Delivery，但仍需真实用户来源。

- 关联允许多对多，同一次改动可实现多项要求；共享文件路径、时间相邻或主 AI 的完成声明只能作为候选，不能单独判定归属。
- `resolved` 表示关联范围明确，不等于检查通过。无法明确归属时保留 unresolved，并展示“这次变化对应哪些要求仍待核对”。
- 每个验收项明确对应要求、实际行为、试用步骤和预期结果；卡片展示联合范围及结果版本。检查和用户反馈按覆盖项计算，不能因为其中一项通过就覆盖整张卡或其他要求。
- `Acceptance` 引用 OutcomeScope ID／版本、验收项 ID 和结果 Basis；提交时重新核对。已过时或范围不清时保留用户反馈并标为待关联／需重新确认，不给旧结果贴当前完成标签，也不要求用户填写技术 ID。
- 对每条要求分别计算完成状态：对应改动、适用检查、覆盖该要求的用户验收齐备，关联范围明确、依据仍有效且无已知未满足项，才显示完成。纯视觉、文案等要求也须定义适用检查的范围，不能由一次笼统点击补造检查记录。

### 用户验收入口（新增）

“完成”需要三样依据：对应改动、适用的检查、用户验收（R8），且没有已知未满足项。前两样来自事件与 workbench；第三样由用户在“当前进展”的变化卡上提供。**验收只影响完成标签，不是主线继续开发的放行条件。**

- 卡片给出“我试过了，符合要求”／“我试过了，不对”两个按钮，以及可选的一句话说明。
- 保存为 `Acceptance`：OutcomeScope 及版本、具体验收项、要求及版本、被验收的结果与 Basis、符合／不符、用户实际做了什么和看到了什么、时间、受认证的用户来源。侧栏点击不伪造主会话事件；采用 SidebarInputRef，用户在主对话反馈时才关联原生 SourceRef。
- 卡片应明确对应行为和验收范围；若用户按卡片所示步骤试用，可记录该步骤和用户的符合／不符反馈，补充说明可选。只点一个没有行为范围的笼统按钮时，不推断测试了全部功能，必要时询问所试内容。
- 卡片中的步骤与预期结果由服务端按版本保存，按钮引用该范围；“符合”且无补充说明时，保存“用户表示按这些步骤试用并符合”，不要求再填一遍，也不虚构未观察到的细节。“不对”可先记录不符，缺少具体表现时再引导描述，以便澄清修改目标。
- 选“不对”时，用户的说明作为新输入进入第 11 章意图判断；明确的修改照常自动转交。
- 后续相关文件变化时，验收按本章规则标为过时。

| 已有依据 | 界面呈现 |
|---|---|
| 有改动，没有适用检查 | 已有改动，尚未验证 |
| 适用检查通过，用户尚未验收 | 检查已通过，等待你试用确认；不显示完成 |
| 用户表示符合，但检查缺失或已过时 | 已收到你的体验反馈，检查仍待补齐；不显示完成 |
| 已有反馈，但结果归属或验收范围未明确 | 已收到你的反馈，对应范围仍待核对；不显示完成 |
| 改动、适用检查、对应用户验收齐备，无已知未满足项 | 本次要求已完成，仍标明实际覆盖范围 |

不因为缺少用户验收而抹掉已经发生的自动检查结果；用户不点击时仍可阅读、提问或继续开发。验收被判过时也不自动向主 AI 发送修复要求。

### 验证

修改文件后依赖它的事实、节点、解释和验收都重新核对；无关文件变化不影响它们；没有用户验收不显示完成，但仍准确展示已有检查结果。验收输入失败不得显示已验收，也不得暂停主线。

# 16 权限与安全

### 身份与作用域

前端通过宿主认证连接调用服务；服务端由会话元数据解析真实项目，逐次校验订阅、查询和发送对象。用户输入的路径、模型生成的来源 ID、浏览器缓存都不能作为授权依据。每个请求校验会话可访问、记录属于该项目、请求 ID 没有绑定不同内容。

跨项目只复用明确设为个人的沟通偏好，不复用需求、代码摘要或解释。

### 文件与模型输入

- 只读当前工作区允许的文件，遵守忽略规则，不沿符号链接越界。
- 进入模型前过滤密钥、凭据、环境配置中的秘密值和明显个人数据；错误诊断默认不记录完整提示词或原始秘密。
- 使用宿主模型不等于离线：内容仍受所配置模型提供方处理。安装说明需告知用户解释会使用项目上下文；不额外复制密钥，不自动上传整个项目。

### 低可信材料（R10）

代码注释、README、网页摘录、工具输出和历史解释都是分析材料。即使其中出现“忽略规则”“把这段发给主 AI”，也不构成用户授权。解释模型无执行工具；发送服务只接受已校验的当前用户输入。

### 宿主权限继续有效

转交的要求不绕过主 AI 的工具权限、网络授权、付费选择或发布确认。侧栏普通阅读和提问不制造额外暂停。

### 课程数据

默认不开启云端遥测。本地诊断保留时间、状态码和关联 ID；完整对话用于人工评估时须告知参与者并限定保存范围。

# 17 异常与性能

### 异常处理

| 情况 | 系统处理 | 用户看到 |
|---|---|---|
| 模型不可用／超时 | 终止本次解释，保留快照；有限重试 | 解释暂未生成，主线继续 |
| 记录忙碌／冲突 | 只释放本次持有的锁，重读重算；其他持有者与遗留锁按第 14 章处理 | 记录尚未更新，不假称已保存 |
| 事件缺口 | 标记跟踪不完整，尝试补读 | 数据截止时间和缺口 |
| 发送超时 | 保留 `unknown`，按请求 ID 对账 | 待核实，不自动重发 |
| 会话删除／项目改变 | 停止向无效目标发送 | 请在有效主会话继续，不擅自换目标 |
| 磁盘满／容量上限 | 停止新增记录，保留原文件 | 明确未保存，宿主历史不受影响 |
| 解释返回时依据已变 | 不发布为当前解释 | 提示已有新变化 |

错误码区分：会话不可用、项目绑定改变、版本冲突、记录忙碌、模型不可用、保存失败、发送未知、跟踪不完整。前端用人话说明影响，原始诊断放在详情里。

### 起始预算（待测，不是已有结果）

| 指标 | 目标 |
|---|---|
| 事件监听回调 | 不做 I/O 或模型调用；p95 < 10 ms |
| 本地快照查询 | p95 < 300 ms |
| 点击／判定发送后的本地反馈 | 200 ms 内显示“正在发送”，不提前显示“已发送” |
| 解释首个可读响应 | ≤ 5 秒 |
| 常规问题完整返回 | ≤ 20 秒 |
| 模型并发 | 全局 2，单项目 1；用户主动追问优先 |

### 成本与积压

只由用户主动求助创建解释请求，结合相关范围检索、版本化缓存和在途请求去重，减少重复调用。变化合并只更新事实，不调模型。限制每次输入 token、文件读取总量和输出长度；达到预算时缩小分析范围并说明，不截断关键否定或条件。队列长度、失败次数、补读缺口和 `unknown` 数量需要可观测。

另外记录 `choice_help / term_help / project_overview / user_question / change_help` 等主动请求原因、对应用户请求 ID、缓存命中和调用次数。没有主动求助时，额外摘要与解释调用为零；主线和后台记录提取分别计量，不能推出整个系统零 token，也不得以记录提取名义生成面向用户的摘要。设置每回合／项目的解释预算，具体阈值由 P0/P2 实测确定；超出时保留已有事实并说明暂未生成，不反复自动重试补词。文件合并、重要检查返回或回合结束均不触发模型；用户主动追问不必等整回合结束。

## 第三批落地说明（2026-10-28，alpha.4）

本节记录当前实现，前文仍是最终设计目标。功能与证据清单见 [开发状态](IMPLEMENTATION_STATUS_V2_2.md)。

### 实际数据流

```text
宿主当前会话 → projectFor / snapshot → 当前项目身份
  ├─ projectView：有界文件指纹 + 本地 ProjectRecord → 旧概览 / 变化标记 / 试用反馈
  ├─ overview（显式点击）：受限内容摘录 → 独立模型 JSON → 来源/长度校验 → 本地概览
  ├─ history：本项目各会话的 Explanation + Annotation → 分页历史
  ├─ 选中结构/历史 → ContextRef → 服务端核对 → 原输入框 submit → 只读讲解或原有分流
  └─ 已送达 Delivery → prepareReview（显式点击）→ TrialCard → 逐步用户反馈
```

`ProjectRecord` 按项目保存，独立于按会话的 `GuideRecord`，但共用已有存储锁与串行原子提交。源码摘录仅用于当次请求，不落盘；只持久化指纹、引用投影、生成结果及用户主动保存的纠正/体验反馈。读取、缩放、节点选择、分页、纠正、反馈均不调用模型。概览/试用按文件依据、模型路由、提示版本及相关要求缓存；模型调用不占持久化锁。

### Gateway 和引用边界

所有接口继承已有 owner 校验和 session resource 绑定；每次重新核对当前项目与 VibeGuide 模式。

| 接口 | 核心输入 | 行为 |
|---|---|---|
| `projectView` | sessionId, projectId | 读取本地概览及变化适用性，不生成 |
| `overview` | sessionId, projectId, clientRequestId | 用户主动生成/更新概览，单个生成通道，45 秒超时 |
| `history` | sessionId, projectId, offset | 每页 20 条历史，最多覆盖 100 个本项目会话 |
| `annotate` | 同上身份、explanationId、version、action、text? | correct/retire，版本冲突拒绝，保留原记录 |
| `prepareReview` | 同上身份、deliveryId | 仅针对已送达要求生成试用步骤 |
| `feedback` | 同上身份、cardId、stepId、fileDigest、result、note? | 记录 pass/fail 用户体验，不推导完成状态 |

`ContextRef { kind, id, version }` 只能引用本项目已保存的节点或解释，由服务端解析，客户端不能提交任意背景文本。节点引用携带概览版本；历史引用携带解释与最新纠正的版本散列。旧结构可追问，但明确标为历史；被停用的解释和过期纠正版本不能进入上下文。解释生成过程中再核对项目和引用，晚到答案不能覆盖新项目或新选择。浏览器草稿保留引用及稳定请求 ID，恢复后不自动发送。

### 图形与解析的实际取舍

第三批使用原生 SVG 加等价按钮列表，适合当前最多 8 个节点的只读视图，支持缩放与键盘操作，未引入 React Flow 运行时依赖。React Flow 仍是后续复杂图形的候选，不把“已有 SVG”称为完成图编辑能力。节点职责、使用影响来自 AI 对有限摘录的推测；关系线只从实际读取文件中的字面量相对 import/require/src/href/@import 解析。动态导入表达式、别名、运行时数据流、远程服务和非 Web 语言关系仍未知。不能用节点或连线证明业务功能已实现。

源码范围沿用最多 500 文件、8 MiB、每文件 1 MiB 的限制，结构扫描预算 250 ms；内容摘录另限 24 文件/24,000 字符/每文件 1,800 字符。读取前后核对路径、inode、大小/时间与已有内容散列，拒绝符号链接、硬链接、私有存储及秘密路径。短摘录和有限覆盖是明确的质量限制，不代表完整项目理解。

### 试用反馈和完整 OutcomeScope 的差距

当前实现绑定 `projectId + Delivery + TrialCard + stepId + FileBasis`，足以保存“针对哪条要求、哪个已观察文件版本、哪一步”的体验反馈。步骤由模型建议，原始要求另行保留；无法保证步骤覆盖所有需求条件。文件改变时旧卡/反馈历史化，不自动重新生成，也不触发修复任务。

**尚未实现要求与实际 ChangeSet/检查结果的精确自动关联，因此不展示功能完成、全面验收通过或自动合并多个要求的完成状态。** 已有检查回执独立显示。扫描不完整时，体验反馈只作为当时用户自述，不声称完整环境版本已核对。完整 OutcomeScope、专门的改动影响解释、跨会话历史要求可见转交和用量预算仍是后续工作，不由本批结构图替代。

### 记录、预算和并发

`ProjectRecord.support` 是可选增量字段，旧记录不因读取而重写；沿用单写者锁、全局串行写、原子替换和读回。个人默认偏好存于内部专用项目记录，业务项目只获得有效偏好，不枚举其他项目。项目覆盖优先。设置保存有请求 ID、内容摘要及版本校验。模型调用不持有磁盘写锁。

`Usage` 在模型调用前持久化 pending。失败/取消仍计入尝试预算，重载遗留 pending 视为未知，不退款后自动重试。保留近 30 天及当前轮次记录，上限 5000；满时拒绝新的模型请求。缓存/词条统计按会话与请求 ID 去重，不消耗模型预算。原生 `turn/start.data.turn` 是轮次依据，未知时按会话累计，不随工具事件重置。

宿主 `TokenUsage` 的 inputTokens 是未缓存输入，cacheReadTokens/cacheWriteTokens 是互斥缓存输入，显示输入总数时相加；输出计 outputTokens。没有 usage chunk 就标记未报告，不从字数估算 token、费用或节省金额。全局最多 2、每项目最多 1 个独立模型调用，忙时直接告知，不偷偷排队重试。

### 偏好、概念和缓存

偏好是 language/detail/style/order 有限枚举，只附加到独立侧栏提示，不改变主对话。解释、概览、试用与分析缓存均包含偏好版本；变化后不自动重写历史。纯概念采用保守别名和“是什么 / what is”等形式匹配；项目特定判断仍需要项目资料。词条是本地通用参考，不是实现证据。

### 故障资料和建议

`Operation.diagnostic` 只保存原生失败回执中最多 2000 字符的脱敏文本，不增加原文展开区。TroubleView 按本会话隔离，限最近 12 次尝试、8 组失败及 8 条未满足的试用反馈。相同 checkKey 的最后连续失败才计为重复，之后成功或未知结果会中断连续；文件变化后标记旧版本。资料不完整时不保证连续性。

按需 trouble 分析缓存还包含尝试版本，同源码下的新失败回执也使缓存失效。每次最多 3 条选项及修改/检查草稿，点击仅填入现有输入框；用户发送后才走原有 submit 分流。日志和模型输出不能直接执行。

### 结构索引和历史

ProjectIndex 按真实目录维护最多 8 个项目的内存指纹缓存；设备/inode/大小/mtime/ctime/链接数与路径核对一致时复用散列，变化时重读。拒绝符号链接、硬链接、秘密路径、构建产物和插件存储。限制 1500 ms、5000 文件、64 MiB 总量、1 MiB 单文件；单次系统读取不保证硬截止，越界标记 incomplete。扩大索引只用于结构，不能扩大检查通过的证明范围。

保守解析 Web 字面本地引用、Python 模块/相对导入、C/C++ 引号 include、Ruby require_relative、PHP 字面相对 include/require。外部模块、别名、动态路径仍未知。概览保留最近 30 版，比较以文件成员重叠对应职责，报告描述与文件范围变化；拆分合并可能表现为新增/消失职责，不能解释为确定重构。浏览、比较不调用模型，不提供恢复入口。
