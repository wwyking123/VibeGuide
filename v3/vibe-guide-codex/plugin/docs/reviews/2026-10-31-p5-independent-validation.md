## 已确认问题

### 1. P1：明确的修复要求无法转交，确认后仍然卡在澄清

用户发送“帮我修复保存失败的问题。”，返回澄清；接着回复“确认修改”，依然澄清，主对话收到 0 条要求。隔离故障建议使用的“请定位并修复失败的检查，保留已有要求及数据。”也有同样问题。对照句“把回答保存功能改成能正常保存。”则成功转交 1 次。

**原因：**`src/guide/intent.ts:9` 的动作规则不包含“修复”；第 19 行只接受已标记为候选修改的确认，而第 49 行的一般澄清没有这个标记。`src/guide/communication.ts:73` 沿用该判定。

**证据：**实际 `CommunicationService`、`GuideStore`、磁盘记录与固定宿主接收回执；没有模型或网络。不是仅看正则的推断。

**修复方向：**支持日常修复表达；对不确定对象保留澄清，并允许用户明确确认原要求。仍需保护“只解释”“先不改”、引用、权限和主对话原题边界，不能简单把所有确认都转交。

### 2. P2：问题已通过检查，旧排障分析在追问时仍被标为当前

同一检查先失败、生成排障分析，再成功，文件不变。界面数据正确显示失败数为 0、旧分析 `historical=true`；继续问该分析时，交给讲解的材料却是 `historical=false`，仍带着旧失败结论。

**原因：**`src/guide/work.ts:46` 检查 `troubleVersion`，但 `src/guide/project.ts:196–198` 解析分析引用时只核对文件和需求，没有使用相同的故障状态版本规则。

**证据：**备用 agent 的实际构建模块与磁盘反例，主 agent 复跑通过。固定分析输出，仅证明追问材料标记错误；尚未证明真实模型一定会给出错误答复。

**修复方向：**显示、追问及缓存使用统一的时效判定。检查结果改变时，应明确保留为历史或提供最新状态，而不是把历史结论重新标成当前。

### 3. P2：排障内容重复，下一步操作离当前解释太远

一次排障同时保留普通 Explanation 和结构化 Analysis。“当前进展”先显示没有建议按钮的解释，然后显示其他进度与项目要求，最后再次显示排障分析及下一步建议。隔离样例有 4 条项目要求，使可操作的建议落到首屏之外。

**位置：**`src/guide/service.ts:105–119`、`src/client/index.tsx:195–215`、`src/client/work-panels.tsx:24–57,78–89`。

**证据：**agy 在 1050 × 820 视窗中操作并检查页面快照；主 agent 核对截图与渲染顺序。截图见 [agy-trouble-progress.png](../../output/review-2026-10-31/agy-trouble-progress.png)。

**修复方向：**同一分析只显示一张完整卡片，解释与下一步建议相邻；其他项目要求按当前任务关联展示或收起。保持用户先查看/修改建议再发送的现有边界，不增加自动修复或自动摘要。

### 4. P2：失败记录没有告诉用户究竟哪一步失败

后端有检查标签、尝试标签和有限诊断信息，前端却只显示“一项检查未通过”“运行操作或检查：未成功”等通用句子。用户即使展开最近尝试，也难以区分具体失败对象。

**位置：**`src/guide/trouble.ts:23–27` 已生成标签；`src/client/project-panels.tsx:91–95` 未展示。

**证据：**agy 页面快照及主 agent 源码核对；未做真人理解测试。

**修复方向：**显示简短、可辨认的操作对象和结果。无需自动调用模型，也不恢复已取消的主 AI 原话或“查看依据”面板；不应把长命令和错误堆栈直接塞给非技术用户。

### 5. P2：较大项目的结构状态在展示和追问时不一致

510 个完全未变的文件：概览读取完整，界面显示当前版本；追问其中节点却被标为历史材料。

**原因：**概览索引在 `src/guide/structure.ts:8` 使用最多 5000 文件的范围；节点解析在 `src/guide/project.ts:206–207` 使用默认最多 500 文件的小范围指纹，两种范围的摘要被直接比较。

**证据：**510 个临时文件、实际构建模块、固定结构输出；主 agent 复跑确认。

**修复方向：**概览与节点追问复用相同扫描口径；读取不完整与真实内容变化应分别表达。这里证明的是时效误判，不是数据丢失。

### 6. P2：两个窗口保存偏好时，旧版本可能覆盖新版本

两个请求携带同一个初始版本。控制异步时序，让较新的保存先落盘为 `zh-CN`，旧请求仍可随后成功保存为 `en`；两条请求都被接受。

**原因：**`src/guide/support.ts:38–47` 先检查一个版本，然后重新读取写入基线。在两次读取之间发生更新时，旧请求会把新设置当成自己的有效基线。

**证据：**人工控制 `await preferences()` 边界的并发顺序，所有保存经过实际构建代码与磁盘 Store；不是浏览器频率测试，也不表示每次同时保存都会发生。主 agent 复跑确认。

**修复方向：**在写入锁内校验用户所持版本对应的设置，过期请求明确提示刷新；不能用稍后重新读取的版本替代用户原版本。

### 7. P2：本地概念查询过于依赖固定句式

“API是什么”命中本地词条；“API是什么意思？”“什么是本地存储呀？”“通俗讲讲缓存”“数据库是干嘛的？”都未命中。已有本地内容仍可能走模型路径，预算耗尽时不能像词条按钮一样直接回答。

**位置：**`src/guide/glossary.ts:19–22`、`src/guide/service.ts:94–104`。

**证据：**agy 静态定位，主 agent 对实际 `lookupConcept()` 执行确认。预算耗尽后的完整浏览器路径未在本轮点击验证，相关影响来自调用路径分析。

**修复方向：**为纯概念问题增加常见口语匹配；当问题涉及“我的项目”“这次改动”时仍保留项目上下文，不能用通用词条冒充项目分析。遇到预算限制，可直接提示已有的本地概念入口。

## 其他意见的取舍

agy 还提出了历史比较方向和节点修改上下文问题。本报告没有把它们合并算入上述 7 项：

- 比较函数本身按所选 from/to 计算；选择旧版为目标、新版为基线时结果反向是定义所致。真正需要明确的是“与哪个旧概览比较”的文案及比较方向，而不是直接认定算法算反。
- 无文件路径交集的同名职责被分为新增/移除，是当前保守匹配的局限；同名也不能证明相同职责，不应无条件强行配对。
- 输入框已明确提示“关联内容只用于讲解；修改要求请写清具体对象和效果”。不自动把讲解材料转成修改授权是现有边界；“把这部分改成……”是否应先澄清仍值得单独验证，本轮不声称它已导致实际错误修改。
